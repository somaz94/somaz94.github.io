    Migrating to EKS Auto Mode: Five Traps, Four of Them Silent

    102 Terraform addresses became 17 — what the migration deleted, what it left behind, and the failure modes that leave every dashboard green


    Overview

    Part 1 compared the four ways to get compute in EKS and argued that Auto Mode is, at heart, Karpenter with AWS as the operator. This post is the record of moving a real production workload onto it.

    To move a production game workload from a cluster running self-managed Karpenter to a new cluster running EKS Auto Mode, I ported the infrastructure code and validated it against a test workload first. Same team, same application, same region — which makes the two a before-and-after pair measured on real data rather than two opinions about infrastructure.

    The reduction in infrastructure code was larger than I expected. So was the residue. And the part worth your attention is neither: four of the five traps I found while preparing the migration are silent failures — the dashboard reports success. A StorageClass that creates cleanly and never provisions a volume. A PVC that reports Bound while its pod cannot start. An application pod that is Running, an ArgoCD tile that says Synced/Healthy, and no load balancer at all.

    This post covers the size of the reduction, then the five traps and how each was fixed. Four of them show up while every monitor is green.

    Identifiers below are sanitized; the API surface, the counts and the measurements are real.


    1. What disappeared, measured

    I counted Terraform state addresses before and after, because “less to manage” is a claim and addresses are a number.

      Before After
    Cluster module 73 17
    Karpenter module 29 0
    Compute total 102 17
    Managed addons declared 7 2 (3 with EFS)
    Infrastructure code 433-line eks.tf + 87-line karpenter.tf 32 lines in the calling stack (the module body is about 340)
    Node-related Terraform arguments 12 0

    The 29 Karpenter addresses are all jobs Auto Mode took over: the controller IAM role and its Pod Identity association, the Karpenter node IAM role with four policy attachments (Auto Mode’s own node role is counted inside the cluster module’s 17), an EKS access entry, an SQS queue for Spot interruption notices with its policy, and five EventBridge rules with their targets. Auto Mode runs the Karpenter engine itself — interruption handling included — so none of it is needed any more.

    The arguments that left the codebase entirely:

    instance_types · capacity_type · min_size / max_size / desired_size · ami_type · ami_release_version · block_device_mappings · metadata_options · cloudinit_pre_nodeadm · taints · labels

    Two scripts I wrote for version management have nothing to do on the Auto Mode cluster. The first looked up the addon versions AWS offers for a target Kubernetes version and checked them against the code at every upgrade. The second polled SSM for new AMI releases, because a pinned AMI version means security patches stop arriving on their own and something has to tell you they exist. Under Auto Mode the platform manages the AMI, and the two or three managed addons that remain are deliberately left unpinned so they follow the latest compatible version — so neither script is needed. Both stay only for as long as the old cluster runs.

    The node stage of the upgrade runbook is gone too. Upgrading the old cluster meant moving the control plane first, blocking node drift with the karpenter.sh/do-not-disrupt annotation, and then running the node roll as a separate step. On Auto Mode you upgrade the control plane and the platform rolls the nodes.


    2. Five things that are still yours to manage

    AWS managing compute does not make the engineering disappear.

    • CoreDNS changes shape. It no longer runs as a Deployment of pods; Auto Mode runs it as a node-level system service (Under the hood: Amazon EKS Auto Mode). If the cluster also has nodes Auto Mode does not manage — a managed node group, say — those nodes cannot reach the node-local DNS service, and you have to keep a CoreDNS Deployment for them.
    • NodePool manifests are still yours. The built-in system pool is tainted CriticalAddonsOnly. The pools your application workloads run on are still objects you write and keep under version control.
    • The bootstrap is circular. The first build deadlocks on scheduling — section 3.
    • EFS is out of scope. storage_config covers EBS block storage only. The EFS CSI driver is a managed addon you install yourself.
    • IRSA does not fully retire. Most pods can move to Pod Identity, but a single third-party workload that cannot — here, ECK-managed Elasticsearch writing S3 snapshots — is enough to keep the OIDC provider and IRSA alive. And while the Pod Identity Agent ships built in, the associations themselves are still Terraform you write.


    3. The bootstrap is circular, and it bites on rebuild

    Provisioning a cluster with node_pools = ["system"] creates exactly one node pool, tainted CriticalAddonsOnly, and no ordinary pod can schedule on it. Enabling the built-in general-purpose pool as well would avoid the deadlock — but that pool runs amd64 on-demand instances only, and this cluster puts every pool on arm64 (Graviton) and runs its build pool on Spot, so it enables only system and defines its own pools. So:

    • ArgoCD’s controller pods sit Pending.
    • The GitOps pipeline does not run.
    • The workload NodePool manifests that would fix it are waiting on the ArgoCD that cannot start.

    Breaking the dependency takes a tier that runs before the GitOps engine exists:

    Tier 0   NodePools + IngressClass       (helmfile, applied directly)
Tier 1   ArgoCD                          (helmfile)
Tier 2   everything else                 (ArgoCD pull)

    Adopting Tier 0 into ArgoCD later is possible, and it would reintroduce the circle the one time it matters — rebuilding the cluster from scratch.

    The same bottleneck exists one layer down, in Terraform. Enable a managed addon before any workload NodePool exists and its pods have nowhere to land, so terraform apply waits out the addon creation timeout (20 minutes by default) and then fails. The first cluster build therefore takes three steps, in this order:

    1. apply with the addon flags (enable_*_addon) set to false
    2. kubectl apply the workload NodePool manifests by hand
    3. Set the flags to true and apply again

    After that, the NodePools move into Tier 0, managed by helmfile.


    4. Writing NodePools for production

    Three configuration points that came out of building the production environment.

    4.1 Do not name a pool system

    Auto Mode already creates and uses a built-in NodePool named system. Write a manifest with the same name and the two collide.

    Renaming it later — to platform, say — is expensive. A NodePool’s name is its identity, so a rename is handled as deleting the old pool and creating a new one: every node the old pool launched is drained and terminated. That is a different path from the drift a spec change causes, but the result is the same — every node in the pool is replaced.

    4.2 Pick the consolidation policy for the workload

    Karpenter lets each NodePool choose one of three consolidation policies.

    Policy Nodes it consolidates Evicts running pods Fits On this cluster
    WhenEmpty Empty nodes only (nodes left with only pods that carry no disruption cost, such as DaemonSet pods) No Long jobs that are sensitive to interruption; shared cluster components platform and observability (consolidateAfter: 30m), build and game (consolidateAfter: 5m)
    WhenEmptyOrUnderutilized (default) Empty nodes, plus nodes whose pods can be rescheduled elsewhere at lower cost Yes — whenever there is any saving Stateless web and API workloads that tolerate restarts game, at first (consolidateAfter: 5m) — later moved to WhenEmpty
    Balanced (v1.14+) The same candidates as WhenEmptyOrUnderutilized Yes — only when the saving outweighs the disruption cost A middle ground between cost and stability Not used

    That decision is made on pod requests, not on a node’s actual CPU usage. If the requests fit on other nodes, a node that is genuinely busy still becomes a consolidation candidate.

    The default, WhenEmptyOrUnderutilized, works for an ordinary web application and causes trouble for special-purpose workloads. This cluster ended up on WhenEmpty for every pool, with only the wait varying by pool:

    • Platform and observability: WhenEmpty with consolidateAfter: 30m. Nodes that carry shared components such as ArgoCD and monitoring are more stable when they are reclaimed only once they are completely empty, rather than having their pods moved to pack nodes tighter.
    • Build: WhenEmpty. WhenEmptyOrUnderutilized evicts even a running build pod once it judges the pod can be rescheduled onto another node, and the build starts over from scratch.
    • Game: started on WhenEmptyOrUnderutilized with consolidateAfter: 5m. On the old cluster the same setting consolidated 16 times in two hours, so it moved to WhenEmpty.

    There is also Balanced, which consolidates only when the saving outweighs the disruption cost. But that judgement comes from Karpenter’s internal scoring, so for workloads where disruption is expensive, such as builds, WhenEmpty — whose outcome is unambiguous — is the safer choice.

    4.3 medium passes the scheduler and starves the container

    I restricted instance-size from the permissive default to an explicit [large, xlarge], to head off a failure that never announces itself.

    Karpenter packs nodes on requests alone; limits are invisible to it. With a game pod at requests 500m and limits 2000m, a 1-vCPU medium accepts the pod by requests — yet the node is smaller than that one pod’s limit. The moment traffic pushes the pod toward its limit, it is held to the node’s single core and throttled.

    (AWS documents that Auto Mode only creates instances with more than one CPU, so on Auto Mode the 1-vCPU case is excluded by construction. The rule below holds for any node smaller than a pod’s limit.)

    Cluster monitoring shows the pod Running and the node within its requests, while inside the container CPU throttling and latency climb steeply.

    If a pod’s limits are larger than its requests, the instance-size floor must be at least that one pod’s limit. That is a setting for preventing failures, not for saving money.

    Note: a pod with requests < limits is Burstable QoS

    Kubernetes assigns every pod a QoS (Quality of Service) class from its requests and limits. The game pod at requests 500m / limits 2000m is Burstable.

    QoS class Condition CPU Under memory pressure
    Guaranteed Every container’s CPU and memory requests equal its limits Requests always guaranteed; cannot use more Evicted last
    Burstable Requests set and different from limits (or only some set) Only requests guaranteed; up to limits while the node has spare CPU Evicted after BestEffort
    BestEffort No requests or limits No guarantee Evicted first

    The CPU a Burstable pod uses above its requests is not a guarantee; it is spare CPU on the node, borrowed. When several pods on one node burst at once, the spare CPU is shared in proportion to their requests (cgroup cpu.weight). Limits are enforced by the CFS quota, so the moment a pod reaches its limit it is throttled. It does not restart and stays Running, so from the outside it looks healthy.

    That leaves three options for Burstable pods:

    • Switch to Guaranteed (requests = limits): performance becomes predictable, but requests have to be sized for the peak, which raises node count and cost.
    • Stay Burstable and set a node-size floor: this cluster’s choice. A node at least one pod’s limit in size lets at least one pod burst all the way to its limit.
    • Remove CPU limits (requests only): CFS throttling disappears and a pod can use any spare CPU on the node. In exchange, when one pod takes the node’s CPU, the other pods on it cannot use more than their requests — a noisy neighbour. Memory limits stay regardless of this choice.

    Throttling never shows in pod status, so it has to be watched as a metric. This query gives the share of CPU periods that were throttled:

    sum by (namespace, pod) (rate(container_cpu_cfs_throttled_periods_total[5m]))
  /
sum by (namespace, pod) (rate(container_cpu_cfs_periods_total[5m]))

    If it stays above 25%, either the limit is too small for the workload or the node has no room to absorb the burst.


    5. Four failures that reported success, and one false alarm

    These are the areas that eat the most troubleshooting time if you do not know them in advance.

    5.1 The IngressGroup annotation is ignored

    Auto Mode’s built-in load balancer controller does not read alb.ingress.kubernetes.io/group.name. Grouping is applied only through the IngressClassParams.spec.group.name field.

    You can tell which controller you are on from the ALB’s tags:

      Standalone controller Auto Mode built-in controller
    Tag key ingress.k8s.aws/stack ingress.eks.amazonaws.com/stack
    Tag value The group name you set namespace/name of a single Ingress

    Because Auto Mode does not recognise the group name in the annotation, it treats every Ingress as a stack of its own.

    The failure is quiet. While a group holds only one Ingress, nothing surfaces. The moment a second Ingress with the same group settings is deployed, the controller tries to create a separate new ALB — and because every Ingress in the group carries the same load-balancer-name annotation, it hits DuplicateLoadBalancerName:

    • the application pod stays Running
    • ArgoCD reports Synced and Healthy
    • only the Ingress ADDRESS field is empty

    The fix is to declare a dedicated IngressClass and IngressClassParams for each group, one to one. group.order still has to be declared as an annotation, and changing an Ingress’s IngressClass deletes and recreates its ALB, so plan for an endpoint change and a brief outage.

    5.2 The StorageClass provisioner was renamed

    Auto Mode ships EBS CSI under the provisioner name ebs.csi.eks.amazonaws.com. The open-source driver’s ebs.csi.aws.com does not exist in the cluster.

    A StorageClass naming the old provisioner creates successfully — the Kubernetes API accepts it without a warning; nothing checks that a driver by that name exists. Every PVC that uses it then sits Pending forever, and the StorageClass itself shows no error at all.

    Auto Mode also does not create a default StorageClass — the documentation is explicit: “EKS Auto Mode does not create a StorageClass for you.” So even with block storage enabled, nothing is provisioned until you deploy a StorageClass manifest that names the new provisioner.

    5.3 EFS: the PVC says Bound and the pod cannot start

    EFS is not inside Auto Mode’s managed scope, and with statically provisioned volumes the gap stays out of sight.

    A PVC bound to a statically created PV moves to Bound immediately, whether or not the driver is actually running. Only when a pod that mounts the volume is deployed does it stop, in ContainerCreating:

    driver name efs.csi.aws.com not found in the list of registered CSI drivers

    kubectl get pvc shows every volume bound normally, so the failed pod start is found only after the migration has been declared finished.

    5.4 Pods per node drop: 110 with prefix tuning, 27 on Auto Mode

    The old cluster ran aws-node with ENABLE_PREFIX_DELEGATION=true and WARM_PREFIX_TARGET=1, which let even a t4g.medium system node hold up to 110 pods (17 by default).

    Auto Mode uses /28 prefix delegation by default as well. What it does not support is any of the buffer tuning — warm IP, warm prefix and the rest. With no tuning to rely on, the platform appears to assume the worst case of ENI fragmentation, and so it calculates max-pods very conservatively.

    Measured: a c7g.large Auto Mode node allows 27 pods. To keep the density the old cluster packed onto small nodes, choose larger instance types or run more nodes.

    $ kubectl get nodes \
  -o custom-columns=NAME:.metadata.name,TYPE:.metadata.labels.node\\.kubernetes\\.io/instance-type,PODS:.status.allocatable.pods

    5.5 Bottlerocket’s ZRAM swap trips a memory alert on a healthy node

    Unlike the four above, here the system is healthy and the alert fires. Auto Mode nodes run AWS-managed Bottlerocket, which enables 1 GiB of ZRAM swap by default.

    The memory-pressure rule bundled with kube-prometheus-stack (NodeMemoryMajorPagesFaults) was designed on the assumption of disk I/O:

    rate(node_vmstat_pgmajfault[5m]) > 500

    ZRAM is compressed memory: a page fault costs a decompression, not a disk read. In a healthy state with no disk I/O at all, the rule measured 500–8,000 major page faults per second, and the alert fired constantly.

    Replace it with a rule based on PSI (Pressure Stall Information). This cluster turned the default rule off and alerts when memory stall time stays above 0.1 seconds per second for 15 minutes:

    rate(node_pressure_memory_stalled_seconds_total[5m]) > 0.1


    6. Controller metrics you can never collect again

    Under Auto Mode, Karpenter and the ALB controller run in the AWS-managed control plane, not inside your cluster. There is no pod endpoint in the cluster that exposes their metrics.

    I removed the controller alert rules entirely:

    • karpenter-alerts — 3 rules
    • aws-load-balancer-controller-alerts — 2 rules

    A query like absent(karpenter_build_info) can no longer hold. Left in place, the missing metric fires the alert permanently and wears down trust in the alert channel.

    Node provisioning and infrastructure health have to move to CloudWatch metrics and the EKS console. Not running the controllers yourself costs you in-cluster metric visibility, and the operating design has to account for that.


    7. The safety model changes underneath you

    The change I felt most was the cluster’s isolation mechanism.

    The old cluster put system workloads on a managed node group and game and build workloads on Karpenter pools. The system node group was safe without a taint: no autoscaler was attached to it, so it stayed fixed at three nodes. An application pod could stray onto a system node and take its capacity, but the node group itself could never grow.

    Under Auto Mode (Karpenter), every pool scales with demand. An application pod that lands in an untainted platform pool makes that pool provision more nodes for it. The logical split between pools stops meaning anything, and the first symptom is an unexpected bill.

    The fixed group size used to be the safety mechanism. Now taints (who may land here) and NodePool limits (how large it may grow) share that job.

    Every system and platform pool — everything except the workload pool — needs an explicit taint, with tolerations only on the workloads it is meant for, and every pool needs CPU and memory limits. This cluster taints every pool except game and sets limits on all of them (the platform pool, for example, is capped at 16 CPUs).


    8. Pre-migration checklist

    The items to check before starting the actual migration:

    1. Grep every manifest. Change references to ebs.csi.aws.com and ingress.k8s.aws to their Auto Mode names. Leave efs.csi.aws.com as it is, and first check that the EFS CSI addon is installed.
    2. Count your Ingresses per group. If any group has two or more, finish the class-per-group design on IngressClassParams before cutover.
    3. Recompute capacity at conservative pod density. Prefix-delegation tuning is not available, so re-plan node counts with the lower max-pods per node.
    4. Inventory every workload that depends on EFS. The EFS CSI driver is outside the managed scope, so keep a separate addon deployment path for it.
    5. Check the fields in your existing EC2NodeClass. amiFamily, amiSelectorTerms, userData, kubelet and metadataOptions have no counterpart in Auto Mode’s NodeClass (eks.amazonaws.com/v1), so verify your workloads run without them.
    6. Identify the workloads that cannot use Pod Identity. Find any third-party pod that depends on IRSA and decide whether the OIDC provider stays.
    7. Check SwapTotal on a new node, and move the page-fault alert to a PSI-based rule before Bottlerocket’s ZRAM swap makes it fire falsely.
    8. Confirm AWSServiceRoleForEC2Spot exists. It is an account-wide resource and the Spot NodePool (this cluster’s build pool) keeps using it, so make sure it is not deleted while the old stack is being cleaned up.


    9. Wrap-up

    Terraform resources falling from 102 to 17, and the addon- and AMI-tracking scripts no longer being needed, are a substantial improvement for infrastructure operations. Removing the node-roll stage from the cluster upgrade runbook alone cuts a recurring chunk of operational work.

    But “AWS manages compute” does not mean “there is nothing left for an engineer to manage”. NodePool manifests are still a core asset you write, and the consolidation policy, the ratio of your pods’ limits to their requests, and strict taint-based isolation still take careful engineering.

    Above all, four of the five traps found here surface without an error, while every indicator reads normal. A successful migration needs more than a deploy: before you start, plan the checks that prove each component is actually working.
