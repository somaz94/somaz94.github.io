    EKS Compute Modes: Fargate, Managed Node Groups, Karpenter, and Auto Mode

    Auto Mode is not a fifth kind of node — it is Karpenter with the operator changed, and that is what decides whether it fits


    Overview

    When I compared EKS Fargate and EC2 node groups there were two ways to get compute in EKS. Then Karpenter arrived, and running it turned out to be a two-layer job spread across Terraform and Helm. Now there is a fourth, and the way it is usually described — “EKS manages compute for you” — is the least useful sentence anyone could write about it.

    Here is the sentence I would use instead:

    EKS Auto Mode is Karpenter, operated by AWS.

    Not a new scheduler. Not a Fargate successor. The same project, the same NodePool object, the same consolidation behaviour — with the controller, its CRDs and its node class moved out of your cluster and into the AWS-managed control plane. Once you see it that way, every question about it becomes answerable: what you keep writing, what you stop writing, and what you can no longer express at all.

    This post is the map. Next week’s is the drive — I moved a production game workload from a self-managed Karpenter cluster onto an Auto Mode cluster, and wrote down what broke.

    Identifiers below are sanitized; the API surface, the version numbers and the measurements are real.


    1. The four modes at a glance

    The useful axis is not “managed vs unmanaged”. It is who provisions the node, who patches it, and which knobs survive.

      Fargate Managed node group Self-managed Karpenter Auto Mode
    Unit you get a pod a group of nodes a node per pending pod a node per pending pod
    Who provisions AWS, per pod ASG, at the size you declare Karpenter, in your cluster Karpenter, in AWS’s control plane
    Who patches the OS AWS you — pin and bump an AMI you — amiAlias and drift AWS — a new AMI roughly weekly
    Scales up on a pending pod n/a no, not without an autoscaler yes yes
    Node class object — — EC2NodeClass (yours) NodeClass (AWS ships one)
    You choose the AMI no yes yes no
    You set disk / IMDS / kubelet no yes yes no
    DaemonSets no yes yes yes
    Provisioner metrics to scrape n/a n/a yes — it is your pod no — it is not your pod

    Two rows in that table do most of the work.

    “Scales up on a pending pod: no” is the row that pushed me off managed node groups in the first place. A managed node group at min = desired = 0 does not grow when a pod goes Pending; something has to move desired. That is the entire reason Cluster Autoscaler or Karpenter exists, and it is why my build and game tiers stopped being node groups.

    “Provisioner metrics to scrape: no” is the row people discover after they migrate. I will come back to it.


    2. Fargate and managed node groups — the short version

    I am not re-deriving these; the earlier post covers both in depth. What matters for placing Auto Mode next to them:

    Fargate gives you a pod and no node. That is its strength and its whole limitation surface at once — no DaemonSets, no privileged containers, no node-level tuning, no GPU, and a per-pod billing model that stops being cheap the moment utilisation is decent. It is a good answer for spiky, isolated, low-density work. It is not an answer for a cluster that runs a logging agent.

    Managed node groups give you an ASG with EKS bookkeeping on top: an AMI you choose, a size you declare, a rolling update you trigger. Everything is expressible, which is the point — and everything is yours to maintain, which is the cost.

    Auto Mode is not positioned against Fargate at all. It is positioned against the node group, and against the Karpenter setup that most people bolted onto their node groups to make them elastic.


    3. Self-managed Karpenter — the two layers Auto Mode absorbs

    This is the baseline worth understanding precisely, because Auto Mode is defined by what it removes from it.

    Running Karpenter yourself is two layers in two repositories:

    Layer 1 — AWS infrastructure, in Terraform. A controller IAM role with a Pod Identity association, a node IAM role plus its instance profile, an EKS access entry for that role, an SQS queue for Spot interruption notices, the EventBridge rules and targets that feed it, and discovery tags on your subnets and security groups.

    Layer 2 — in-cluster, in Helm. The controller chart itself, its CRDs, and your EC2NodeClass and NodePool objects.

    Neither layer is difficult. Both are fiddly in ways that only show up once:

    • The rendered controller policy can exceed the 6,144-character managed-policy limit, so it has to go inline.
    • AWSServiceRoleForEC2Spot must exist in the account or Spot launches fail with AuthFailure.ServiceLinkedRoleCreationNotPermitted.
    • The CRDs cannot be a plain Helm release — helmfile diff fails with “no matches for kind EC2NodeClass” before the controller is ever installed, so they need a prepare hook that applies them server-side first.

    That is the layer Auto Mode takes. All of it.


    4. What Auto Mode actually is

    4.1 It is four flags on the cluster

    Auto Mode is not a cluster type. It is a set of fields on aws_eks_cluster:

    resource "aws_eks_cluster" "main" {
  # ...

  compute_config {
    enabled       = true
    node_pools    = ["system"]
    node_role_arn = aws_iam_role.node.arn
  }

  kubernetes_network_config {
    elastic_load_balancing {
      enabled = true
    }
  }

  storage_config {
    block_storage {
      enabled = true
    }
  }

  bootstrap_self_managed_addons = false
}

    Read them one at a time, because each one deletes a different piece of your stack:

    • compute_config — AWS runs Karpenter. The controller, the CRDs and a NodeClass named default become part of the cluster.
    • elastic_load_balancing — AWS runs the AWS Load Balancer Controller. You stop installing it.
    • block_storage — AWS runs the EBS CSI driver. You stop installing it, and its IAM role goes with it.
    • bootstrap_self_managed_addons = false — the cluster comes up without the self-managed kube-proxy / coredns / vpc-cni bootstrap, because Auto Mode supplies all three.

    4.2 The IAM surface is a different set of policies

    This is the quickest way to confirm you are actually in Auto Mode, and the quickest way to get a cluster that half-works if you copy the old set:

    cluster_policies = [
  "AmazonEKSClusterPolicy",
  "AmazonEKSComputePolicy",          # provisions nodes
  "AmazonEKSBlockStoragePolicyV2",   # manages EBS volumes
  "AmazonEKSLoadBalancingPolicy",    # manages ALBs/NLBs
  "AmazonEKSNetworkingPolicy",       # manages ENIs
]

node_policies = [
  "AmazonEKSWorkerNodeMinimalPolicy",     # not AmazonEKSWorkerNodePolicy
  "AmazonEC2ContainerRegistryPullOnly",   # not ...ReadOnly
  "CloudWatchAgentServerPolicy",
]

    The node role is deliberately smaller than the classic one. AmazonEKSWorkerNodeMinimalPolicy and AmazonEC2ContainerRegistryPullOnly exist because an Auto Mode node does less: the CNI and the CSI driver are no longer processes on the node authenticating with the node’s identity.

    4.3 node_pools is a choice, and [] is a real option

    compute_config.node_pools accepts two built-in pools:

    • general-purpose — an untainted pool that will happily run your application pods, on amd64 on-demand capacity only.
    • system — tainted CriticalAddonsOnly, labelled app.kubernetes.io/managed-by=eks, intended for cluster components.

    I enable only system. Every workload pool is a NodePool object I write myself. That is a deliberate choice and the reasoning is in Part 2, but the short form is: general-purpose is a sensible default for a cluster you are not going to think about, and a loss of control for one you are — it cannot give you Graviton or spot, which is why every pool here is one I wrote.

    The consequence to notice now: with only system enabled, a fresh cluster has no untainted capacity at all. Nothing you deploy will schedule until you apply a NodePool of your own. Auto Mode does not mean nodes appear on their own.

    node_pools = [] is also legal and goes one step further — with no built-in pool at all, the default NodeClass is not provisioned either, so you write your own NodeClass, create an EC2-type access entry for its node role, and then write your pools. That is the fully-custom end of the spectrum; enabling system alone is the middle of it.


    5. The API surface changes — manifests do not port

    This is where “Auto Mode is Karpenter” stops being a simplification and starts being a trap. It is the same project, so most of your manifest looks portable. It is not.

    5.1 NodePool survives, EC2NodeClass does not

      Self-managed Auto Mode
    Node pool karpenter.sh/v1 NodePool same
    Node class karpenter.k8s.aws/v1 EC2NodeClass — you write it eks.amazonaws.com/v1 NodeClass — AWS ships default
    Claim karpenter.sh/v1 NodeClaim same, but the CRD is the cluster’s

    So the reference inside your NodePool changes group:

    # self-managed
nodeClassRef:
  group: karpenter.k8s.aws
  kind: EC2NodeClass
  name: game

# Auto Mode
nodeClassRef:
  group: eks.amazonaws.com
  kind: NodeClass
  name: default

    5.2 The requirement keys are not the same keys

    This is the one that actually broke my manifests, and it is a boring reason with a wide blast radius: the prefix changes on every key. Karpenter’s AWS provider labels are karpenter.k8s.aws/*. Auto Mode’s are eks.amazonaws.com/*.

    Axis Self-managed Auto Mode
    Instance family karpenter.k8s.aws/instance-family eks.amazonaws.com/instance-family
    Category karpenter.k8s.aws/instance-category eks.amazonaws.com/instance-category
    Generation karpenter.k8s.aws/instance-generation eks.amazonaws.com/instance-generation
    Size karpenter.k8s.aws/instance-size eks.amazonaws.com/instance-size
    CPU count karpenter.k8s.aws/instance-cpu eks.amazonaws.com/instance-cpu
    Capacity type karpenter.sh/capacity-type same
    Architecture kubernetes.io/arch same

    The vocabulary survives. My build pool pins nine families by name to maximise the number of independent Spot capacity pools — more pools means a lower aggregate interruption rate, which means fewer in-flight builds get reclaimed — and that requirement ports across with one string changed:

    # self-managed
- key: karpenter.k8s.aws/instance-family
  operator: In
  values: ["c8g","c7g","c6g","m8g","m7g","m6g","r8g","r7g","r6g"]

# Auto Mode — same list, same operator, different prefix
- key: eks.amazonaws.com/instance-family
  operator: In
  values: ["c8g","c7g","c6g","m8g","m7g","m6g","r8g","r7g","r6g"]

    Two keys carry over unchanged because they are not AWS-provider labels at all: karpenter.sh/capacity-type belongs to Karpenter core, and kubernetes.io/arch is upstream Kubernetes. Everything else needs rewriting, which is mechanical — and mechanical is exactly the kind of change that looks like it worked when you have only edited some of them.

    5.3 The instance catalogue is an allowlist with a floor

    Auto Mode does not launch anything you ask for. It launches from a published set of supported instance types — C, M, R, T, Z/X, I/D, accelerated and HPC families — and applies two minimums on top:

    • more than 1 CPU
    • size is not nano, micro or small

    So burstable is fine (t4g, t3, t3a, t2 are all supported) and medium is fine where the type has 2 vCPUs, but a 1-vCPU medium such as m7g.medium will never be provisioned no matter what your requirements say.

    This matters less for what it excludes than for how it excludes it: a NodePool whose requirements resolve only to unsupported types does not error — it simply never launches a node, and your pods stay Pending while the pool looks healthy.

    5.4 The NodeClass is not small — but four specific things are gone

    It is tempting to describe the Auto Mode NodeClass as a stripped-down EC2NodeClass. It is not: it carries role (or instanceProfile), subnet and security-group selectors, separate pod subnet and security-group selectors, capacity-reservation selectors, snatPolicy, networkPolicy and its event logs, ephemeralStorage (size, iops, throughput, kmsKeyID), advancedNetworking (proxy settings, ipv4PrefixSize, static ENIs for EFA), advancedSecurity.fips, certificateBundles, placementGroupSelector, tags, and hugepage configuration. Several of those have no EC2NodeClass equivalent at all.

    Disk size is available — ephemeralStorage.size accepts 1–59000Gi — which is the one I got wrong on my first read and would have planned around unnecessarily.

    What is genuinely absent is narrower and more specific:

    • No AMI selection. AWS determines the image, and ships a new one roughly weekly.
    • No user data. Anything you did with cloudinit_pre_nodeadm or a bootstrap script has no hook.
    • No kubelet configuration. No maxPods override, no eviction thresholds, no reserved resources.
    • No IMDS tuning. IMDSv2 is enforced with a hop limit of 1 and the documentation states plainly that this cannot be modified. A pod that genuinely needs IMDS has to run with hostNetwork: true.

    That is a much shorter list than “you lose control of the node”, and it is the list that actually decides whether a workload can move.


    6. What changes name, and what is simply absent

    Auto Mode does not just add things. It renames the identity of components you already depend on, and it omits two you may assume are included.

    Renamed — same function, different string:

      Self-managed Auto Mode
    EBS CSI provisioner ebs.csi.aws.com ebs.csi.eks.amazonaws.com
    IngressClass controller ingress.k8s.aws/alb eks.amazonaws.com/alb
    ALB stack tag ingress.k8s.aws/stack ingress.eks.amazonaws.com/stack

    Each of those is a string in a manifest somewhere in your repo. A StorageClass naming the old provisioner will create successfully and then leave every PVC Pending forever, with no error on the StorageClass itself.

    Absent:

    • EFS. storage_config carries blockStorage and has no file-storage counterpart. The EFS CSI driver is still yours to install, even if every EFS volume you use is a statically defined PersistentVolume.
    • VPC CNI tuning. Prefix delegation itself is not missing — Auto Mode uses /28 prefixes by default, and advancedNetworking.ipv4PrefixSize can switch it to secondary IPs. What is missing is everything you used to tune around it: warm IP, warm prefix and warm ENI targets, minimum IP targets, and the rest of the open-source VPC CNI’s configuration surface are all explicitly unsupported. Auto Mode also computes max-pods conservatively, assuming worst-case prefix fragmentation, and caps it at 110. On a c7g.large that arithmetic gave me 27 pods where the tuned old cluster ran 110 — same feature, different sizing.
    • Controller metrics. Karpenter and the load balancer controller run in the AWS-managed control plane. There is no pod to scrape. Any alert built on karpenter_build_info or the controller’s own series is not “not yet configured” — it is permanently unsatisfiable, and node-provisioning health has to move to CloudWatch.


    7. What it costs

    Two line items, and only one of them is new.

    The control plane is unchanged — $0.10 per cluster-hour whether Auto Mode is on or off. It is not a differentiator and I will not mention it again.

    The management fee is. Auto Mode bills on top of the EC2 instance price, and AWS publishes two worked examples:

    Instance EC2 Auto Mode fee Total
    m5a.xlarge $0.1720/hr $0.02064/hr $0.19264/hr
    c6a.2xlarge $0.3060/hr $0.03672/hr $0.34272/hr

    Both come to exactly 12%, and that is where most write-ups stop. It is also where the number stops being true.

    The fee is an amount, not a percentage

    While you can leverage the full range of Amazon EC2 instance purchase options with EKS Auto Mode, including On Demand, one- and three-year Reserved Instances, Compute Savings Plans, and Spot Instances, the EKS Auto Mode charges are independent of the EC2 instance purchase option.

    Read that twice, because it inverts the headline. The fee is a fixed rate per instance-hour, set by instance type. Spot, Reserved, Savings Plan — you pay the same absolute amount. So 12% is not the surcharge; 12% is the surcharge only if you pay list price. Discount the instance and the fee does not move, which means its share of what you actually pay goes up.

    Here is a c7g.large in Seoul, using this site’s own cloud pricing figures for the discounts. AWS sets the fee per instance type and publishes a rate for each; I do not have a quoted rate for this one, so it is modelled at the same 12%-of-list ratio the two examples above share — check yours rather than inheriting my assumption:

    How you buy it You pay for the instance Auto Mode fee Fee as a share of the instance price
    On-Demand list $0.0816/hr $0.0098/hr 12.0%
    1-year RI, All Upfront $0.0503/hr $0.0098/hr 19.5%
    3-year RI, All Upfront $0.0323/hr $0.0098/hr 30.3%
    Spot (62% off, measured) $0.0310/hr $0.0098/hr 31.6%

    The general form is 12% / (1 − discount). At an 80% Spot discount it is 60%. At 90% the fee costs more than the instance.

    So the people who have worked hardest on their compute bill are the ones who pay the most for Auto Mode, proportionally. If you are already on Spot and Savings Plans, budget for something nearer a third than a tenth.

    And it multiplies by node count

    The fee is per instance-hour, so anything that makes you run more instances scales it. That is where the density arithmetic from the previous section lands: on a c7g.large, Auto Mode’s defensive max-pods calculation gave me 27 pods where a tuned cluster ran 110. If pod slots are what you run out of first — and on one of my tiers they were, at 96% of slots against 5% CPU — a fleet sized on tuned density needs more nodes here, and each extra node carries the fee too. The two compound; they do not add, and neither is visible in a feature comparison.

    The counterweight, deliberately unpriced

    Auto Mode deleted 85 Terraform state addresses, five pinned addon versions, two bespoke drift-detection scripts and an entire stage of an upgrade runbook — figures from the migration, which is Part 2. That is labour, it was being paid every upgrade cycle, and whether the fee is cheaper than it depends on what your engineering time is worth and how often you upgrade.

    The trade is legible: a known rate on compute against an unknown number of engineer-hours. Which side wins is specific to you, and anyone who quotes you a number for it is guessing. What I would not do is take the 12% at face value — price it against what you actually pay per instance, and at your real pods-per-node.


    8. Choosing

    Reduced to the questions that actually decide it:

    Fargate — when you want no node at all, run few pods, and none of them need a DaemonSet, a privileged container or a GPU. Isolation per pod is worth real money to you.

    Managed node groups — when the fleet is stable, you need specific AMIs or node-level configuration, and you would rather roll nodes on a schedule you choose than have a controller choose for you. Also the correct answer for a tier that must be a fixed size: a group that cannot grow is a blast-radius control, and that property is not free to reproduce elsewhere.

    Self-managed Karpenter — when you need one of the four things Auto Mode cannot express: a specific AMI, user data, kubelet configuration, or an IMDS hop limit above 1. Also when you need an instance type outside Auto Mode’s supported set, when you want VPC CNI warm-pool tuning rather than Auto Mode’s defensive max-pods calculation, or when you want to pin the Karpenter version rather than take AWS’s — and when you need to scrape the provisioner’s own metrics.

    Auto Mode — when nothing you need lives in an AMI, a user-data script or a kubelet flag, and you want the two-layer Karpenter plumbing to stop being yours. The surface it refuses is narrower than the marketing-shaped fear suggests: disk size, tags, placement groups, capacity reservations, pod-level subnets and security groups all have a home in the NodeClass.

    A useful test before committing: grep your EC2NodeClass for amiFamily, amiSelectorTerms, userData, kubelet and metadataOptions. Those five are the ones with nowhere to go. Everything else you find is either supported under a different name or genuinely unnecessary — and the fastest way to scope a migration is to find out which of your fields are in that first group.


    9. Wrap-up

    Auto Mode is a smaller thing than the marketing implies and a bigger change than the diff suggests. It does not invent a scheduler; it takes over the operation of one you may already be running. What you write shrinks to NodePool objects. What you can express shrinks with it.

    The mode map is the easy half. The half that costs time is the migration — where identical-looking manifests bind to different API groups, where a renamed provisioner produces no error at all, and where four separate components report Healthy while a load balancer never gets created. That is Part 2, next week.
