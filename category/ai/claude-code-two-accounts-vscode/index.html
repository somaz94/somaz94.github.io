    Running Two Claude Code Accounts Side by Side in VS Code

    A work account and a personal account in two VS Code windows at once, each logged in separately, sharing the same settings, extensions and agents


    Overview

    I use Claude Code with two accounts: one for work and one for personal projects. I wanted both open at the same time, each VS Code window logged into its own account, while sharing my editor settings, extensions and Claude Code sub-agents.

    Claude Code covers the account side with a single environment variable. The hard part is VS Code. My first alias looked right and silently used the wrong account. This post walks through the setup I ended up with, the trap I hit, and how to verify that the two accounts really are separate.

    1. How Claude Code Separates Accounts

    Claude Code keeps everything it knows about you in one configuration directory, ~/.claude by default. Point the CLAUDE_CONFIG_DIR environment variable at a different directory and Claude Code stores its settings, session history, projects and plugins there instead. The account record (.claude.json, which holds oauthAccount) moves into that directory too.

    The login token follows the same rule. On macOS, Claude Code stores credentials in the login Keychain, and the official docs state that when CLAUDE_CONFIG_DIR is set, the Keychain entry is keyed to that directory, “so a session with a different CLAUDE_CONFIG_DIR reads a different entry.”

    So two directories mean two independent logins:

    Directory Account record Keychain entry
    ~/.claude (default) ~/.claude.json Claude Code-credentials
    ~/.claude-personal ~/.claude-personal/.claude.json Claude Code-credentials-<hash>


    2. The Aliases

    The work account uses the defaults, so it is plain code . and claude. The personal account gets two aliases in ~/.bash_profile (they work the same in ~/.zshrc):

    alias claude-personal="CLAUDE_CONFIG_DIR=~/.claude-personal command claude"
# Separate user-data-dir forces its own VS Code process, so it runs alongside the work window.
alias codepersonal='CLAUDE_CONFIG_DIR=~/.claude-personal code --user-data-dir ~/.vscode-personal .'
    • claude-personal is the terminal CLI on the personal account. command claude skips any shell function or alias called claude.
    • codepersonal opens the current folder in a VS Code instance whose Claude Code extension uses the personal account.

    The --user-data-dir flag is the part that matters, and it was missing from my first version.


    3. The Trap: VS Code Is Single-Instance

    My first alias was:

    alias codepersonal='CLAUDE_CONFIG_DIR=~/.claude-personal code .'

    It worked only when VS Code was fully quit. With a work window already open, the “personal” window came up on the work account.

    The reason is how the code command behaves. When a VS Code process is already running, code . does not start a new one. It asks the running process to open another window, and that window inherits the environment of the process that was started first. The CLAUDE_CONFIG_DIR I passed on the command line went to a short-lived launcher and never reached the extension. If I launched the personal window first, the effect flipped and every later code . window used the personal account.

    Why VS Code profiles do not solve this
    • Profiles switch settings and extensions, but every profile runs inside the same VS Code process.
    • The same process means the same environment, so CLAUDE_CONFIG_DIR cannot differ between profiles.

    --user-data-dir fixes it. A different user data directory makes VS Code start a separate main process, and that process inherits the environment of the shell that launched it.

    You can confirm the variable reached the right process. Find the personal instance’s main process, then print its environment:

    ps -Ao pid,command | grep -- '--user-data-dir' | grep -v grep
ps eww -o command= -p <pid> | tr ' ' '\n' | grep CLAUDE_CONFIG_DIR
# CLAUDE_CONFIG_DIR=/Users/<you>/.claude-personal


    4. First Launch: The Sign-In Screen Is Not Claude

    The first codepersonal run shows “Welcome to VS Code — Sign in to use GitHub Copilot” with GitHub, Google, Apple and GHE buttons.

    This is not the Claude login. It is the GitHub or Microsoft account VS Code uses for Copilot and Settings Sync. It shows up because a new user data directory looks like a fresh install. Unless you want Copilot in this window, choose Continue without Signing In. Whatever you pick here has no effect on which Claude account the window uses.


    5. Bringing Your Existing Settings Over

    A new user data directory starts empty. Here is what you need to bring over and what you can leave alone.


    Extensions: nothing to do

    --user-data-dir does not move the extensions directory. Both instances still load from ~/.vscode/extensions, so the Claude Code extension and everything else is already installed. Only --extensions-dir would separate them.


    Editor settings: symlink, do not copy

    VS Code keeps user settings in ~/Library/Application Support/Code/User/ on macOS. Symlinking the files means a change made in either window applies to both, so the two instances never drift:

    SRC="$HOME/Library/Application Support/Code/User"
DST="$HOME/.vscode-personal/User"

mv "$DST/settings.json" "$DST/settings.json.bak"
rmdir "$DST/snippets"
ln -s "$SRC/settings.json"    "$DST/settings.json"
ln -s "$SRC/keybindings.json" "$DST/keybindings.json"
ln -s "$SRC/snippets"         "$DST/snippets"

    Run this after the personal instance has started once, so that $DST exists. Then run Developer: Reload Window from the Command Palette and the window picks up your theme and settings.

    Leave globalStorage/ alone. It holds extension state and the GitHub sign-in sessions, so linking it would carry the work instance’s login state over and undo the separation you just set up. The cost is that sidebar layout and the recent-folders list start fresh in the personal window.


    Claude Code side: share agents, keep logins apart

    The same idea works inside the Claude configuration directory. Link the parts you want both accounts to share, and keep everything else separate:

    cd ~/.claude-personal
for f in agents commands skills settings.json CLAUDE.md; do
  [ -e "$f" ] && [ ! -L "$f" ] && mv "$f" "$f.bak"
  ln -s ~/.claude/"$f" "$f"
done

    Sub-agents, slash commands, skills, global instructions and settings are now the same on both accounts. Login, history, sessions and projects stay per account, because they live in files and directories that are not linked.


    6. Log In and Verify

    Before the personal login, the Keychain holds a single Claude entry:

    security dump-keychain | grep '"svce"' | grep -i claude
#     "svce"<blob>="Claude Code-credentials"

    That is expected. That entry belongs to the work account, and no Claude process has started from the personal window yet. Open the Claude Code panel in the personal window and log in with the personal account. Then run the same command again:

    security dump-keychain | grep '"svce"' | grep -i claude
#     "svce"<blob>="Claude Code-credentials"
#     "svce"<blob>="Claude Code-credentials-<hash>"

    Two entries mean two separate tokens. If there were still only one, the personal login would have overwritten the work token, and the work window would now be on the wrong account.

    To see which account each directory belongs to:

    python3 -c '
import json, os
for p in ["~/.claude.json", "~/.claude-personal/.claude.json"]:
    a = json.load(open(os.path.expanduser(p))).get("oauthAccount") or {}
    print(p, "->", a.get("emailAddress"))
'
# ~/.claude.json -> work@example.com
# ~/.claude-personal/.claude.json -> personal@example.com


    7. The Result

    Window Config directory Keychain entry Account
    code . ~/.claude Claude Code-credentials work
    codepersonal ~/.claude-personal Claude Code-credentials-<hash> personal

    Both windows can be open at the same time. What they share and what they keep apart:

    • Shared: VS Code extensions, settings.json, keybindings and snippets; Claude Code agents, commands, skills, CLAUDE.md and settings.json.
    • Separate: the Claude login, conversation history, sessions and projects; VS Code UI state and globalStorage.


    8. Removing an Old Config Directory

    I also had an unused config directory from an earlier attempt. After deleting it, I checked three places so nothing still pointed at it:

    ls -d ~/.claude-old                      # should be gone
grep -n "claude-old" ~/.bash_profile ~/.zshrc ~/.claude.json \
  "$HOME/Library/Application Support/Code/User/settings.json"
security dump-keychain | grep '"svce"' | grep -i claude

    The directory is gone, no shell file or settings file references it, and the Keychain lists only the entries for the directories still in use.


    Wrap-up

    The account side takes one environment variable: CLAUDE_CONFIG_DIR gives each directory its own settings, history and Keychain entry. Getting the variable into VS Code is the part that breaks quietly. Because VS Code runs as a single instance, a new window inherits the environment of the first process, so the variable has to come with --user-data-dir to get a separate process.

    With symlinks for the files you want shared, the two windows look and behave the same and differ only in the account they log into. Check the Keychain once after logging in: two entries mean the setup worked.
