    Testing Failure Hypotheses with Chaos Mesh on a Local kind Cluster

    Hypotheses, verified injection, and recovery with PodChaos, NetworkChaos and StatusCheck, measured on a laptop kind cluster


    Overview

    The single point of failure post argued that servers sharing a dependency stop together, however many of them you run. That judgment came from reading an architecture diagram. Whether they really stop together, and whether a fallback response really holds up, only shows once a failure is injected. This post turns those claims into hypotheses and tests them with Chaos Mesh’s PodChaos and NetworkChaos.

    Installation gets only the values that affected the results; the focus is the measurements for each hypothesis. The first thing to look at is a case where Chaos Mesh reported a successful injection and real traffic felt nothing. After that come the difference between pod-kill and a process crash, the conditions under which readiness design grows a partial failure into a total one, the point where latency turns into failure, and the safeguards that stop an experiment safely.


    How to read the numbers

    Every figure was measured on a local kind cluster on one laptop (Chaos Mesh 2.8.7, Kubernetes 1.35). There is no real network latency and no availability zone here, so the numbers show relative differences between configurations, not production values. Unlike the earlier posts in this series, this one has no real operating case. The number of runs is given in each table or the sentence before it, and an experiment run only once is marked as such.


    Hypotheses and Test Setup


    Steady-State Metrics

    Principles of Chaos Engineering lays out the order of an experiment: define the system’s normal behavior as a measurable output (the steady state), hypothesize that this state will hold, introduce variables that reflect real-world events, and try to disprove the hypothesis by looking for a difference from the steady state.

    The heart of it is turning “we have redundancy, so we are fine” into a sentence that can be disproved. “There are three frontends, so it is safe” cannot be tested. “With frontend and backend cut off for 30 seconds, 30 requests per second keep getting responses” can.

    The steady-state metrics here are ok%, the share of normal responses, and served%, which adds fallback responses to the normal ones. Why the two are split becomes clear later. The baseline of every experiment was 100% success and a p50 of about 6ms. The exceptions are the baselines of two runs (C1 run 4, B4 run 3), each with 3 timeouts whose cause was not established.


    Test Target and Load

    Item Setup
    Cluster kind v0.31.0, Kubernetes v1.35.0, containerd 2.2.0, kube-proxy in iptables mode, 1 control-plane and 2 workers
    Application 3 frontend replicas (spread over 2 workers) call backend through a ClusterIP Service; backend has 1 replica unless noted
    Load An in-cluster load generator (probe) sends a steady 30 requests per second (open-loop), a new connection per request, client timeout 5 seconds
    Measurement window 15 seconds of baseline, 30 seconds of fault, 25 seconds after it ends
    Result labels TO is a client timeout, ERR is a connection error


    The demo app is built on the Python standard library. Each backend call opens a new TCP connection, and a 4-slot pool per replica limits concurrent calls. Environment variables set the call timeout (TIMEOUT), whether readiness checks as far as backend (DEEP_READY), and whether a failure returns a fallback response (FALLBACK). This is the code that directly affected the experiments.

    if self.path == "/ready":
    if DEEP:
        try:
            call(1)
        except Exception:
            return self.reply(503, b"backend down")
    return self.reply(200, b"ready")
with POOL:
    try:
        return self.reply(200, call(TIMEOUT))
    except Exception:
        if FALLBACK:
            return self.reply(200, b'{"degraded":true}')
        return self.reply(503, b"backend error")

    The readiness probe has a 2-second period and a failure threshold of 2, and terminationGracePeriodSeconds is 5.

    Preparation turned up one more result. With a spread constraint of maxSkew: 1 and DoNotSchedule on the 3 frontend replicas, the third pod stayed Pending with “didn’t match pod topology spread constraints”. The tainted control-plane was being counted as a topology domain with 0 pods, because nodeTaintsPolicy behaves as Ignore when it has no value. Setting nodeTaintsPolicy: Honor fixed it.

    When Reported Injection and Real Effect Differ

    Hypothesis

    If the status is AllInjected=True and the events show Applied, the fault is in.


    The first hypothesis is about the experiment tool, not the application. If it is wrong, none of the other results can be trusted.


    Service Traffic That direction: to Missed

    A 300ms delay went onto the traffic from frontend to backend.

    apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: exp
  namespace: shop
spec:
  action: delay
  mode: all
  duration: 30s
  direction: to
  selector:
    namespaces: [shop]
    labelSelectors: {app: frontend}
  target:
    mode: all
    selector:
      namespaces: [shop]
      labelSelectors: {app: backend}
  delay:
    latency: 300ms
    correlation: "0"
    jitter: 0ms

    The status was AllInjected=True and the events showed Applied. Direct calls from inside a frontend pod measured something else.


    direction Called through the Service ClusterIP Called directly at the backend Pod IP
    to 0-8ms (no delay) About 605ms
    from About 605ms About 605ms
    both About 605ms About 1205ms
    3 to 4 calls per direction and destination, with a new connection per call.


    One run of the same config under 30 requests per second (D4) gave 900 successes out of 900 and a p50 of 6ms, indistinguishable from no fault at all. Keeping the delay at 300ms and switching to direction: from (D2, 3 runs) brought the success rate to 40.75-47.16%. Without checking the injection, the record would have read “no impact from a 300ms delay”, which is the wrong conclusion.

    Inside the frontend pod’s network namespace, the tc netem delay rule is clearly present, and the ipset its filter uses holds only the backend Pod IP. In kube-proxy iptables mode, Service traffic is translated by rules on the node, so the packet reaches that filter still addressed to the ClusterIP and does not match it.


    flowchart LR subgraph Pod["frontend pod network namespace"] P["Packet to backend
    destination: ClusterIP"] T["tc filter
    ipset: backend Pod IP only"] end N["Rules on the node
    DNAT to the backend Pod IP"] B["backend pod"] P --> T T -->|"no match, no delay"| N N --> B

    Service traffic under a direction: to delay, in kube-proxy iptables mode.


    Chaos Mesh 2.8.7’s tc implementation puts the rule on the source pod for to and on the target pod for from. from working on Service traffic is read as a result of the responses backend sends: inside the pod, those are packets between real Pod IPs.


    Where this explanation applies

    It combines values measured in kube-proxy iptables mode with code reading and reasoning, and it is not a claim about every CNI. Setups that replace kube-proxy with eBPF translate Service addresses in a different way, so the results may differ there, but that was not tested here.


    One more thing to watch. The field table in the official docs and the 2.8.7 CRD both define the default of direction as to. Leaving the field out was not tested separately, but going by the default it is the same setting as the direction: to above. That is why the delay experiments D1 to D3 in this post all use direction: from.

    The table shows 300ms as about 600ms because each call opens a new connection. That makes two round trips (connection setup, then request and response), and the injected delay lands on both. HTTP keep-alive was not tested. For a client that reuses connections, this doubling does not carry over as it stands.


    partition Did Cut the Same Traffic

    This result must not be generalized to all of NetworkChaos. In an experiment that cut the same Service traffic with action: partition and direction: to (C5, 1 run), 872 of 894 requests got a 503. The injection worked as it should.

    The partition implementation shows that for to it puts a rule on the source pod’s Output and also on the target pod’s Input. A packet arriving at the target pod has the real frontend Pod IP as its source, so that appears to be where it was caught. No other tc-family action besides delay was tested, so what this covers is delay and partition only.


    mode: one Picked a Terminating Pod

    The second case of an experiment appearing to pass came from pod-kill. mode: one picked a pod that a rollout had put into Terminating 6 seconds earlier. The status was Applied, while the pod actually receiving traffic stayed the same for the whole observation.

    This happened in a script measuring a timeline, not in a measured run. In every pod-kill run in the result tables, the new pod was confirmed to be 8 seconds old at the 8-second mark. If an experiment starts right after a rollout, look first for Terminating pods still around.


    Experiments Stopped by the Namespace Filter

    With enableFilterNamespace=true, injection happens only in namespaces carrying the annotation. A pod-kill in a namespace without it leaves Selected=False and “Failed to select targets: no pod is selected”, and the pod stays as it was. In a namespace with the annotation, the pod was deleted. The shop namespace in this lab got its annotation from a manifest; with the command from the docs it looks like this.

    kubectl annotate ns shop chaos-mesh.org/inject=enabled

    This filter is a guard against accidents, so it is better left on. The chart default is false, though, and with it on an experiment can have no effect and raise no error, so check the Selected condition too.


    Checking the Effect Before the Experiment

    With the direction: to delay and with mode: one, Chaos Mesh’s status alone could not tell whether the injection had any effect. With the namespace filter the status does say so through Selected=False, but you miss it if you do not look at that condition. AllInjected is a condition saying injection finished on the target pods, not a guarantee that traffic is affected. Checking an injection can follow this order.

    1. Inject first without load, and check Selected and AllInjected with kubectl -n shop describe networkchaos exp.
    2. From inside the source pod, call along the same path as real users (the Service name) and see whether delay or failure shows up.
    3. For pod-kill, check that a new pod appeared and that the deleted pod was one receiving traffic.
    4. Apply load only with a setup whose effect is confirmed, and test the hypothesis.

    Since the demo image has Python, the call times in step 2 were measured in the way shown below. The actual measuring script has an extra try statement to record exceptions too; the code below raises an exception and stops if the connection is cut. Values are in milliseconds.

    kubectl -n shop exec <frontend-pod> -- python -c "
import time, urllib.request as u
for _ in range(3):
    t = time.time()
    u.urlopen('http://backend:8080/', timeout=3).read()
    print(round((time.time() - t) * 1000))
"


    The Difference Between pod-kill and a Process Crash

    Hypothesis

    A service that passes pod-kill is safe when its process exits suddenly.


    The API Object Goes First

    PodChaos’s gracePeriod defaults to 0, and the 2.8.7 CRD describes that as “delete immediately”. According to the forced termination section of the Kubernetes docs, a grace period of 0 removes the pod from the API server at once, and on the node the process is force killed after a short grace period. Measured, the order looks like this.


    App behavior API object deleted Old container ends New pod Ready Result
    Ignores SIGTERM +0.1s +2.5s +1.9s About 0.6s of overlap
    Exits on SIGTERM +0.1s By +0.7s +1.8s About 1.1s of gap
    One recorded run of pod-kill on a single backend replica, sampled about every 0.6 seconds.


    With Python as PID 1 and no signal handler, SIGTERM is ignored. In that case the container of a pod already gone from the API kept running for about another 2.5 seconds. The overlap and gap in the table, however, compare the times of the container and the new pod. In the same record, both cases had no Ready address in the EndpointSlice from +0.1s until the new pod became Ready, so the overlap does not mean a window that could take traffic.

    pod-kill removes the API object first. A real crash runs in the opposite order: the process ends first and the pod object stays. A specified gracePeriod was not tested.


    Injecting into Three frontend Replicas

    All three experiments ran 3 times. They have no duration, so the counts cover about 55 seconds from injection to the end of measurement rather than a 30-second fault window, which comes to about 1665 requests per run.


    Experiment Setup Failures (3 runs)
    A pod-kill, app ignores SIGTERM 0, 0, 0
    A3 pod-kill, app exits on SIGTERM 0, 0, 1
    A2 container-kill 8, 4, 4 (all ERR, within 0.4-0.7 seconds)


    The counts are small, but the tendency differs. Passing pod-kill alone does not let you say a process crash is safe too. With container-kill the process ends first while the pod is still in the endpoints, which is how the connection errors are read here.


    Split Failure Counts from backend pod-kill

    With backend as the target, the result depends on the replica count and how the app exits. All of these ran 3 times, the counting window is the same roughly 55 seconds as above, and the failures are what the probe got when calling frontend.


    Experiment Setup Failures (3 runs)
    B1 pod-kill, 1 replica, ignores SIGTERM 0, 18, 18 (503, within 1 second)
    B4 pod-kill, 1 replica, exits on SIGTERM 19, 17, 15
    B2 pod-kill, 2 replicas, ignores SIGTERM 0, 0, 0
    B5 pod-kill, 2 replicas, exits on SIGTERM 0, 0, 6


    The same B1 manifest gave 0 failures once and 18 twice. Had it run once and shown 0, the note would have said a single replica is safe. This data does not establish why the runs split.

    B1 looking better than B4 is no reason to recommend ignoring SIGTERM. The 0 in run 1 is a value of unknown cause, and graceful shutdown itself is something to design together with the preStop hook covered in the Pod termination post.

    The table also holds values that stay unexplained. Besides the 503s at injection, B4 has 1 to 3 timeouts at around +20 to +30 seconds, and the third run of B5 has 5 timeouts at +40.9 to +41.9 seconds. They are apart from the injection and their cause was not established, so they are not read as results of the fault injection.


    container-kill Impact That Grows with Repetition

    container-kill was repeated on the same pod about every minute and a half. backend has 1 replica, and the frontend call timeout is 2 seconds.


    Round Restart count Impact window Failures
    1 1 1.6s 39
    2 2 10.6s 315
    3 3 24.7s 730


    In rounds 2 and 3 the pod was in CrashLoopBackOff at the 8-second mark. The kubelet’s restart delay grows through 10, 20 and 40 seconds, and resets after 10 minutes of running without a problem. So repeating an experiment without resetting that state does not reproduce the same experiment; it becomes a different one. When averaging repeated runs, replace the pod or leave time for the delay to reset. The reset itself was not measured here.

    In the impact windows of rounds 2 and 3, nearly all of the 30 requests per second failed. While backend is down, calls hold the 4-slot pool for up to 2 seconds each, which appears to saturate frontend as well. 503s came first, followed by client timeouts.


    When Three frontend Replicas Stop Together

    Hypothesis

    With frontend made redundant across three replicas, the service survives losing backend.


    This tests two claims from the previous post: that redundant copies with a shared dependency still stop together, and that moving to a soft dependency takes you out of the single point of failure (SPOF). frontend and backend were cut off for 30 seconds with action: partition and direction: both. Only the readiness design, the call timeout and the fallback changed.


    Experiment Setup Runs ok% served% p50 Failure breakdown
    C1 deep readiness, 0.2s timeout 3 11.59, 14.90, 12.05 Same 5006ms 503 127/161/152, ERR 32/30/31, TO 627/563/605
    C2 shallow, 0.2s timeout, no fallback 1 1.90 1.90 207ms 503 879
    C3 shallow, 0.2s timeout, fallback 3 2.13-3.13 100.00 206-208ms None
    C4 shallow, 2s timeout, fallback 1 17.47 20.07 5007ms TO 709


    C1 ran 4 times, but run 2 was thrown out: the laptop went to sleep during the experiment and latency values up to 860 seconds were recorded. A rerun replaced it.


    Deep Readiness Removes All Three at Once

    flowchart TD X["Partition between frontend and backend"] subgraph Deep["Deep readiness (C1)"] D1["Readiness calls backend"] D2["All 3 frontends 0/1 Ready"] D3["Out of the Service together"] D1 --> D2 --> D3 end subgraph Shallow["Shallow readiness (C2, C3)"] S1["Readiness does not look at backend"] S2["All 3 frontends stay 1/1 Ready"] S3["C2: mostly 503, after 207ms"] S4["C3: fallback, served 100%"] S1 --> S2 S2 --> S3 S2 --> S4 end X --> D1 X --> S1

    In C1 all three replicas were 0/1 Ready at the 8-second mark; in C2 and C3 they stayed 1/1 Ready throughout.


    In C1 the three replicas left the Service for the same reason at the same moment. Over time (run 4), the first roughly 6 seconds gave 503s, and from then until the partition ended there were about 29 timeouts and 1 connection error per second. Most C2 users failed too, but they got their 503 in 207ms, while most C1 users waited 5 seconds and then timed out. C3’s 100% also depends on the pods staying in the Service. Deep readiness combined with a fallback was not run, but once the pods are out, requests cannot reach the fallback code.


    Put a dependency shared by several replicas into readiness, and the moment that dependency is cut, readiness grows a partial failure into a total one. That is as far as this data goes.


    A /ready that also checks external dependencies such as a database and a cache needs weighing against this result when the replicas share those dependencies. Readiness that checks for faults in an individual replica was not part of this test.


    What Comparing ok% Alone Misses

    In the table, C1’s ok% is higher than C2’s. That is not because it held up better. The raw logs (runs 1 and 4) show that most of C1’s successes were requests sent in the last roughly 4 seconds of the fault window, and their latency falls with send time through about 4.1, 3.1, 2.1 and 1.0 seconds. They appear to have waited on a connection and been handled after the partition ended. Do not judge an experiment on one summary metric; look at failure types and the time distribution too.


    Fallback That Requests Did Not Reach

    C3 and C4 differ only in the call timeout. C4, run once, comes out at served 20.07%. This value also needs its time distribution, as with C1. Of 178 responses, 23 are fallback, 22 of them from requests sent in the first 5 seconds. The 155 normal responses are 20 from the first 5 seconds and 135 sent in the last 5. served 20.07% is close to the 6 rps (20% of 30 rps) in the calculation below, but the two do not measure the same thing. The fallback code was there, and most requests did not reach it in time.

    C4 capacity: 3 replicas x 4 slots / 2s   = 6 rps  < offered 30 rps
C3 capacity: 3 replicas x 4 slots / 0.2s = 60 rps > offered 30 rps

    In C4 a queue waiting for slots is read as having built up until requests hit the 5-second client timeout. The queue length was not measured directly. Calling something a soft dependency because it has a fallback only holds once the timeout and the concurrency limit have been worked through.


    Timeouts from a Service with No Endpoints

    C1 has one more value that needs explaining. kube-proxy rejects traffic to a Service with no endpoints right away, so the expectation was that clients would fail fast. The node’s rule was indeed as expected. The address is masked.

    -A KUBE-SERVICES -d <ClusterIP>/32 -p tcp -m comment --comment "shop/frontend has no endpoints" -m tcp --dport 8080 -j REJECT --reject-with icmp-port-unreachable

    At 30 rps, though, connection errors came at about 1 per second and the rest were 5-second timeouts. Twenty sequential connections to a ClusterIP with no endpoints all ended in ConnectionRefused, but the first 6 took 0-1ms and the other 14 took about 1023ms each.

    The node’s settings were net.ipv4.icmp_ratelimit = 1000 and net.ipv4.icmp_ratemask = 6168. According to the Linux kernel docs, this mask includes Destination Unreachable, and the ratelimit is the minimum space between ICMP responses to a target, in milliseconds. The first 6 getting through appears to come from the kernel implementation accumulating tokens up to 6 times the interval (XRLIM_BURST_FACTOR in inetpeer.c). When a rejection is lost to the limit, the client never receives it and retransmits the SYN a second later. Under load, the retransmissions hitting the limit as well is read here as what led to the timeouts.

    This load came from a single source, and how it changes with traffic from many sources was not tested. At least in this environment, “no endpoints means immediate failure” did not hold under load, and the caller’s connect timeout decided how long a user waited.


    Where Latency Turns into Failure

    Hypothesis

    If a 100ms delay causes no errors, more delay only makes things a little slower.


    As established above, the delay experiments use direction: from and ran for 30 seconds each.


    Experiment Setup Runs ok% p50 p99 Notes
    D1 100ms, 2s timeout 3 100 210-211ms 290-354ms 0 failures
    D2 300ms, 2s timeout, no fallback 3 44.67, 47.16, 40.75 5003-5006ms 5012-5020ms TO 493/474/519
    D3 300ms, 0.2s timeout, fallback 3 1.22-1.44 (served 100) 207-208ms 274-281ms 887-888 degraded
    D4 300ms, direction: to, 2s timeout 1 100 6ms 63ms No delay


    The Threshold Where a Queue Forms

    Tripling the injected delay was enough to turn 0 failures into more than half failing. By calculation, the cause is capacity more than the delay itself. Slot occupancy and queue length were not measured directly.

    100ms: call about 0.2s -> 3 replicas x 4 slots / 0.2s = 60 rps > offered 30 rps (no queue)
300ms: call about 0.6s -> 3 replicas x 4 slots / 0.6s = 20 rps < offered 30 rps (queue grows)

    In D2 the calls themselves were shorter than the 2-second timeout, so no 503s appeared. With offered load above capacity, though, the queue grew until it reached the 5-second client timeout. The first failure appearing at +6.0 to +6.6 seconds is also read as the time the queue took to grow. All the while frontend stayed Ready, so readiness said nothing.

    The calculated boundary sits around 200ms, but that value was not measured; only 100ms and 300ms were. The doubling also comes from how this app connects, so the numbers may change with connection reuse. What carries to another environment is the method of calculation, not the 300ms value. Work out the threshold from your own service’s concurrency limit and call time, then experiment on either side of it.


    Failures That Status Codes Do Not Show

    Every response in D3 is a 200. But 887-888 of the 898-900 are fallback responses, and normal responses are only 1.22-1.44%. With a call of about 0.6 seconds and a timeout of 0.2 seconds, nearly every call failed.

    Had the steady state been defined by status codes alone, D3 would be a pass. Availability was kept while the feature was nearly switched off, and whether the business can accept that is a separate judgment. This is the reason for splitting ok% and served% in these experiments. The probe also counted the degraded marker in the response body.


    Keeping an Experiment from Becoming an Outage

    Hypothesis

    With duration set, the experiment ends after 30 seconds no matter what.


    Faults That Stay Without the Controller

    After starting a delay with direction: from, 300ms and duration: 30s, the controller manager was scaled to 0 at about the 5-second mark. This lab normally runs 1 replica, and the chart default is 3; the point was to create a situation where no controller at all is available. Below is the result of one run. Values are the times of three calls from frontend to backend, in milliseconds.


    Moment Call times (ms) State
    Before injection 7, 0, 0 Normal
    +3s 613, 605, 603 Injected
    +45s 615, 607, 606 duration passed, 0 controllers
    After the delete attempt 614, 608, 609 Deletion does not finish
    +72s 613, 604, 606 Still injected
    +16s after scaling the controller back to 1 612, 608, 608 Still injected
    +22s after scaling the controller back to 1 8, 1, 0 Recovered (the query after the +31s call found no resource)


    While there was no controller, the following happened.

    • The injected delay stayed after duration passed, because nothing was left to keep time and take the rule away.
    • Creating a new NetworkChaos was refused. The call to the webhook mnetworkchaos.kb.io failed and returned an Internal error.
    • kubectl delete networkchaos exp --timeout=10s ended in a timeout. deletionTimestamp was set, but the finalizer chaos-mesh/records remained.

    The delay went away about 20 seconds after the controller came back. So the emergency procedure of “just delete it if something goes wrong” only works with the controller running. The official docs also say injected faults cannot be recovered if the controller manager and the Chaos Daemon cannot communicate.


    Do not strip the finalizer to clean up faster

    This was not tested here, but the Clean up docs warn that force-clean removes the finalizer without waiting for recovery, so the resource can disappear while the fault stays on the target.


    Before starting an experiment, confirm the controller is healthy, and write down in a runbook who does what if the controller is gone. The PodChaos docs telling you to check that the target pods have no controller manager on them can be read in the same light.


    StatusCheck That Stopped the Experiment in 8-9 Seconds

    So that a runaway experiment does not depend on a person noticing, a Workflow StatusCheck goes with it. This setup runs a partition and an HTTP status check in parallel, and aborts the whole Workflow when the check fails repeatedly.

    apiVersion: chaos-mesh.org/v1alpha1
kind: Workflow
metadata:
  name: guarded
  namespace: shop
spec:
  entry: root
  templates:
  - name: root
    templateType: Parallel
    deadline: 120s
    children: [partition, slo-check]
  - name: partition
    templateType: NetworkChaos
    deadline: 120s
    networkChaos:
      action: partition
      mode: all
      direction: both
      selector:
        namespaces: [shop]
        labelSelectors: {app: frontend}
      target:
        mode: all
        selector:
          namespaces: [shop]
          labelSelectors: {app: backend}
  - name: slo-check
    templateType: StatusCheck
    deadline: 120s
    abortWithStatusCheck: true
    statusCheck:
      mode: Continuous
      type: HTTP
      intervalSeconds: 2
      timeoutSeconds: 1
      failureThreshold: 3
      successThreshold: 1
      http:
        url: http://frontend.shop.svc.cluster.local:8080/api
        method: GET
        criteria:
          statusCode: "200"

    The fault duration inside a Workflow is set by the outer deadline, not by duration in the Chaos spec. frontend was set to shallow readiness, a 0.2-second call timeout and no fallback, and this ran 3 times.


    Run Impact window 503 count
    1 8.0s 241
    2 9.1s 271
    3 8.1s 245


    The events recorded StatusCheckFailureThresholdExceed, WorkflowAborted and ChaosCRDeleted. Three consecutive failures at 2-second intervals mean this setup always takes about 6 seconds. Without the abort, about 3600 requests would have failed over 120 seconds at 30 rps. The 3600 is a calculation, not a measurement.

    StatusCheck goes through the same Service as users, so it sees the failures users see. It has limits too.

    • Its criterion is the status code alone. In a setup like D3, where a fallback returns 200, the criterion does not count a failure, so no abort happens either. This combination was not run.
    • The Workflow controller also lives inside the Chaos Controller Manager. Whether StatusCheck can carry out an abort with the controller down was not tested, and given the earlier result it is safer not to expect it.


    Deciding When an Experiment Is Over

    An experiment ends when the steady-state metrics are back, not when the resource disappears. That is why measurement continued for 25 more seconds after the fault window. Where recovery time starts and ends can follow the distinctions drawn in the MTTR post.


    Experiment Runs Failures in the 25 seconds after the fault Last failure
    C1 3 0, 0, 1 +0.9s
    C2 1 7 (503) +0.2s
    C4 1 0 None
    D2 3 0, 0, 0 None


    C1 was back within about 1 second for new connections, even though its pods had to become Ready again. This setup is a stateless demo app, though. A service with caches, connection pools or queues may not finish the way these numbers do, which is why the recovery window has to be measured as part of the experiment.


    Scope and Limits of These Experiments

    Before carrying these results anywhere, here is their scope.

    • All nodes share one host on a single laptop. There is no real network latency and no real availability zone.
    • Only kube-proxy iptables mode was tested. direction may behave differently in setups that replace kube-proxy with eBPF.
    • HTTP keep-alive was not tested. The delay showing up doubled comes from opening a new connection per call.
    • Dashboard, Schedule, DNSChaos, StressChaos, IOChaos and TimeChaos are not covered.
    • C2, C4, C5, D4 and the controller failure experiment each ran once. Do not read them as repeated results.
    • Alerting and observability are not covered. Testing monitoring responsiveness and alert accuracy through fault injection gets a brief mention in the AWS monitoring stack post.


    Conclusion

    What failed first here was not a hypothesis about the system but the assumption that the tool’s status display is right. In kube-proxy iptables mode a direction: to delay had no effect on Service traffic while the status read AllInjected=True, and mode: one picked a pod already terminating. Either way, writing the result down as it stood would have left a false record of “it holds up”. Measure the effect of the injection before testing the hypothesis.

    On the application side, these are the conclusions. pod-kill removes the API object first, so it cannot stand in for a process crash. The same experiment can split between 0 and 18 failures, or grow with repetition because of CrashLoopBackOff, so run counts and state resets belong in the design. A shared dependency in readiness takes all three replicas out together, and a fallback behind a long timeout did not protect the service. In the delay experiments, 100ms produced no failures and 300ms, beyond the calculated capacity, failed more than half (values in between were not measured), and a steady state defined only by status codes passes a feature that is nearly switched off.

    The experiment tool is itself a dependency. With the controller down, the injected delay stays past duration, and new experiments and deletion are blocked along with it. StatusCheck could abort in 8-9 seconds, but it too runs on top of the controller.

    The numbers in this post come from one laptop, so measure again in your own environment. What carries over is the procedure, not the numbers: write the hypothesis as a sentence that can be disproved, confirm the injection, record the run count, and measure as far as recovery time. Whether the action items left in a postmortem really worked can be tested the same way.
