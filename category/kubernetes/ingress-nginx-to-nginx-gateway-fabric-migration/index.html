    ingress-nginx → nginx-gateway-fabric Migration: A Field Report

    Cutting over 11 ingress-nginx instances on bare-metal Kubernetes to a single NGF control plane with eleven Gateways — without a DNS or firewall change


    Overview

    ingress-nginx has entered maintenance mode, and the Kubernetes Gateway API reached v1.2 GA. With the writing on the wall, I migrated the 11 ingress-nginx instances running on our on-premises cluster to NGINX Gateway Fabric (NGF) 2.x.

    Scope and scale:

    Item Value
    Target cluster On-prem Kubespray (K8s v1.34)
    Existing controllers 11 ingress-nginx instances (1 default nginx + 10 nginx-public-a–j)
    LoadBalancer MetalLB L2 (14 fixed internal IPs)
    Migration targets 11 infra-deployed apps + 9 ArgoCD ApplicationSet apps + 2 standalone repos
    Final shape Single NGF control plane + 11 Gateway CRs (per-Gateway Deployment)
    Downtime per class ~30s–1m (only during the IP swap window)


    Three core goals drove the work:

    1. Cut operational surface — collapse 11 ingress-nginx Helm releases into a single NGF install plus 11 Gateway CRs.
    2. No DNS or firewall changes — keep the same MetalLB IPs so external routing rules don’t need to be touched.
    3. Easy rollback — run NGF in parallel with ingress-nginx and cut over class-by-class with a single values toggle for instant fallback.


    This isn’t a tutorial — it’s a field report covering the architectural decisions, the dead ends, and the eight cutover gotchas that only show up when you actually flip the switch on production traffic. If you’re staring at the same migration, hopefully this saves you a few hours.

    1. Why nginx-gateway-fabric?

    The ingress-nginx project announced a transition to maintenance mode, and the official successor direction is the Gateway API standardized by Kubernetes SIG Network. Multiple implementations exist (Istio, Envoy Gateway, Cilium, Contour, NGF), but I picked NGF 2.x for four reasons:

    1. Stack reuse — the data plane stays NGINX, so existing log/tuning know-how transfers directly.
    2. Native per-Gateway Deployment — each Gateway CR auto-provisions an isolated NGINX Deployment, mapping cleanly onto our existing “class-per-release” model.
    3. One control plane, N data planes — 11 Helm releases collapse to 1, while still keeping IP and process isolation.
    4. CRD-based policy extensions — ClientSettingsPolicy, UpstreamSettingsPolicy, BackendTLSPolicy, etc. cover most of the annotations we relied on.


    The structural win of Gateway API over Ingress is clear resource boundaries. Ingress mixed cluster-scoped concerns (listeners, TLS, class) with app-scoped concerns (route rules) in a single object. Gateway API splits these into GatewayClass / Gateway / HTTPRoute — the cluster admin and the app developer get a natural permission boundary.



    2. Architecture Decision: 1 GatewayClass + 11 Gateways


    The wrong assumption

    Initial design assumed: “11 ingress-nginx instances → 11 ingressClasses → therefore 11 GatewayClasses.” Wrong.

    NGF 2.x reconciles a single GatewayClass per install. The controller is started with --gatewayclass=ngf and ignores all others. If you need multiple GatewayClasses, you have to install NGF multiple times.


    Corrected design

    • 1 GatewayClass: ngf (created automatically by the NGF chart)
    • 11 Gateways: ngf, ngf-public-a … ngf-public-j, all with gatewayClassName: ngf
    • 11 NginxProxy CRs referenced via each Gateway’s infrastructure.parametersRef, pinning the MetalLB IP through service.loadBalancerIP
    • Tenancy boundary = Gateway name. Each app’s HTTPRoute attaches to a specific Gateway via parentRefs, automatically routing through that Gateway’s data plane (and its IP)


    So the multi-tenancy split is not “11 classes” but “11 Gateways.” Because NGF spins up an independent NGINX Deployment per Gateway, process-level isolation is preserved with no extra effort.


    Final directory layout

    network/nginx-gateway-fabric/
├── Chart.yaml                      # upstream mirror — version + appVersion = single source
├── helmfile.yaml.gotmpl            # references Chart.yaml via readFile + fromYaml
├── values.yaml                     # upstream default (helm pull)
├── values.schema.json              # upstream schema
├── values/
│   └── mgmt.yaml                   # custom override (replicas, telemetry off, etc.)
├── cr-chart/                       # Phase 7+ refactor result
│   ├── Chart.yaml
│   ├── values.yaml
│   └── templates/
│       ├── gateways.yaml           # 11 Gateways
│       ├── nginxproxies.yaml       # 11 NginxProxies (LB IP pin)
│       └── servicemonitor.yaml
└── upgrade.sh                      # external-oci canonical
    Chart.yaml as single source

    The chart's version and appVersion (= NGF software git tag) live as a single source of truth in Chart.yaml. helmfile.yaml.gotmpl reads it via readFile + fromYaml, so updating Chart.yaml alone keeps both the chart version and the prepare hook's ?ref=v<APP_VER> path in sync.


    Hook design (apply / destroy)

    Phase Hook Action
    Before any command prepare Pre-install Gateway API CRDs + NGF's own CRDs
    After apply postsync Apply Gateway / NginxProxy (initially via kubectl apply, later via local chart)
    Before destroy preuninstall Remove custom CRs while the controller is still alive (so finalizers complete)
    After destroy postuninstall Remove CRDs + namespace


    OCI chart upgrade script

    NGF only ships via OCI registry (oci://ghcr.io/nginx/charts/nginx-gateway-fabric). The existing upgrade.sh canonical relied on helm search repo to detect the latest version — but helm search repo doesn’t support OCI.

    So I added an external-oci.sh canonical. The version-discovery logic now hits the GitHub Releases API (api.github.com/repos/$GITHUB_REPO/releases/latest) and strips the prefix (default v) from tag_name. With GITHUB_TOKEN set, the rate limit goes from 60 to 5,000 req/h.



    3. Annotation → Gateway API Translation Map

    A practical table of every annotation we actually used and what it became under Gateway API + NGF CRDs:

    ingress-nginx annotation Gateway API / NGF replacement Use case
    force-ssl-redirect: "true" HTTPRoute + RequestRedirect filter (HTTP listener only) Apps requiring HTTPS
    force-ssl-redirect: "false" None (default) Most apps
    ssl-passthrough: "true" TLSRoute + listener tls.mode: Passthrough None in scope — excluded
    backend-protocol: "HTTPS" BackendTLSPolicy (gateway.networking.k8s.io/v1) TLS-backend apps
    backend-protocol: "HTTP" Default Plain HTTP backends
    rewrite-target: / URLRewrite filter (ReplacePrefixMatch) Path rewrite apps
    proxy-body-size: "500m" ClientSettingsPolicy.spec.body.maxSize: "500m" Apps with large uploads
    proxy-body-size: "0" (unlimited) ClientSettingsPolicy.spec.body.maxSize: "0" Container registry
    proxy-read/send-timeout: "300" HTTPRoute timeouts.request + timeouts.backendRequest Long-lived requests
    proxy-buffering: "off" ProxySettingsPolicy.spec.buffering.disable SSE streaming
    proxy-http-version: "1.1" NGF default → no-op, drop —
    limit-rps: "15" RateLimitPolicy (key, rate, burst) Rate limits
    limit-connections: "25" Not natively supported (workaround via SnippetsFilter) Concurrent-connection limits
    configuration-snippet SnippetsFilter CRD (NGF 1.4+) Last resort


    Practical notes from the field

    force-ssl-redirect: split into two sibling HTTPRoutes. One attaches to the HTTP listener with only a RequestRedirect filter. The other attaches to the HTTPS listener with the actual routing rules. Use 307, not 301 — 301 rewrites POST to GET, breaking webhooks and API receivers.


    backend-protocol: HTTPS: solve via BackendTLSPolicy. For ECK-managed Elasticsearch, the operator stores the CA in an internal Secret. We added a chart helper that uses lookup to read it and replicate it as a ConfigMap. When the operator rotates the CA, the next helm upgrade picks it up automatically.


    limit-connections: feature dropped. NGINX’s limit_conn directive is not exposed as an NGF policy. We accepted the loss and pushed the responsibility down to the application layer. A SnippetsFilter workaround exists, but it widens the attack surface — out of scope.



    4. Zero-Downtime Parallel Mode

    The single most important strategic decision: how do you cut over without affecting live traffic, while keeping rollback to a single toggle?


    Core principle: ingress + httproute coexist

    Throughout the migration window, every app stayed in ingress.enabled: true + httproute.enabled: true simultaneously. This satisfies four conditions at once:

    • DNS still points at the existing MetalLB IPs → user traffic flows through ingress-nginx
    • HTTPRoute is reachable only via temp IPs → developers can verify with curl --resolve
    • Rollback = httproute.enabled: false toggle (the ingress was never touched, so no recovery needed)
    • Identical procedure across prod / dev / qa / staging — no per-environment branching


    MetalLB pool expansion

    We added 11 temporary verification IPs to the MetalLB pool, carefully avoiding clashes with existing services and manually reserved IPs (e.g., bare-metal node IPs). These temp IPs get swapped to the real IPs during Phase 6 cutover.


    Verification pattern

    Standard smoke-test commands during the parallel period:


    If the two responses match, OK. One mandatory rollback drill per phase:

    1. Toggle httproute.enabled: false → helmfile apply → temp IP returns 404, real IP returns 200 (existing path unaffected)
    2. Toggle httproute.enabled: true back → temp IP returns 200 again
    3. Each step under 10 seconds; live traffic untouched throughout


    Unified HTTPRoute template across charts

    To make this manageable across many charts, we standardized a httproute values schema. Both individual app charts and the ApplicationSet shared base chart use the same shape:

    httproute:
  enabled: false
  parentRefs:
    - name: ngf
      namespace: nginx-gateway
      # sectionName: https   # use when HTTPS only
  hostnames: []
  rules:
    - matches:
        - path: { type: PathPrefix, value: / }
      # filters:
      #   - type: URLRewrite
      #     urlRewrite: { path: { type: ReplacePrefixMatch, replacePrefixMatch: / } }
      # timeouts:
      #   request: 300s
      #   backendRequest: 300s
      backendRefs:
        - port: 80   # `name` defaults to chart fullname when omitted
  httpsRedirect:
    enabled: false   # if true, auto-generates a sibling HTTP→HTTPS 301 route


    This single schema covers basic routing, rewrites, timeouts, and HTTPS redirects. We validated the pattern on one app first, then replicated.



    5. TLS Wildcard Centralization + cert-manager Future Path


    Constraint

    Our domains are managed at a registrar without a DNS API. This shaped everything:

    • cert-manager + Let’s Encrypt DNS-01 challenge: not feasible (no DNS API)
    • HTTP-01: cannot issue wildcard certs (ACME spec restriction)
    • → Manual self-signed wildcard cert is essentially the only option today


    Previously, every app held its own self-signed Secret. We consolidated into a single wildcard Secret centrally managed.


    Centralized Secret structure

    Secret "wildcard-tls" (nginx-gateway ns)
  └─ CN = *.example.com
     SAN: example.com, *.example.com
     10-year validity
  │
  ▼
Gateway "ngf" listeners:
  - name: http   (port 80)
  - name: https  (port 443, hostname: "*.example.com",
                  certificateRefs: wildcard-tls)
  │
  ▼
Each app's HTTPRoute:
  parentRefs[*].sectionName omitted    : auto-attaches to BOTH HTTP and HTTPS listeners
  parentRefs[*].sectionName: https     : explicit HTTPS-only
  parentRefs[*].sectionName: http      : reserved for the httpsRedirect sibling route


    Chart’s role: nothing (deliberately)

    This is the design point I went back and forth on the longest. Where should TLS ownership live?

    Conclusion: charts stay TLS-agnostic. TLS is a Gateway-layer responsibility.

    • No Certificate CR template in any chart — avoids forcing cert-manager dependency, avoids violating Gateway API’s separation of concerns
    • No Secret / secretName values in charts — the Gateway layer owns it
    • Charts only expose httproute.parentRefs[].sectionName + httpsRedirect.enabled — per-app listener selection and HTTPS-enforcement are the only knobs apps need


    This buys near-zero migration cost when we eventually move to cert-manager:

    • Gateway change: 0 (Secret name/ns stays identical)
    • Chart change: 0 (charts don’t know about the Secret)
    • App values change: 0
    • Work: add a cert-manager CA Issuer + a Certificate CR. Configure it to overwrite the existing Secret → automatic renewal kicks in


    Manual renewal load drops too: from N per-app self-signed Secrets to one wildcard Secret valid for 10 years.


    Why we didn’t unify everything to HTTPS-redirect

    A reasonable question: “Now that we have a wildcard, why not switch every app to sectionName: https + httpsRedirect: true for consistency?”

    I rejected it for three reasons:

    1. cert-manager migration ergonomics are already secured by fixed Secret name/ns alone — has nothing to do with sectionName uniformity.
    2. Internal API clients vary in how reliably they follow 301/307 redirects — verifying every consumer per-app is a real cost.
    3. External port-forward paths break under redirects (RequestRedirect flips scheme but preserves host/port).


    Principle: preserve existing Ingress behavior. Apps that were HTTP stay HTTP; apps that already enforced HTTPS keep enforcing it.



    6. Phase 6 Cutover: The Eight Gotchas

    This is where the lessons live. We cut over 11 classes in ascending order of blast radius, leaving the production-critical class for last. The original plan was simple — and reality found eight ways to complicate it.


    The naive plan

    1. Scale ingress-nginx controller to replicas=0 → IP releases
    2. Patch the matching NginxProxy’s loadBalancerIP to the real IP → helmfile apply
    3. Done


    The first class blew up immediately.


    Issue 1: replicas=0 does NOT release the MetalLB IP

    After kubectl scale deploy/<release>-controller --replicas=0, the pod count went to 0 but MetalLB kept holding the IP. With the pool saturated, NGF couldn’t claim the same IP.

    Cause: with externalTrafficPolicy: Cluster + spec.loadBalancerIP set + a saturated pool, MetalLB does not release the IP as long as the Service object exists. Pod presence is irrelevant.

    Fix: patch the Service to ClusterIP and explicitly remove loadBalancerIP:

    kubectl patch svc <release>-controller -n ingress-nginx --type=json -p='[
  {"op":"replace","path":"/spec/type","value":"ClusterIP"},
  {"op":"remove","path":"/spec/loadBalancerIP"}
]'

    This became Step 2 of cutover.sh.


    Issue 2: helmfile apply doesn’t pick up manifests/ changes

    Edited manifests/nginxproxies.yaml with the new IP, ran helmfile apply, and the postsync hook never executed.

    Cause: helmfile skips release-level postsync hooks if there is no chart-level diff. manifests/ files were raw kubectl targets, invisible to helmfile’s diff machinery.

    Workaround: drive manifest-only changes via kubectl directly:

    kubectl diff -f manifests/nginxproxies.yaml
kubectl apply -f manifests/nginxproxies.yaml

    Structural fix (Phase 7+): refactor manifests/ into a local CR chart so helmfile diff covers Gateway/NginxProxy IP changes end-to-end. We later split this chart out as a public Helm chart — see Section 7.5.


    Issue 3: ValidatingWebhookConfiguration blocks Ingress UPDATE / DELETE

    Right after the first class cutover, ArgoCD prune timed out at 2 minutes trying to delete the now-orphaned Ingress resources.

    Cause: the <release>-admission ValidatingWebhookConfiguration (VWC) is still alive. Its endpoint Service was just patched to ClusterIP, and there are 0 backing pods. All admission webhook calls hang → every Ingress UPDATE / DELETE fails (including ArgoCD prune).

    Fix: pre-delete the VWC during cutover:

    kubectl delete validatingwebhookconfiguration <release>-admission

    Pre-emption is essential — skip this and you cascade into Issue 4.


    Issue 4: foregroundDeletion finalizer stuck

    On the first class, Ingress resources stayed in Terminating indefinitely after deletion.

    Cause: ArgoCD cascade delete attached a foregroundDeletion finalizer. Even though the Ingress had no dependents, garbage collection couldn’t make progress.

    Fix: strip the finalizer manually:

    kubectl get ingress <name> -n <ns> -o jsonpath='{.metadata.finalizers}'
# if [foregroundDeletion]:
kubectl patch ingress <name> -n <ns> -p '{"metadata":{"finalizers":null}}' --type=merge

    Key observation: handle Issue 3 (VWC pre-delete) first and this finalizer stuck never happens. It didn’t recur on subsequent classes. The VWC was the root cause; the stuck finalizer was just a symptom.


    Issue 5: internal pod → public domain → LB IP times out for 2 minutes

    Discovered on the sixth class cutover. Internal CI generator stages started hanging. External clients saw nothing wrong; only cluster-internal pod → LB IP was broken.

    Cause: the NGF chart defaults NginxProxy.kubernetes.service.externalTrafficPolicy to Local. For traffic from internal pods to the LB IP, kube-proxy only forwards if the receiving node has a local endpoint. With NGF data-plane pods at replica=1, most nodes missed and dropped the traffic. The previous ingress-nginx ran with Cluster, so the issue was masked.

    Fix: explicitly set service.externalTrafficPolicy: Cluster on all 11 NginxProxies:

    apiVersion: gateway.nginx.org/v1alpha1
kind: NginxProxy
metadata:
  name: ngf-public-f
  namespace: nginx-gateway
spec:
  kubernetes:
    service:
      type: LoadBalancer
      externalTrafficPolicy: Cluster   # ← this one line
      loadBalancerIP: <real-ip>
    Trade-off

    ETP: Cluster SNATs the client source IP. If your HTTPRoute backends rely on the original client IP, switch to X-Forwarded-For (NGF injects it by default). Anything that keys off client IP — e.g., the source_ip column in container registry audit logs — needs to be re-validated against XFF.


    Issue 6: Router ARP cache

    With the MetalLB pool saturated, one temp IP showed RST from external clients but worked fine internally — a strange asymmetric failure.

    Cause: stale ARP cache on the router.

    Fix: self-resolved when we cut over to the real IP. The temp IP’s ARP entry expired and got cleaned up.

    Bonus discovery: an audit of the router UI showed every forward rule was keyed on MetalLB LB IP:80. Because Phase 6 reassigns the same IP to NGF, no router config change is required — the cutover is transparent at the network layer. Forward rules: zero edits.


    Issue 7: ArgoCD recreates Ingress if values aren’t toggled

    For ApplicationSet apps, if you don’t set ingress.enabled: false post-cutover, ArgoCD keeps recreating the Ingress.

    Fix: add to cutover Step 5 as a permanent procedure:

    # applicationset/values/<project>/<service>/<env>.values.yaml
ingress:
  enabled: false   # required after Phase 6 cutover
httproute:
  enabled: true
  # ...

    To trigger ArgoCD refresh immediately after pushing the values change:

    kubectl annotate application <name> -n argocd argocd.argoproj.io/refresh=normal --overwrite

    Default auto-sync polling is 3 minutes — easy to think nothing’s happening if you don’t force-refresh.


    Issue 8: cutover.sh smoke output rendered as “HTTP 2000”

    When the curl succeeded, $(curl ... || echo "0") concatenated the stdout success code with echo "0", producing nonsense output.

    Fix: separated HTTP_CODE capture and used ${CODE:-000} defaults. Trivial bug, but the kind of thing that adds noise during a midnight cutover. Worth recording.


    Final cutover.sh procedure (per class)

    All eight issues folded in:

    1. Wait check: kubectl get svc -n ingress-nginx <release>-controller -o wide
    2. ingress-nginx Service → patch to ClusterIP + remove loadBalancerIP (Issue 1)
    3. ingress-nginx Deployment → replicas=0
    4. Edit manifests/nginxproxies.yaml to set this Gateway’s IP to the real IP
    5. kubectl diff -f manifests/nginxproxies.yaml → kubectl apply -f (Issue 2)
    6. Toggle ingress.enabled: false in the relevant values files (Issue 7)
    7. Pre-delete VWC: kubectl delete validatingwebhookconfiguration <release>-admission (Issue 3)
    8. Confirm MetalLB reassignment + smoke test (curl --resolve <host>:80:<real-ip>)
    9. Strip finalizers from any leftover Ingress in Terminating (Issue 4)
    10. Monitor for 24h. Non-critical classes can run in parallel with the next cutover; reserve 1–2 days of soak time before the production-critical class.

    Real downtime per class spans only Step 2 (patch) → Step 5 (NGF IP swap completion): roughly 30s–1m.

    7. Results and Lessons


    Final state

    Metric Before After
    Helm releases 11 (ingress-nginx) 1 (NGF)
    Ingress resources 24 0
    HTTPRoute resources 0 15
    Gateway CRs 0 11
    MetalLB allocated IPs unchanged scale unchanged scale
    Self-signed TLS Secrets one per app 1 (wildcard)
    Cert renewal cadence per app once every 10 years


    The MetalLB pool was trimmed back after cutover — most of the temp verification IPs returned to free, with a small reserve.


    Phase 7+ follow-ups

    Originally planned for a one-week soak window, but compressed into the same day. Rationale: rollback cost is identical whether the old releases are in drift state or destroyed state — both recover via a single helmfile apply.

    1. helmfile destroy on all 11 ingress-nginx releases (namespaces wiped clean)
    2. Move network/ingress-nginx/ → network/_optional/ingress-nginx/ (git mv + README archive note)
    3. Shrink the MetalLB pool
    4. Convert NGF manifests/ → local CR chart (manually attach Helm ownership labels/annotations to adopt)
    5. Migrate the container registry to chart-native HTTPRoute (zero-downtime, four-step swap)
    6. Retire all per-app self-signed TLS Secrets


    The chart-native HTTPRoute swap was the most interesting move. New routes were created alongside the old ones, sharing the same hostname (older-wins keeps existing routes serving traffic while new policies sit in TargetConflict state). Deleting the old HTTPRoute releases the conflict — the new policy flips to Accepted=True instantly, and traffic swaps transparently.


    7.5 nginx-gateway-cr — published as a public Helm chart

    The single biggest Phase 7+ effort was refactoring manifests/ into a local Helm chart, then separating that chart out as a public repo.

    Background: the internal manifests/ approach worked around Issue 2 (helmfile skipping hooks) by going through kubectl apply -f. Structurally, those resources sat outside the helmfile pipeline. During Phase 6 IP swaps, this meant manually mixing kubectl diff and kubectl apply every time.

    Why publish?

    • The upstream NGF chart releases actively on OCI and has 20+ templates — non-trivial to track manually
    • What we override is not NGF’s internal templates, but the separate CRs the controller reconciles (Gateway, NginxProxy)
    • These resources have no environment-specific quirks — “Gateway + NginxProxy (LB IP pin) + ServiceMonitor” is the common shape for anyone wanting per-Gateway multi-tenancy on NGF
    • Standard Helm chart practice → publish

    Chart repo: github.com/somaz94/helm-charts/tree/main/charts/nginx-gateway-cr


    What the chart provisions

    • Gateway — 1 or N, declared as a values array. Each Gateway defaults to gatewayClassName: ngf
    • NginxProxy — referenced by each Gateway’s infrastructure.parametersRef. service.loadBalancerIP pins the MetalLB / cloud-LB IP. externalTrafficPolicy: Cluster is the default (Issue 5 baked in)
    • ServiceMonitor — Prometheus metrics resource that the upstream NGF chart doesn’t ship. Ready to scrape if Prometheus Operator is installed


    Usage with helmfile

    # helmfile.yaml.gotmpl — two releases linked via `needs`
repositories:
  - name: somaz
    url: https://charts.somaz.blog

releases:
  - name: nginx-gateway-fabric
    namespace: nginx-gateway
    chart: oci://ghcr.io/nginx/charts/nginx-gateway-fabric
    version: 2.5.1
    # ... NGF controller config

  - name: nginx-gateway-cr
    namespace: nginx-gateway
    chart: somaz/nginx-gateway-cr
    version: <chart-version>
    needs:
      - nginx-gateway/nginx-gateway-fabric
    values:
      - values/cr.yaml


    Per-Gateway multi-tenancy values (verify exact field names against the chart README):

    # values/cr.yaml
gateways:
  - name: ngf
    loadBalancerIP: <main-ip>
    listeners:
      - name: http
        port: 80
        protocol: HTTP
      - name: https
        port: 443
        protocol: HTTPS
        tls:
          certificateRefs:
            - name: wildcard-tls
  - name: ngf-public-a
    loadBalancerIP: <public-a-ip>
    # ...


    Who this chart is for

    • Per-Gateway multi-tenancy — assigning a separate LoadBalancer IP per Gateway
    • Migrators from the ingress-nginx-multi-instance pattern (one ingressClass per release)
    • Bare-metal / on-prem with MetalLB where IPs need to be manually pinned
    • Anyone who wants ServiceMonitor auto-provisioned alongside

    Who this chart is overkill for: setups with a single Gateway, or cloud LBs with dynamic allocation. The upstream NGF chart’s nginxGateway.gateway section may suffice; v2.5+ also provides some Gateway provisioning natively.


    What we got

    • One helmfile diff covers Gateway / NginxProxy IP changes end-to-end
    • Cutover collapses to “edit one values line → helmfile apply”
    • The internal manifests/ + manual kubectl combo disappears
    • Reusable across the next cluster with only values changes


    In hindsight, starting with the public chart from day one would have made Phases 1–6 cleaner. But evolving through manifests/ → local chart → public chart in that order was instructive — each step exposed which abstraction layer solves which class of problem. The destination is obvious in retrospect; getting there required the intermediate steps.


    Lessons

    Question your design assumptions before reading documentation. “11 instances → 11 GatewayClasses” was a mental-model carryover, not a fact. Verify implementation-specific constraints from primary sources before sketching the architecture.


    The value of parallel mode is psychological safety, not literal rollback. We never triggered a rollback during the parallel window. But the fact that we could — with one toggle — is what made it OK to cut over on a Friday evening. Worth repeating in any future migration.


    80% of the problems live in the cutover hour. Design, chart authoring, parallel-mode validation: relatively calm. The IP-swap moment fired Issues 1–6 in sequence. Issue 5 (ETP: Local) in particular was a silent failure — internal services timing out for 2 minutes at a time, easy to miss. Wire up internal-traffic monitoring (CI, webhooks, cross-service calls) before the cutover window starts.


    One default value can rewrite operations. NGF’s ETP: Local default is sensible (security + performance), but it silently breaks internal reachability when migrating from ingress-nginx’s Cluster default. For the next migration, build a checklist comparing tool defaults against the assumptions of the existing environment, item by item.


    TLS ownership belongs at the Gateway layer. It’s tempting to put cert/secret values on the chart. Resist it. Following Gateway API’s resource-boundary model — chart knows HTTP routing, Gateway knows TLS — gave us a free path to cert-manager later, with zero chart code changes.



    Conclusion

    This wasn’t just a controller swap. Migrating 11 instances drove home, viscerally, how Kubernetes’ L7 routing model has evolved from Ingress’s “everything in one object” toward Gateway API’s “explicit resource boundaries.”

    The numbers shifted: 11 Helm releases collapsed to 1, scattered self-signed certs unified to a single wildcard, ad-hoc annotations consolidated into CRD-based policies. From outside, DNS and firewall rules look identical. From inside, the operational load is meaningfully lower.

    The two patterns that will travel to the next migration are parallel mode (rollback cost reduced to a values toggle) and TLS-as-a-Gateway-layer-responsibility (cert-manager future-migration cost reduced to near zero).

    Phase 6’s Issues 1–8 don’t appear in any documentation — they only surface under the actual conditions of a production cutover. The externalTrafficPolicy: Local default in particular was the closest thing to a true silent failure. If this post saves someone an hour during their own cutover, that’s the post doing its job.

    Next on the list: restoring X-Forwarded-For-based audit logging, and evaluating Gateway API v1.3 features (especially full GRPCRoute adoption). Those will get their own writeups.
