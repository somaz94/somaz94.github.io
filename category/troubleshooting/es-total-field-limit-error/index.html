    Elasticsearch total_fields.limit Exceeded After Migrating from Winston to Pino

    Understanding and resolving the field mapping limit error when switching Node.js logging libraries


    Table of Contents

    1. Overview
    2. Problem Description
    3. Root Cause Analysis
    4. Solution Approaches
    5. Post-Change Verification
    6. Additional Considerations
    7. Conclusion
    8. References


    Overview

    After migrating a Node.js logging library from Winston to Pino, you may encounter the Limit of total fields [1000] has been exceeded error in Elasticsearch. This occurs because Pino automatically serializes the req object — including headers, query parameters, and method details — into log entries by default.

    This article walks through the root cause of this error and provides three practical solutions: removing unnecessary fields in Filebeat, adjusting the total_fields.limit setting in Elasticsearch, or applying both for maximum safety.


    Problem Description


    Error Message

    While ingesting Pino-based logs through a Filebeat → Logstash → Elasticsearch pipeline, the following error appeared:

    IllegalArgumentException: Limit of total fields [1000] has been exceeded while adding new fields


    Why Does This Happen?

    Elasticsearch enforces a default setting of index.mapping.total_fields.limit: 1000 on every index. This limits the maximum number of field mappings a single index can contain. The limit is always active, even without explicit configuration.


    Why Wasn’t This an Issue with Winston?

    Winston does not automatically include the HTTP request object (req) in log output. As a result, the total number of fields remained well below 1,000 and never triggered the limit.

    Pino, on the other hand, serializes the req object by default:

    {
  "level": 30,
  "time": 1707600000000,
  "msg": "request completed",
  "req": {
    "method": "GET",
    "url": "/api/users",
    "headers": {
      "host": "example.com",
      "user-agent": "Mozilla/5.0...",
      "accept": "application/json",
      "accept-language": "ko-KR,ko;q=0.9",
      "accept-encoding": "gzip, deflate, br",
      "connection": "keep-alive",
      "cache-control": "no-cache",
      "cookie": "session=abc123...",
      "x-forwarded-for": "192.168.1.1",
      "x-request-id": "uuid-1234"
      // ... 17+ header fields
    },
    "query": {
      "page": "1",
      "limit": "20"
    },
    "remoteAddress": "192.168.1.1",
    "remotePort": 54321
  },
  "res": {
    "statusCode": 200
  },
  "responseTime": 42
}

    Each nested field under req gets mapped as an individual field in Elasticsearch. When combined with the existing fields, the total exceeded the 1,000-field limit.


    Root Cause Analysis

    The core issue can be summarized as follows:

    Factor Winston Pino
    req object in logs Not included Automatically serialized
    Typical header fields 0 ~17+
    Query parameter fields 0 Dynamic
    Risk of exceeding limit Low High

    Pino’s default serializers attach req.headers.*, req.query.*, req.method, req.url, and several other nested properties. In a mature logging index that already contains hundreds of fields from application-level data, adding these extra fields pushes the total count past the default 1,000-field boundary.


    Solution Approaches

    There are three approaches available. You can apply one or combine them depending on your requirements.

    Approach Pros Cons
    Remove req field in Filebeat No ES config changes needed, removes redundant data Log output differs from Pino's raw format
    Increase ES total_fields.limit Single-line config change, preserves req data Existing indices require a separate API call
    Apply both Safest option Two configuration changes required


    Approach 1: Remove the req Field in Filebeat

    Use the drop_fields processor in the Filebeat configuration to strip the req field before sending data to Elasticsearch.

    filebeat.yml

    filebeat.inputs:
  - type: log
    enabled: true
    paths:
      - /var/log/app/*.log
    json.keys_under_root: true
    json.overwrite_keys: true
    json.add_error_key: true

processors:
  - drop_fields:
      fields: ["req"]
      ignore_missing: true

    Dropping the entire req field removes all nested children including req.headers.*, req.query.*, and req.method.

    If you need to preserve specific fields from req, use the script processor instead:

    processors:
  - script:
      lang: javascript
      source: >
        function process(event) {
          var req = event.Get("req");
          if (req) {
            // Preserve only method and url, discard everything else
            event.Put("req_method", req.method || "");
            event.Put("req_url", req.url || "");
            event.Delete("req");
          }
        }

    After modifying the configuration, restart Filebeat:

    # Linux
sudo systemctl restart filebeat

# Kubernetes
kubectl rollout restart -n <namespace> deployment filebeat


    Approach 2: Increase the Elasticsearch total_fields.limit

    New Indices — Index Template Configuration

    Configure the limit via an index template so that all newly created indices inherit the higher value.

    PUT _index_template/app-logs-template
{
  "index_patterns": ["app-logs-*"],
  "template": {
    "settings": {
      "index.mapping.total_fields.limit": 2000
    }
  },
  "priority": 100
}

    When using Logstash, specify the template in the output block:

    output {
  elasticsearch {
    hosts => ["https://elasticsearch:9200"]
    index => "app-logs-%{+YYYY.MM.dd}"
    template => "/etc/logstash/templates/app-logs-template.json"
    template_name => "app-logs-template"
    template_overwrite => true
  }
}

    Contents of app-logs-template.json:

    {
  "index_patterns": ["app-logs-*"],
  "settings": {
    "index.mapping.total_fields.limit": 2000
  }
}

    Existing Indices — Update via API

    Template changes do not retroactively apply to existing indices. You must update them directly via the Settings API.


    The same operation can be executed from Kibana Dev Tools:

    PUT app-logs-*/_settings
{
  "index.mapping.total_fields.limit": 2000
}

    Verifying the Change

    # Check a specific index
GET app-logs-2025.02.11/_settings/index.mapping.total_fields.limit

# Check multiple indices at once
GET app-logs-*/_settings/index.mapping.total_fields.limit


    Approach 3: Apply Both (Recommended)

    The safest strategy is to combine both approaches:

    1. Remove unnecessary req fields in Filebeat to prevent redundant data from being indexed in Elasticsearch.
    2. Set total_fields.limit with headroom to accommodate any future field additions without triggering the error.
    # filebeat.yml — Remove req field
processors:
  - drop_fields:
      fields: ["req"]
      ignore_missing: true

    // ES index template — Set limit with headroom
{
  "index_patterns": ["app-logs-*"],
  "settings": {
    "index.mapping.total_fields.limit": 2000
  }
}


    Post-Change Verification


    Checking the Current Field Count

    After applying changes, verify that the index field count remains below the configured limit.


    Verifying the Current Limit Setting


    Confirming Filebeat Behavior

    Verify that the req field is being properly removed by Filebeat.

    # Run Filebeat in debug mode
sudo filebeat -e -d "processors"

# Or monitor the Filebeat log file
tail -f /var/log/filebeat/filebeat.log


    Additional Considerations


    Customizing Serialization at the Pino Level

    Rather than handling the issue downstream, you can modify how Pino serializes the req object at the source.

    const pino = require('pino');

const logger = pino({
  serializers: {
    // Exclude headers from req serialization
    req: (req) => ({
      method: req.method,
      url: req.url,
      // headers intentionally omitted
    }),
  },
});

    This approach modifies the log output itself, eliminating the need for Filebeat or Logstash workarounds.


    Controlling Dynamic Mapping

    You can set Elasticsearch’s Dynamic Mapping to strict or false to prevent unexpected fields from being mapped.

    PUT _index_template/app-logs-template
{
  "index_patterns": ["app-logs-*"],
  "template": {
    "settings": {
      "index.mapping.total_fields.limit": 2000
    },
    "mappings": {
      "dynamic": "false"
    }
  }
}

    With dynamic: false, unmapped fields are still stored in _source but are not indexed or searchable. This effectively prevents the field mapping count from growing unboundedly.


    Avoid Setting total_fields.limit Too High

    While it may be tempting to set a very high limit, this is not recommended. A large number of field mappings increases the Cluster State size, which leads to higher memory consumption on master nodes and can degrade cluster stability. A reasonable range is between 2,000 and 5,000. The correct long-term strategy is to minimize the number of fields being indexed in the first place.


    Conclusion

    The index.mapping.total_fields.limit error is one of the most commonly encountered issues when operating Elasticsearch. It is especially likely to surface when switching logging libraries or introducing new data sources that significantly increase the number of fields.


    Key Takeaways:

    • Elasticsearch enforces a default limit of 1,000 fields per index
    • Pino automatically serializes the req object, generating numerous nested fields
    • The safest resolution is to combine field removal (Filebeat/Pino) with a limit increase (ES settings)
    • The long-term best practice is to minimize the number of fields indexed in Elasticsearch to maintain cluster health
