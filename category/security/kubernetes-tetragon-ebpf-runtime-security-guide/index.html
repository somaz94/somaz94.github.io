    Kubernetes Tetragon Guide: eBPF In-Kernel Runtime Security

    In-Kernel eBPF Filtering, TracingPolicy CRDs, Real-Time Sigkill Enforcement, and BTF Optimization


    Overview

    Enterprise security in cloud-native environments cannot rely solely on static container image vulnerability scanning (such as Trivy or Grype) and admission control policy enforcement (such as Kyverno or OPA/Gatekeeper). Even pods that pass every pre-deployment verification check remain vulnerable during active execution to zero-day exploits, remote code execution (RCE), unauthorized interactive shell takeovers, privilege escalation, and container escapes. Securing modern Kubernetes workloads therefore requires an active runtime defense layer capable of monitoring low-level container actions directly at the Linux kernel boundary and neutralizing threats the instant they occur.

    Traditional runtime security platforms typically rely on a passive, post-execution detection model. They intercept raw system call events in kernel space and stream them through ring buffers or perf buffers to a user-space daemon, where signature rules are evaluated and alerts are generated. In high-throughput production Kubernetes clusters, however, this architecture introduces major structural bottlenecks: event transmission latency between kernel and user space, CPU overhead from constant context switching, and dropped events during peak I/O. Furthermore, in the seconds or minutes it takes for an alert to reach an external SIEM or alerting webhook, adversaries can execute payloads, exfiltrate sensitive credentials, or compromise adjacent nodes.

    Developed under the Cilium project, Tetragon fundamentally transforms this paradigm using Extended Berkeley Packet Filter (eBPF) technology. Instead of forwarding raw event streams to user space for inspection, Tetragon pushes security policy evaluation directly into the Linux kernel. This in-kernel filtering eliminates user-space context switching overhead and ring buffer congestion. When a policy violation is detected, Tetragon immediately executes bpf_send_signal(SIGKILL), terminating the offending process synchronously before it can execute malicious instructions in user space. This guide explores Tetragon core architecture and its in-kernel execution model, provides a production DaemonSet Helm deployment, walks through declarative TracingPolicy CRDs, validates real-time attack simulation with synchronous Sigkill termination, and covers enterprise tuning including kernel BTF/CO-RE requirements, BPF map sizing, and false-positive reduction.


    1. eBPF In-Kernel Execution Model and Tetragon Architecture

    Limitations of User-Space Detection and the In-Kernel Filtering Shift

    Runtime security monitoring tools that rely on Linux kernel system call hooking continuously copy raw event streams from kernel space to user-space daemons via perf buffers or BPF ring buffers. The user-space daemon parses these events and matches them against predefined signature rulesets.

    In enterprise production clusters handling demanding workloads, this architecture creates three critical bottlenecks:

    1. Context Switching and Memory Bandwidth Overhead: Generating tens or hundreds of thousands of system call events per second forces non-stop transitions between kernel and user space, driving up CPU context switching and memory bus consumption.
    2. Event Drop Risks: When file I/O or process spawning surges, ring buffer capacity saturates. Events are dropped, creating an opening for adversaries who generate deliberate system call noise to blind security audit logging.
    3. Asynchronous Detection Latency: Transporting raw events from the kernel to user-space daemons, executing rule evaluation pipelines, and dispatching alerts to SIEMs or messaging webhooks incurs latency ranging from tens of milliseconds to several seconds. Attackers can open a reverse shell or dump a database in fractions of a second, rendering post-execution alerts incapable of preventing damage.

    Tetragon resolves this dilemma by executing a fundamental design shift: push logic into the kernel rather than streaming data to user space. User-declared TracingPolicy rules are compiled into eBPF bytecode and loaded directly into the kernel. Parameter checks, process namespace inspections, and binary execution paths are verified entirely within kernel space. Non-matching benign events are discarded immediately inside the kernel without consuming ring buffer slots, and only matched security anomalies or enforcement signals are emitted to user space.

    Kernel Hook Points: kprobe, tracepoint, LSM BPF, and Cilium Ecosystem Integration

    Rather than restricting itself to generic system call entry and exit points (sys_enter, sys_exit), Tetragon attaches precision hooks across multiple Linux kernel subsystems:

    • kprobe / kretprobe: Hooks entry and exit boundaries of arbitrary internal kernel functions to capture arguments and return values. Beyond sys_execve, Tetragon inspects Virtual File System (VFS) operations such as vfs_read, vfs_write, and security_file_open to verify file integrity with high fidelity.
    • tracepoint: Attaches to statically defined trace points in kernel source code, delivering stable, high-performance monitoring of scheduler and system call events without sensitivity to internal function symbol shifts across kernel versions.
    • LSM (Linux Security Modules) BPF: Supported in Linux 5.7+, bpf_lsm couples eBPF programs directly to LSM security hooks, enabling kernel-level decisions to authorize or deny operations before execution occurs.
    • uprobe: Hooks user-space binaries and shared libraries (such as glibc or OpenSSL) to inspect unencrypted payloads or authentication API calls before data encryption or after decryption.

    Tetragon also shares its underlying eBPF infrastructure with the Cilium network CNI. By binding kernel cgroups v2 hierarchies directly with BPF maps, Tetragon instantly resolves the Kubernetes namespace, pod name, and container ID associated with a system call without issuing asynchronous queries to the Kubernetes API server. Combining L3-L7 network filtering via Cilium NetworkPolicy with in-kernel process and syscall controls via Tetragon TracingPolicy delivers full-stack Zero Trust across the cluster.


    Real-Time Enforcement Architecture and bpf_send_signal Mechanics

    What sets Tetragon apart from purely observational tools is its synchronous, in-kernel enforcement engine.

    Introduced in Linux 5.3, the bpf_send_signal() eBPF helper allows a kernel eBPF program to inject POSIX signals directly into the currently executing task (current). Tetragon uses this helper to deliver real-time process termination via action: Sigkill:

    1. An adversary inside a container attempts to execute an unauthorized binary (e.g., /tmp/nc or nmap) by calling the execve system call.
    2. Before the kernel replaces the process image in user space, the attached kprobe eBPF program triggers.
    3. The eBPF program extracts arguments (argv[0]) and verifies them against the loaded TracingPolicy within the kernel.
    4. Upon detecting a matching violation, the eBPF program immediately executes bpf_send_signal(SIGKILL).
    5. The targeted process is terminated synchronously in kernel space before control ever returns to user space or a single instruction of the payload executes.

    Because this sequence executes synchronously within the system call context, there is no latency window for exploitation, establishing reliable real-time protection.

    2. Deploying Tetragon DaemonSet on Kubernetes and tetra CLI Operations

    Production values.yaml Configuration and Least-Privilege Capabilities

    Tetragon runs as a DaemonSet across all worker nodes to hook local kernels. A production Helm configuration requires defining host network access, BPF filesystem mounts, kernel BTF (BPF Type Format) paths, and resource limits.

    Add the official Cilium Helm repository:

    helm repo add cilium https://helm.cilium.io/
helm repo update

    Create a production-ready values.yaml:

    # Tetragon production settings
enabled: true
hostNetwork: true
dnsPolicy: Default

# Path for exporting JSON audit event logs
exportDirectory: "/var/log/tetragon"

# Enable process audit log export (host file mode)
export:
  mode: "file"
  filenames:
    - "tetragon.log"

tetragon:
  image:
    repository: quay.io/cilium/tetragon
    tag: v1.7.1
    imagePullPolicy: IfNotPresent
  
  # Kernel BTF file path (auto-detects /sys/kernel/btf/vmlinux if empty)
  btf: ""

  # Least-privilege security context
  securityContext:
    privileged: false
    allowPrivilegeEscalation: false
    appArmorProfile:
      type: Unconfined
    capabilities:
      drop:
        - ALL
      add:
        - SYS_ADMIN
        - BPF
        - PERFMON
        - SYS_RESOURCE

  resources:
    limits:
      cpu: "1000m"
      memory: "1024Mi"
    requests:
      cpu: "250m"
      memory: "512Mi"

# Automatically install Tetragon CRDs
crds:
  installMethod: "operator"

# Production DaemonSet rolling update strategy
updateStrategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1

    Setting hostNetwork: true is essential for Tetragon to track host process hierarchies and cgroups accurately. Rather than configuring a blanket privileged: true, this configuration adheres to least-privilege principles by dropping all capabilities and granting only SYS_ADMIN, BPF, PERFMON, and SYS_RESOURCE.


    Least Privilege over Monolithic Privileged Mode
    • SYS_ADMIN: Required for attaching BPF programs and performing system administrative tasks where BPF capability alone is insufficient on earlier kernels.
    • BPF: Grants permission to load, verify, and inspect eBPF programs and maps without full root privileges.
    • PERFMON: Grants permission to attach performance monitoring hooks, kprobes, tracepoints, and ring buffer event listeners.
    • SYS_RESOURCE: Allows raising locked memory limits (RLIMIT_MEMLOCK) required for allocating BPF map memory.


    Deploying the DaemonSet with Helm and Validating Agent Health

    Deploy Tetragon into the kube-system namespace using the configured values.yaml:

    helm upgrade --install tetragon cilium/tetragon \
  --namespace kube-system \
  --create-namespace \
  -f values.yaml

    Verify that the DaemonSet pods reach the Running state across all nodes:

    kubectl get daemonset -n kube-system tetragon
kubectl get pods -n kube-system -l app.kubernetes.io/name=tetragon -o wide

    Check the Tetragon agent logs to verify that BPF maps initialized and default sensors loaded without errors:

    kubectl logs -n kube-system -l app.kubernetes.io/name=tetragon -c tetragon --tail=50

    When logs report Listening for events... alongside Loaded probe... entries, the eBPF programs are successfully running in the host kernel.


    Real-Time Event Streaming via the Built-In tetra CLI

    Tetragon bundles a dedicated CLI binary, tetra, which communicates with the daemon over gRPC. Operators can execute commands inside the daemon pod to inspect runtime state and stream live events.

    Check daemon health and loaded sensors:

    kubectl exec -ti -n kube-system ds/tetragon -c tetragon -- tetra status

    In a healthy deployment, the command confirms operational status:

    Health Status: RUNNING

    Stream live process execution events in compact format for workloads running in the default namespace:

    kubectl exec -ti -n kube-system ds/tetragon -c tetragon -- tetra getevents -o compact --namespaces default

    Opening another terminal and running commands such as ls or whoami inside any pod in the default namespace produces instant event output:

    process default/demo-pod /bin/ls -la
exit    default/demo-pod /bin/ls -la 0

    The output captures the executed binary path, arguments, parent process ID, and exit codes in real time.


    3. Declarative Security Observability with TracingPolicy CRDs

    Tetragon manages monitoring and enforcement policies as Kubernetes custom resources: TracingPolicy (cluster-wide scope) and TracingPolicyNamespaced (namespace scope). This allows security policies to be maintained declaratively as code in GitOps workflows.


    sys_execve Argument Inspection and Unauthorized Binary Execution

    Running package managers or launching binaries from ephemeral directories (/tmp, /dev/shm, /var/tmp) or network reconnaissance tools (nmap, netcat, tcpdump) inside production containers represents a primary Indicator of Compromise (IoC).

    The following manifest defines a TracingPolicy that monitors executions from temporary paths or common hacking utilities:

    apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "audit-suspicious-binaries"
spec:
  kprobes:
    - call: "sys_execve"
      syscall: true
      args:
        - index: 0
          type: "string"
      selectors:
        - matchArgs:
            - index: 0
              operator: "Prefix"
              values:
                - "/tmp/"
                - "/dev/shm/"
                - "/var/tmp/"
        - matchArgs:
            - index: 0
              operator: "Postfix"
              values:
                - "nmap"
                - "nc"
                - "netcat"
                - "tcpdump"

    Policy specifications:

    • call: "sys_execve": Attaches the probe to the primary system call responsible for process execution.
    • syscall: true: Designates an architecture-specific system call entry point rather than an internal kernel helper.
    • args: Instructs the probe to inspect the first argument (index: 0), which contains the binary path string.
    • selectors: Evaluates filtering conditions using Prefix and Postfix operators. Only executions matching temporary paths or target utility names trigger events; benign executions are dropped immediately within kernel space.


    Privilege Escalation (setuid) and Namespace Escape Detection

    When adversaries compromise a low-privilege container, their subsequent actions typically involve attempting root privilege acquisition (UID 0) or escaping namespace boundaries.

    The following manifest monitors attempts to alter process user IDs or manipulate host namespaces:

    apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "audit-privilege-escalation"
spec:
  kprobes:
    - call: "sys_setuid"
      syscall: true
      args:
        - index: 0
          type: "int"
      selectors:
        - matchArgs:
            - index: 0
              operator: "Equal"
              values:
                - "0"
    - call: "sys_setns"
      syscall: true
      args:
        - index: 0
          type: "int"
        - index: 1
          type: "int"
    • sys_setuid: Monitors calls where argument index: 0 equals 0 (Root), detecting attempts by non-root processes to transition into root privileges.
    • sys_setns: Monitors invocations attempting to attach a process to other Linux namespaces, capturing attempts to escape container isolation into host PID, network, or IPC namespaces.


    Sensitive File Integrity Monitoring: /etc/shadow and LSM VFS Hooks

    Adversaries attempting to read system account password hashes in /etc/shadow or exfiltrate cluster credentials require immediate detection.

    Tetragon hooks the Virtual File System (VFS) function security_file_open to trace file read operations:

    apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "audit-sensitive-file-access"
spec:
  kprobes:
    - call: "security_file_open"
      syscall: false
      args:
        - index: 0
          type: "file"
      selectors:
        - matchArgs:
            - index: 0
              operator: "Equal"
              values:
                - "/etc/shadow"
                - "/etc/sudoers"
                - "/etc/kubernetes/admin.conf"

    security_file_open is called across all file open operations by the Linux Security Module (LSM) framework. By parsing the file structure directly, Tetragon inspects normalized absolute paths, defeating attempts to evade detection via symbolic links or relative directory traversal (../../etc/shadow).


    4. Real-World Attack Simulation and In-Kernel Sigkill Enforcement

    Simulating Interactive Attacks and Verifying Synchronous Sigkill Termination

    To demonstrate in-kernel active enforcement, configure a policy that terminates any process executing from temporary directories using action: Sigkill.

    Save the following policy as enforce-block-tmp-exec.yaml:

    apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "enforce-block-tmp-exec"
spec:
  kprobes:
    - call: "sys_execve"
      syscall: true
      args:
        - index: 0
          type: "string"
      selectors:
        - matchArgs:
            - index: 0
              operator: "Prefix"
              values:
                - "/tmp/"
          matchActions:
            - action: Sigkill

    Apply the policy:

    kubectl apply -f enforce-block-tmp-exec.yaml

    Confirm that the policy is recognized by the cluster:

    kubectl get tracingpolicies

    Launch a test pod in the default namespace:

    kubectl run attacker-victim --image=ubuntu:22.04 --restart=Never -- sleep 3600
kubectl wait --for=condition=Ready pod/attacker-victim --timeout=30s

    Open an interactive shell inside the container:

    kubectl exec -ti attacker-victim -- bash

    Inside the container shell, create an executable script under /tmp and attempt execution:

    # Create executable shell script in temporary directory and grant execution permissions
echo '#!/bin/bash' > /tmp/payload.sh
echo 'echo "Pwned!"' >> /tmp/payload.sh
chmod +x /tmp/payload.sh

# Attempt execution
/tmp/payload.sh

    The shell does not output the script payload; instead, execution halts instantly with:

    Killed

    The moment the command was entered, the eBPF program injected bpf_send_signal(SIGKILL) in kernel space, terminating the process before /tmp/payload.sh executed its first line of code. Active protection completes synchronously without waiting for user-space intervention.

    5. Enterprise Production Optimization, BTF, and Tuning

    Kernel Prerequisites: BTF (BPF Type Format) and CO-RE Portability

    Tetragon relies on BPF CO-RE (Compile Once – Run Everywhere). Prior to CO-RE, eBPF programs required installing kernel development headers (linux-headers-$(uname -r)) on each host node and invoking Clang/LLVM to compile C code at runtime, wasting node CPU and memory.

    Under CO-RE, pre-compiled BPF bytecode dynamically relocates internal structure offsets at load time by querying host kernel BTF (BPF Type Format) metadata.


    Kernel Requirements for Production Tetragon
    • Kernel Version: Linux 5.4+ LTS minimum for reliable bpf_send_signal support; Linux 5.7+ for combining LSM BPF security hooks.
    • BTF Support: Kernel compiled with CONFIG_DEBUG_INFO_BTF=y and binary present at /sys/kernel/btf/vmlinux.
    • BPF Configuration: CONFIG_BPF=y and CONFIG_BPF_SYSCALL=y enabled.


    Verify BTF availability on worker nodes:

    ls -la /sys/kernel/btf/vmlinux

    Modern distributions—such as Ubuntu 20.04/22.04 LTS, RHEL 8.4+, Amazon Linux 2023, and Bottlerocket—enable BTF out of the box. Environments running older kernels require mounting external BTF archives from repositories such as BTFhub.


    BPF Map Tuning and Host Resource Overhead Boundaries

    Tetragon maintains BPF hash maps and ring buffers to track process lineages and open file descriptors. On high-density nodes, adjusting cache sizes prevents table exhaustion or memory locking (RLIMIT_MEMLOCK) errors.

    Tune cache allocations in values.yaml:

    tetragon:
  extraArgs:
    # Process cache table size for lineage tracking (default: 65536)
    process-cache-size: "131072"
    # Event export queue buffer size
    event-queue-size: "20000"


    Pushing Logic into Kernel: The Efficiency Advantage

    By filtering system calls at the eBPF layer rather than streaming every syscall to user space, Tetragon maintains an average CPU overhead below 1% to 2% and memory consumption between 200 MiB and 400 MiB even on high-density Kubernetes worker nodes handling tens of thousands of requests per second.


    Eliminating False Positives with In-Kernel Selectors and Namespace Filtering

    Applying real-time termination policies (action: Sigkill) without granular filtering risks disrupting administrative scripts, CI/CD jobs, or backup tasks. In-kernel selectors allow creating precise exception rules.

    The following policy excludes administrative and monitoring namespaces from the /tmp execution ban:

    apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "enforce-block-tmp-with-exceptions"
spec:
  podSelector:
    matchExpressions:
      - key: "k8s:io.kubernetes.pod.namespace"
        operator: NotIn
        values:
          - "kube-system"
          - "monitoring"
  kprobes:
    - call: "sys_execve"
      syscall: true
      args:
        - index: 0
          type: "string"
      selectors:
        - matchArgs:
            - index: 0
              operator: "Prefix"
              values:
                - "/tmp/"
          matchActions:
            - action: Sigkill
    • podSelector.matchExpressions: Excludes kube-system and monitoring pods from enforcement using the NotIn operator on k8s:io.kubernetes.pod.namespace.
    • matchPIDs / matchArgs: Can be configured to allow specific binary names or parent processes.

    Because these exception rules are evaluated in eBPF bytecode inside the kernel, evaluation completes in microseconds without degrading cluster performance.


    Conclusion

    Cloud-native workloads require runtime defenses that extend beyond pre-deployment static scans and admission webhooks. While first-generation detection tools stream raw system call events to user space for post-execution alerting, Cilium Tetragon establishes a new standard for runtime security through in-kernel eBPF enforcement.

    Key advantages of adopting Tetragon include:

    1. Synchronous In-Kernel Process Termination: Utilizing bpf_send_signal(SIGKILL) to terminate malicious processes synchronously before unauthorized binaries execute payload instructions.
    2. Minimal Resource Overhead via In-Kernel Filtering: Discarding benign system calls inside kernel space to eliminate ring buffer exhaustion, CPU context switching, and event loss.
    3. Declarative Kubernetes-Native Management: Managing TracingPolicy custom resources as code to integrate security controls cleanly into GitOps pipelines.

    For comprehensive protection, organizations can adopt a defense-in-depth posture: deploying Falco for broad behavioral auditing and alert notification, while placing Tetragon on critical production namespaces to enforce immediate process termination against active threats.
