    Single Point of Failure and Blast Radius: Spares vs Isolation Boundaries

    Count spares by what stops together, then draw the boundary


    Overview

    Add a second server and it is easy to believe the single point of failure is gone. But if the two servers use the same database and the same config and receive the same deploy, they stop as one. Adding machines does not remove the things that make them stop together.

    This post shows how to count redundancy by the unit that stops together rather than by the number of machines, and it separates adding spares from drawing boundaries. It then looks at why a bad deploy crosses those boundaries, and tests the distinction against two cases: an internal portal and a VPN server.

    How to read the examples

    The cases come from real operating experience, with the company, products and addresses generalized. The configs shown were written as examples and are not real production files. Addresses use documentation ranges, and the numbers in tables labeled as examples were chosen for explanation.


    Finding Single Points of Failure

    A single point of failure (SPOF) is a component with nothing to take its place, so the whole system stops when that one thing stops. The term is not limited to servers and network lines. The one database that takes writes, an authentication server every service depends on, and the only person who knows a procedure are all single points of failure. Getting a procedure out of one person’s head and into a document is covered in the runbook post.


    Stop Each Dependency in Turn

    The method is simple. Write down the path a single request takes and everything that path depends on, then assume each one has stopped. Include what rarely shows up on an architecture diagram. A config store, an image registry and certificate issuance stay out of sight until a restart or a deploy needs them.


    Dependency What happens when it stops Dependency type
    Load balancer Every request fails hard
    Database that takes writes Write requests fail hard
    Authentication server New logins are blocked. If services verify already issued tokens themselves, existing users carry on Depends on the implementation
    Cache Reads go straight to the database and get slower soft
    Recommendation API A default list is returned in its place soft
    An example made up for a typical web service.


    In networking, the hub of a hub-and-spoke layout is the classic single point of failure. The structure of each topology is laid out in the network topology post.


    Hard and Soft Dependencies

    The Availability page of AWS Well-Architected draws the line this way: a dependency is hard if its interruption translates directly into an interruption of the caller, and soft if the caller can compensate another way when it stops.

    The availability of hard dependencies multiplies. In the same page’s example, a system designed for 99.99% availability with a hard dependency on two independent systems, each at 99.99%, can theoretically reach 99.97%.

    99.99% × 99.99% × 99.99% = 99.97%

    This multiplication points to one more way of reducing single points of failure. Even without a spare, a dependency turned soft can no longer stop the whole system. The recommendation API in the table above has no spare and still is not a single point of failure. A dependency that only looks soft, like the cache, needs one more check, though: whether the database behind it can take the extra load when the cache is gone.

    The same page advises settling the availability you actually need first, because cost rises as availability does. Removing every single point of failure is not the goal. Once you have found them, choose which to remove and which to accept.


    Two Servers That Still Stop Together


    The Independence Assumption

    Availability with redundancy, from the AWS whitepaper Availability and Beyond, works the numbers for a component at 99% availability with two copies. The chance of both being down together is 1% × 1% = 0.01%, which gives 99.99% availability. That calculation holds only when the two copies are independent, and the whitepaper too speaks of putting spares on resources that fail independently.

    Once the copies share something, the calculation changes. The table below assumes two front-end servers using one database with 99.9% availability. Annual downtime is converted from the availability figure.


    Setup Calculation Availability Annual downtime
    1 server 99% 99% About 3 days 15 hours
    2 servers 1 − (1% × 1%) 99.99% About 52 minutes
    2 servers + shared database 99.99% × 99.9% About 99.89% About 9.6 hours
    More servers added Approaches 99.9% and never passes it Below 99.9% About 8 hours 45 minutes or more


    flowchart LR subgraph Pair["Front end: 99.99% as a pair"] S1["Server 1
    99%"] S2["Server 2
    99%"] end S1 --> DB[("Shared database
    99.9%")] S2 --> DB style DB fill:#fff59d

    The two branches of the example meet again at the shared database.


    However many front-end servers you add, overall availability cannot pass the availability of what they share.


    What Breaks Independence

    Shared dependencies are not always as visible as a database. The things that stop two servers together can be grouped like this.


    What is shared The event that stops both The question to ask
    Power, rack, switch A power problem, a switch failure Where are the two servers physically?
    Database, config store A failure of the shared dependency Where do the two branches meet on the diagram?
    Code and config A bad deploy, a bad config change How many machines change in one change?
    Remaining capacity A cascading failure, where survivors take on the stopped side's share and fall in turn Is the required capacity left after losing one unit?
    Failover mechanism A failure of the single load balancer or of whatever handles the switch If the failover mechanism stops, who fails over?


    The last row is easy to miss. Adding a spare brings a new failover mechanism with it, and that mechanism can become the next single point of failure.


    Count by the Unit That Stops Together

    The same whitepaper says to look at the unit of failure when deciding how many spares to have. Its example workload needs 10 Amazon EC2 instances to handle peak load. Put all 10 in one Availability Zone (AZ) and the entire AZ can stop together, so the unit is the AZ rather than one instance.

    In the table below, the second row was added for comparison and the rest are the whitepaper’s example.


    Setup Total instances Left after one AZ stops Are the required 10 left?
    10 in 1 AZ 10 0 No
    20 in 1 AZ 20 0 No
    10 each in 2 AZs 20 10 Yes
    5 each in 3 AZs 15 10 Yes


    Rows two and three have the same 20 instances, yet counted as spares they have zero and one. In row three, the extra 10 instances look like spares, but the real spare is one AZ. Row four uses one more AZ and five fewer instances and meets the same condition.

    More spares are not always better either. The whitepaper holds that for components at 99% availability or higher, going beyond three spares brings no noticeable gain for almost all workloads, so it recommends only as many as the required availability calls for.


    Spares and Boundaries Are Different Jobs

    Blast radius is the range of components and users that one failure, one bad deploy or one security breach can reach. AWS documents use scope of impact for the same idea.

    Adding a spare keeps things running through a failure. Drawing a boundary decides how far the failure spreads. Neither can stand in for the other. The table below is an example built to tell the two apart. Cells and AZs are explained further down.


    Setup Spare Boundary One server fails Bad deploy
    1 server No No Total outage Applied everywhere
    Several servers on the same version, load balancer Yes No Remaining servers handle it Applied everywhere
    Spread across AZs, deployed all at once Yes Facility boundary Remaining servers handle it Applied everywhere
    10 cells, 1 server per cell No Yes 10% of requests stop Deployed in turn, it can be stopped at one cell
    10 cells, several servers per cell Yes Yes Remaining servers handle it Deployed in turn, it can be stopped at one cell


    The second row is the setup people mean when they say “it’s redundant, so it’s safe.” The fourth row is divided up but has no spare. Neither one solves the other’s problem.


    AZ: A Boundary for Facility Failures

    According to REL10-BP01, AZs are locations physically separated so that they do not share disasters such as fires, floods and tornadoes. Each AZ also has its own power, mechanical services and network connectivity.

    What this boundary contains is a failure in one facility. Deploy the same code and config to every AZ at once, and a bad deploy goes straight across the AZ boundary. If a service spanning several AZs shares a database or config store, a failure there spreads to all of them.


    Cell: A Boundary Inside the Workload

    REL10-BP03 draws its analogy from a ship’s bulkheads, which keep hull damage inside one compartment. AWS’s guide to cell-based architecture describes the cell structure as bringing the fault isolation concepts used for AZs and Regions down to the workload.

    A cell is one independent copy of the workload. It shares no state with other cells and handles only part of all requests. In the document’s example, with 10 cells serving 100 requests, a failure in one cell leaves 90% of all requests unaffected.

    flowchart TD R["Router layer"] --> C1["Cell 1: failed"] R --> C2["Cell 2"] R --> C3["Cells 3 to 9"] R --> C10["Cell 10"] classDef fail fill:#ffebee,stroke:#c62828,stroke-width:2px,color:#b71c1c; classDef ok fill:#e8f5e9,stroke:#2e7d32,stroke-width:2px,color:#1b5e20; class C1 fail; class C2,C3,C10 ok; style R fill:#fff59d

    The document's 10-cell example with one cell down.


    Four issues in implementing cells
    • Partition key: pick a value available on every request, such as a customer ID, that keeps interaction between cells to a minimum.
    • Router layer: this layer is shared by the cells, so it cannot be divided the way they are. Keep it simple, with no complex business logic.
    • Cell size: set a maximum size by testing. When the workload grows, add cells rather than growing them.
    • Calls between cells: the more of them there are, the more cells depend on each other and the less isolation you get.


    The router layer is a shared dependency that remains after the boundary is drawn. Creating boundaries does not make every shared dependency disappear, and what counts is how simple you keep the ones that remain.

    AWS also calls this structure bulkhead architecture. The bulkhead that appears alongside circuit breakers, where the caller partitions resources such as thread pools, shares only the metaphor.


    Shuffle Sharding: Finer Division from the Same Resources

    AWS’s article on shuffle sharding explains it with 8 workers. With no shards, all 8 are used together, and a problem caused by one customer spreads to the whole service. Group them in pairs to form 4 shards, and the impact drops to 25%.

    Shuffle sharding gives each customer a different combination of workers instead of a fixed group. There are 28 ways to choose 2 workers out of 8.

    worker    1  2  3  4  5  6  7  8
A         x        x
B         x                    x
C                  x     x

    Even if customer A breaks workers 1 and 4, customer B can still get a response from worker 8, and customer C from worker 6. Different combinations overlap on at most one worker.


    Method Units handed out Impact of one problem Precondition
    No shards 1, the whole fleet 100% None
    Fixed shards of 2 workers 4 25% None
    Shuffle sharding 28 combinations 1/28, about 3.6% The caller must be able to send a retry to a different worker


    The precondition in the last row matters. Retries have to work for the impact customers see to drop to 1/28, and two workers still break either way.


    Deploys That Cross the Boundary


    Outages That Come from Change

    Chapter 1 of the Google SRE Book says about 70% of outages come from changes to a live system. The responses it names are progressive rollouts, quick and accurate detection of problems, and safe rollback. REL10-BP03 also lists deploying to all cells at once as an anti-pattern.

    From the point of view of the multiplication earlier, two servers that received the same version are not independent with respect to that change. Both carry the same bug, so a spare that takes over fails in the same place. Two servers do not stop a bad deploy.


    What a maxUnavailable Percentage Means in Pods

    A Kubernetes rolling update has numbers that look like a boundary. According to the Deployment documentation, maxUnavailable and maxSurge both default to 25%, and when a percentage is converted to a count, maxUnavailable rounds down and maxSurge rounds up. With the defaults, Pod counts work out as follows.


    replicas maxUnavailable 25% maxSurge 25% Minimum available Pods during rollout Maximum Pods during rollout
    1 0 1 1 2
    2 0 1 2 3
    3 0 1 3 4
    4 1 1 3 5
    20 5 5 15 25
    1,000 250 250 750 1,250


    In the top three rows, rounding down means no Pod comes down first. At the same percentage, the number going down at once grows as you move down the table.

    What matters here is what kind of number this is.

    maxUnavailable is a cap on how many Pods go down at once, not a cap on how far the new version reaches.

    Change 1,000 Pods at 25% or one at a time, and when the rollout ends all 1,000 run the new version. The value sets the speed. It is not a boundary.


    Rollouts that stop by themselves also need separating from rollouts that do not.

    • A version whose new Pods cannot become Ready: the Deployment controller stops scaling up the new ReplicaSet, so the rollout stalls. Up to maxUnavailable Pods may already be down by then, though, and the stall is only recorded in status. Nothing is rolled back.
    • A version that passes readiness but behaves wrongly: nothing stops it, and it spreads everywhere.

    PodDisruptionBudget is not the answer here either. According to the Disruptions documentation, workload resources such as Deployment are not limited by PDBs during a rolling update. A PDB deals with voluntary disruptions such as a node drain.


    Deploy in Units That Match the Boundary

    To keep a deploy from crossing a boundary, the deploy unit has to match the boundary. AWS’s Automating safe, hands-off deployments groups deployments into waves of increasing size. Each wave starts with a one-box stage that serves 10% of requests or less, and the first wave deploys to only one AZ or one cell at a time. Bake time is set aside to watch before moving to the next stage.

    The same thinking carries over to smaller environments. The table below is an example made up for a service spread across two AZs.


    Stage Deploy scope Condition for moving on
    1 A canary taking part of the traffic Error rate and latency are within the criteria
    2 All of one AZ Metrics hold for a set period
    3 The remaining AZ None


    Stages without a condition for moving on do not work as boundaries, because the deploy moves on before anyone notices something is wrong.

    Code is not the only thing that gets deployed. A config change reaches every replica by the same path, and the next case is one of those.


    Case 1: Seven Internal Apps Behind One Entrance

    Internal apps and operations services had each implemented their own authentication, and that was once consolidated into one portal. A new service only had to register its config to join, so the reason for consolidating was clear. But the portal became the only entrance to the 7 apps it proxied. The portal is a hard dependency of every one of them.


    Every Deploy Cut All Seven Apps

    The early portal kept sessions in an in-memory map on the server. Sessions lived only inside that process, so replicas could not be added, and it was tied to replicas: 1 and the Recreate strategy. Recreate takes all existing Pods down before creating new ones.

    As a result, every portal deploy cut all 7 apps at once. Editing even one comment line in the config file changed the ConfigMap hash and triggered a rollout, the sessions in memory vanished, and everyone was logged out. The apps had not changed at all, and the edit was a comment with no bearing on behavior, yet the blast radius was all 7 apps and every user. There is no record of how long the cuts lasted, though.

    On the earlier table of spares and boundaries, this is the first row, with neither. With sessions in memory, a spare was not even possible. Adding replicas first would not have solved it.


    Moving Sessions Off the Server

    So sessions came off the server before the replica count went up. The claims and the original id_token are compressed and encrypted with AES-256-GCM, and that value itself becomes the cookie. Whichever Pod receives a request can decrypt it with the same key, so Pods have no state to hand over to each other.

    Every Pod has to share the encryption key, so with no key the process fails at startup instead of falling back to a random one. A Pod started with a random key cannot decrypt cookies made by the other Pods, and users get logged out depending on which Pod their request reaches.

    Only with the state gone could availability settings go on top. The manifest below is an example written to show the applied values, not the real one.

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: portal
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: portal
  template:
    metadata:
      labels:
        app: portal
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app: portal
      containers:
        - name: portal
          image: registry.example.com/portal:1.0.0
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: portal
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: portal

    maxUnavailable: 0 and maxSurge: 1 mean an old Pod comes down only after a new Pod is Ready. Node spread is soft because with a hard rule, when Pods reach 3 during a rollout and nodes run short, the new Pod stays Pending and the deploy never finishes. ScheduleAnyway in the example is one way to get a soft spread. According to the topology spread documentation, it schedules the Pod even when the constraint cannot be met, while preferring nodes that keep the skew small.


    A Test to Stop the Config Sliding Back

    A one-line value change returns this config to the earlier setup, and the regression does not show until the next deploy. So make test gained a test that inspects replicas, strategy and the PDB among these values and checks whether the setup has gone back to a single point of failure. A spare is not something you build once and forget, and you need something that tells you when it has gone.


    The Price, and the Blast Radius That Remains

    The price of going stateless is that the server cannot forcibly end a session. The expiry time is inside the encrypted content, so the server cannot revoke a cookie it has already issued. Logging out expires the cookie and also ends the SSO session on the authentication server, so getting back in takes a new login, but the issued cookie itself stays valid until it expires. If immediate invalidation becomes necessary, the next step is a revocation list in an external store, and that brings back the state store dependency just removed. No such requirement exists yet, so there is no store.

    flowchart TB subgraph Early["Early portal: no spare, no boundary"] A1["One Pod, Recreate
    sessions in server memory"] --> A2["7 apps"] end subgraph Now["Stateless portal: a spare, still no boundary"] K["Same code, config and encryption key"] -.-> B1["Pod 1"] K -.-> B2["Pod 2"] B1 --> B3["7 apps"] B2 --> B3 end style A1 fill:#ffebee style K fill:#fff59d

    The 7 apps are still behind one portal, and both Pods use the same code, config and encryption key.


    What this work produced is a spare. Deploys no longer cut all 7 apps together. It did not produce a boundary. If a bad version that passes readiness is deployed, both Pods move to it, and if the defect is in the authentication or proxy path, all 7 apps are affected together. replicas: 2 is not a setting that prevents that.


    Case 2: Two VPN Servers and When the Client Finds Out


    Remote Access Hanging on One Server

    OpenVPN on a single physical server handled all remote access to the internal network. There was no alternate way in. The PKI, holding the CA and the issuance history, lived only on that server and was not being backed up. The install script was idempotent and preserved an existing PKI, but that only helps when it is rerun on the same server. Lose the server and every user certificate has to be reissued. Nothing alerted on the tunnel itself either, so unless the server’s general resource alerts fired, nobody would know right away that the VPN had stopped.


    Moving to keepalived Active-Standby

    Servers A and B were tied together with keepalived active-standby, and the destination of the inbound path changed from the server’s address to a VIP. OpenVPN runs on both servers all the time, and whichever one holds the VIP receives the packets.

    flowchart LR C["OpenVPN clients"] --> R["Upstream router
    one public address"] R --> V(["VIP group
    moves as one"]) V -->|"active"| A["Server A
    OpenVPN always running"] V -.->|"standby"| B["Server B
    OpenVPN always running"] B -.->|"pulls PKI every minute
    from the VIP side"| A style R fill:#fff59d

    The generalized setup. The highlighted router comes back later in this case.


    Before the cutover, the first thing measured was whether the upstream router follows a VIP move right away. With packets going to a test port at 0.5-second intervals while the VIP moved, the standby server received packets 0.16 seconds after the gratuitous ARP, and none of the 154 packets were lost or duplicated.

    What had to move together was treated as one bundle. A site-to-site tunnel exchanged traffic with OpenVPN inside the same server, and if the two moved separately that forwarding path would break, so they went into the same VIP group. Deciding the unit of failover is the same job as deciding the unit that stops together.

    The configs below are examples written to show the setup. The addresses come from a documentation range, and these are not real config files.

    # Example keepalived.conf for server A. Server B differs in priority and addresses.
vrrp_instance VPN {
    state BACKUP
    interface eth0
    virtual_router_id 51
    priority 150
    advert_int 1
    nopreempt
    unicast_src_ip 192.0.2.11
    unicast_peer {
        192.0.2.12
    }
    virtual_ipaddress {
        192.0.2.10/32
    }
}

    # Example excerpt from an OpenVPN server.conf
multihome
keepalive 10 60

    nopreempt keeps a higher-priority server from taking the VIP back when it returns, and according to the keepalived configuration documentation, it works only if the initial state is not MASTER. multihome is an OpenVPN option that makes a server with several addresses send UDP replies from the address the client connected to. Without it, the source of a reply becomes the server’s default address and no longer matches the router’s port-forwarding connection tracking.


    Syncing the Standby, a New Dependency

    Adding a standby server was not the end of it. The two servers’ PKIs must match for the standby to act as a spare, and the mechanism that keeps them matching is itself a new source of failure.


    New risk What guards against it
    The standby lacks the latest PKI The standby pulls the PKI from the VIP side every minute. After the first replication, the hashes of the PKI files were confirmed to match
    An empty source wipes the standby's PKI through a sync that deletes The data is received into a temporary directory and applied only after confirming that the CA certificate, the issued list and the revocation list are present
    The next sync erases anything issued or revoked on the standby A server without the VIP refuses issuing and revoking. Issuing was confirmed to be refused on the standby
    The install script creates a new CA on a server with no CA, and when that server goes active nobody can connect If HA settings exist and the CA certificate does not, the script stops rather than create one
    Both servers go active at once Unicast VRRP and nopreempt were meant to reduce the chance, but they cannot prevent it if VRRP packets between the two servers are cut


    Since the sync runs every minute, anything issued or revoked after the last sync can, by design, be missing from the standby right after a failover.


    The Numbers from the Failover Drill

    The drill stopped keepalived on server A to move the VIP to server B. The results differed widely by path.


    Path How it was measured Result
    From an internal node through the VIP over a static route Probe at 0.5-second intervals 1 failure, within 1.5 seconds
    From another server to an address in the same VIP group Probe at 0.5-second intervals 0 failures
    OpenVPN client Client screen and reconnect time Kept showing "connected," then reconnected after 42 seconds
    OpenVPN client when moving back to server A Reconnect time Reconnected after 8 seconds


    The routing path was back within 1.5 seconds, while the user sat cut off for 42 seconds looking at a “connected” status. The 8 seconds on the way back was a case of the client trying to reconnect right away. A wobble in the network path looks like the trigger, but the cause was not established. The interruption a user experiences ranges from a few seconds to about 60 seconds at most, depending on the case.

    How far these results hold

    This drill shut keepalived down cleanly and did not power off a server. The VIP failover time for a server that halts suddenly was estimated at design time as 3 to 4 seconds, three advert_int intervals plus skew. It is an estimate and was not measured in this drill.


    Time That More Servers Do Not Reduce

    The 42 seconds is not how long a server took to recover. It is how long the client took to reconnect. At the time, this was explained with ping-restart, and the sequence written down then was as follows.

    1. The VIP moves to server B, so the client’s packets arrive at server B
    2. OpenVPN on server A is still alive, so it sends no shutdown notice
    3. Server B discards packets for a session it does not know
    4. The client gets no reply, waits until the ping-restart time has passed, and then reconnects

    According to the OpenVPN manual, keepalive 10 60 on the server pushes ping 10 and ping-restart 60 to the client. That means restarting after 60 seconds with no packets of any kind from the peer, so about 60 seconds is the upper limit.

    The explanation does not fit the measurement

    The server sends a ping once it has gone more than 10 seconds without sending a packet, so this timer alone would not restart the client until about 50 seconds after the switch. The actual reconnect came at 42 seconds. That does not match the explanation above, and the cause of the difference has not been established.


    Lowering the value lowers the upper limit too, but at a cost. With 30 seconds, users on unstable lines were expected to reconnect more often, so 60 stayed.

    Going to three servers would not shorten this time. Spares shorten the time a server failover takes, not the time until the client learns of it. So talking about this setup’s recovery time starts with deciding which moment on which path is the reference. The way one incident gives different values depending on where the start and end are placed is covered in the MTTR measurement post.


    A Measuring Tool Tied to What It Measures

    The drill taught one more lesson. The PC of the operator running it was in the office, yet connected to the internal network through a full-tunnel VPN, and that ssh session froze for the same 42 seconds. The tool directing the drill was tied to the drill’s target. Probes should run from a host that does not go through the VPN and write their results to a file.


    What Still Stops Together

    Two servers did not solve everything. Both sit behind the same upstream router and the same public address, so if that router stops, there is no way in from outside wherever the VIP is. The spare in this setup has only been counted up to the unit of one server.

    Alerts on keepalived state changes and on sync failures were also still follow-up items when this drill was recorded. As of that point, nothing would tell a person right away that a failover had happened or that sync had stopped, and a stale PKI on the standby might only come to light after a failover.


    Questions for Checking a Design

    The table below collects the questions used in this post. If you know from a real outage which group stopped together, look for the answer in that record first. How to keep those records is covered in the postmortem writing guide.


    Question The risky answer Next action
    When this dependency stops, what does the caller do? It stops too Add a spare, or make the dependency soft
    By what unit were spares counted? Only by instance count Recount by the unit that stops together
    Where do the branches of the path meet again? At one database, config store or router Calculate the overall upper limit from the availability at that point
    Is the required capacity left after losing one unit? The survivors cannot handle it Rework the capacity per unit
    What do users see when one machine goes down? Their sessions are cut Move the state off the server
    When do you find out that sync has stopped? After a failover has happened Put an alert on sync status
    How far does one bad deploy reach? Everywhere Deploy in units that match the boundary
    Is there a stop condition between stages? No Set metrics and a wait time as conditions
    What happens when one comment line is edited? A full restart and a session reset Treat config changes as deploys too
    After a failover finishes, when does the client know? Only when a timer runs out Measure by path and write down the user-facing time
    Does the drill tooling avoid passing through the drill target? It uses the same path Put probes outside the path
    When do you find out that the config has gone back to the old setup? At the next deploy Block it with a test


    Conclusion

    Count spares by the unit that stops together, not by the number of machines. Two machines on the same power, the same database or the same version are no different from one machine when that shared part has a problem. However many front-end servers you add, overall availability cannot pass that of what they share.

    Spares and boundaries are different jobs. Spares keep things running through a failure, and boundaries set how far it spreads. The internal portal gained a spare by moving sessions off the server, but seven apps still sit behind one entrance, and a maxUnavailable percentage sets the speed, not how far a new version reaches. To contain a bad deploy as well, the deploy unit has to match the boundary.

    Some time does not shrink with spares. In the VPN failover drill, the routing path was back within 1.5 seconds, but the client reconnected only after 42. When describing what redundancy achieves, measure the server failover time and the recovery users actually experience separately.
