    Apache Kafka on Kubernetes Advanced

    Production-grade Kafka deployments with security, performance tuning, and Kafka Connect


    Overview

    In the Basics post, we covered Kafka fundamentals and deployed a simple cluster with Strimzi. This post takes the next step into production-grade Kafka on Kubernetes.

    This guide covers security hardening, external access patterns, performance tuning, Kafka Connect for data integration, Schema Registry for data governance, and disaster recovery strategies.


    Security: TLS Encryption and Authentication

    In production, all Kafka communication should be encrypted and authenticated. Strimzi makes this straightforward with built-in TLS certificate management.


    TLS Encryption

    Strimzi automatically generates and manages TLS certificates using its internal Certificate Authority (CA).

    # kafka-tls.yaml
apiVersion: kafka.strimzi.io/v1beta2
kind: Kafka
metadata:
  name: production-cluster
  namespace: kafka
spec:
  kafka:
    version: 3.8.0
    replicas: 3
    listeners:
      - name: tls
        port: 9093
        type: internal
        tls: true
        authentication:
          type: tls
      - name: external
        port: 9094
        type: loadbalancer
        tls: true
        authentication:
          type: tls
    config:
      offsets.topic.replication.factor: 3
      transaction.state.log.replication.factor: 3
      transaction.state.log.min.isr: 2
      ssl.cipher.suites: "TLS_AES_256_GCM_SHA384,TLS_AES_128_GCM_SHA256"
      ssl.enabled.protocols: "TLSv1.3,TLSv1.2"
      ssl.protocol: "TLSv1.3"
    storage:
      type: jbod
      volumes:
        - id: 0
          type: persistent-claim
          size: 100Gi
          class: fast-ssd
          deleteClaim: false
  zookeeper:
    replicas: 3
    storage:
      type: persistent-claim
      size: 20Gi
      class: fast-ssd
  entityOperator:
    topicOperator: {}
    userOperator: {}


    SASL/SCRAM Authentication

    For username/password-based authentication, use SASL/SCRAM.

    # kafka-sasl-listener.yaml (add to spec.kafka.listeners)
listeners:
  - name: sasl
    port: 9094
    type: internal
    tls: true
    authentication:
      type: scram-sha-512

    Create a KafkaUser with SCRAM credentials.

    # kafka-user-scram.yaml
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaUser
metadata:
  name: app-producer
  namespace: kafka
  labels:
    strimzi.io/cluster: production-cluster
spec:
  authentication:
    type: scram-sha-512
  authorization:
    type: simple
    acls:
      - resource:
          type: topic
          name: orders
          patternType: literal
        operations:
          - Write
          - Describe
        host: "*"
      - resource:
          type: topic
          name: orders
          patternType: literal
        operations:
          - Read
          - Describe
        host: "*"
      - resource:
          type: group
          name: order-processors
          patternType: literal
        operations:
          - Read
        host: "*"

    # After applying, credentials are stored in a Kubernetes Secret
kubectl get secret app-producer -n kafka -o jsonpath='{.data.password}' | base64 -d


    TLS Client Authentication (mTLS)

    For stronger authentication, use mutual TLS where both client and server verify certificates.

    # kafka-user-tls.yaml
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaUser
metadata:
  name: app-consumer
  namespace: kafka
  labels:
    strimzi.io/cluster: production-cluster
spec:
  authentication:
    type: tls
  authorization:
    type: simple
    acls:
      - resource:
          type: topic
          name: "events-*"
          patternType: prefix
        operations:
          - Read
          - Describe
        host: "*"
      - resource:
          type: group
          name: "event-processor-*"
          patternType: prefix
        operations:
          - Read
        host: "*"


    External Access Patterns

    Applications outside the Kubernetes cluster often need to connect to Kafka. Strimzi supports several external access methods.


    Access Methods Comparison

    Method Use Case Pros Cons
    LoadBalancer Cloud environments (AWS, GCP, Azure) Simple setup, direct TCP access One LB per broker (costly), cloud-specific
    NodePort On-premises, development Works anywhere, no cloud dependency Port range 30000-32767, firewall config needed
    Ingress HTTP-based clients (REST Proxy) Shared entry point, SSL termination Not native Kafka protocol, extra hop
    Route (OpenShift) OpenShift clusters Native OpenShift integration OpenShift-specific


    LoadBalancer Configuration

    # External access via LoadBalancer
listeners:
  - name: external
    port: 9094
    type: loadbalancer
    tls: true
    authentication:
      type: tls
    configuration:
      bootstrap:
        annotations:
          service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
          service.beta.kubernetes.io/aws-load-balancer-internal: "false"
      brokers:
        - broker: 0
          advertisedHost: kafka-broker-0.example.com
        - broker: 1
          advertisedHost: kafka-broker-1.example.com
        - broker: 2
          advertisedHost: kafka-broker-2.example.com


    NodePort Configuration

    # External access via NodePort
listeners:
  - name: external
    port: 9094
    type: nodeport
    tls: true
    authentication:
      type: tls
    configuration:
      bootstrap:
        nodePort: 32100
      brokers:
        - broker: 0
          nodePort: 32000
        - broker: 1
          nodePort: 32001
        - broker: 2
          nodePort: 32002


    Client Connection Example

    # Python client connecting to external Kafka with SASL/SCRAM
from confluent_kafka import Producer

config = {
    'bootstrap.servers': 'kafka-broker-0.example.com:9094',
    'security.protocol': 'SASL_SSL',
    'sasl.mechanism': 'SCRAM-SHA-512',
    'sasl.username': 'app-producer',
    'sasl.password': '<password-from-secret>',
    'ssl.ca.location': '/path/to/ca.crt',
}

producer = Producer(config)

producer.produce('orders', key='order-123', value='{"item": "widget", "qty": 5}')
producer.flush()


    Performance Tuning

    Optimizing Kafka on Kubernetes requires tuning at multiple layers: Kafka broker configuration, JVM settings, Kubernetes resources, and storage.


    Broker Configuration Tuning

    # Performance-optimized Kafka configuration
spec:
  kafka:
    config:
      # Replication
      num.replica.fetchers: 4
      replica.fetch.min.bytes: 1
      replica.fetch.max.bytes: 10485760     # 10 MB

      # Log settings
      num.partitions: 12
      log.retention.hours: 168              # 7 days
      log.retention.bytes: -1               # No size limit
      log.segment.bytes: 1073741824         # 1 GB
      log.cleanup.policy: delete

      # Network and I/O threads
      num.network.threads: 8
      num.io.threads: 16
      socket.send.buffer.bytes: 102400
      socket.receive.buffer.bytes: 102400
      socket.request.max.bytes: 104857600   # 100 MB

      # Producer/Consumer performance
      message.max.bytes: 10485760           # 10 MB max message size
      compression.type: lz4


    JVM and Resource Tuning

    spec:
  kafka:
    jvmOptions:
      -Xms: 4096m
      -Xmx: 4096m
      gcLoggingEnabled: true
      javaSystemProperties:
        - name: com.sun.management.jmxremote
          value: "true"
    resources:
      requests:
        memory: 6Gi
        cpu: "2"
      limits:
        memory: 8Gi
        cpu: "4"
    template:
      pod:
        affinity:
          podAntiAffinity:
            requiredDuringSchedulingIgnoredDuringExecution:
              - labelSelector:
                  matchExpressions:
                    - key: strimzi.io/name
                      operator: In
                      values:
                        - production-cluster-kafka
                topologyKey: kubernetes.io/hostname
    JVM Heap Sizing Rules
    • Set -Xms equal to -Xmx — Prevents GC overhead from heap resizing
    • Do not exceed 6 GB heap — Kafka uses OS page cache heavily; leave memory for that
    • Container memory = heap + 2-3 GB — Account for off-heap memory and OS page cache
    • Use G1GC — Default in modern JVMs, well-suited for Kafka's workload


    Storage Optimization

    # Use dedicated StorageClass with high IOPS
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: kafka-storage
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iops: "6000"
  throughput: "400"
  encrypted: "true"
volumeBindingMode: WaitForFirstConsumer

---

  kafka:
    storage:
      type: jbod

    Kafka Connect: Data Integration

    Kafka Connect is a framework for streaming data between Kafka and external systems (databases, search indexes, file systems, etc.) without writing custom code.


    Deploy Kafka Connect Cluster

    # kafka-connect.yaml
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaConnect
metadata:
  name: my-connect-cluster
  namespace: kafka
  annotations:
    strimzi.io/use-connector-resources: "true"
spec:
  version: 3.8.0
  replicas: 2
  bootstrapServers: production-cluster-kafka-bootstrap:9093
  tls:
    trustedCertificates:
      - secretName: production-cluster-cluster-ca-cert
        pattern: "*.crt"
  config:
    group.id: connect-cluster
    offset.storage.topic: connect-offsets
    config.storage.topic: connect-configs
    status.storage.topic: connect-status
    offset.storage.replication.factor: 3
    config.storage.replication.factor: 3
    status.storage.replication.factor: 3
    key.converter: org.apache.kafka.connect.json.JsonConverter
    value.converter: org.apache.kafka.connect.json.JsonConverter
    key.converter.schemas.enable: true
    value.converter.schemas.enable: true
  resources:
    requests:
      memory: 2Gi
      cpu: "1"
    limits:
      memory: 4Gi
      cpu: "2"
  build:
    output:
      type: docker
      image: my-registry.io/kafka-connect:latest
      pushSecret: registry-credentials
    plugins:
      - name: debezium-postgres
        artifacts:
          - type: tgz
            url: https://repo1.maven.org/maven2/io/debezium/debezium-connector-postgres/2.7.3.Final/debezium-connector-postgres-2.7.3.Final-plugin.tar.gz
      - name: jdbc-sink
        artifacts:
          - type: jar
            url: https://packages.confluent.io/maven/io/confluent/kafka-connect-jdbc/10.7.6/kafka-connect-jdbc-10.7.6.jar
      - name: elasticsearch-sink
        artifacts:
          - type: zip
            url: https://d2p6pa21dvn84.cloudfront.net/api/plugins/confluentinc/kafka-connect-elasticsearch/versions/14.1.1/confluentinc-kafka-connect-elasticsearch-14.1.1.zip

    Schema Registry

    Schema Registry enforces data contracts between producers and consumers, preventing breaking changes and ensuring data compatibility.


    Deploy Schema Registry with Strimzi

    # schema-registry.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: schema-registry
  namespace: kafka
spec:
  replicas: 2
  selector:
    matchLabels:
      app: schema-registry
  template:
    metadata:
      labels:
        app: schema-registry
    spec:
      containers:
        - name: schema-registry
          image: confluentinc/cp-schema-registry:7.7.1
          ports:
            - containerPort: 8081
          env:
            - name: SCHEMA_REGISTRY_HOST_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            - name: SCHEMA_REGISTRY_KAFKASTORE_BOOTSTRAP_SERVERS
              value: "production-cluster-kafka-bootstrap:9092"
            - name: SCHEMA_REGISTRY_LISTENERS
              value: "http://0.0.0.0:8081"
            - name: SCHEMA_REGISTRY_SCHEMA_COMPATIBILITY_LEVEL
              value: "BACKWARD"
          resources:
            requests:
              memory: 512Mi
              cpu: 250m
            limits:
              memory: 1Gi
              cpu: 500m
---
apiVersion: v1
kind: Service
metadata:
  name: schema-registry
  namespace: kafka
spec:
  selector:
    app: schema-registry
  ports:
    - port: 8081
      targetPort: 8081


    Using Avro with Schema Registry

    from confluent_kafka import SerializingProducer
from confluent_kafka.schema_registry import SchemaRegistryClient
from confluent_kafka.schema_registry.avro import AvroSerializer

# Schema Registry client
schema_registry_conf = {'url': 'http://schema-registry.kafka.svc:8081'}
schema_registry_client = SchemaRegistryClient(schema_registry_conf)

# Avro schema
order_schema = """
{
  "type": "record",
  "name": "Order",
  "namespace": "com.example",
  "fields": [
    {"name": "order_id", "type": "string"},
    {"name": "customer_id", "type": "string"},
    {"name": "total_amount", "type": "double"},
    {"name": "status", "type": {"type": "enum", "name": "Status",
      "symbols": ["PENDING", "CONFIRMED", "SHIPPED", "DELIVERED"]}},
    {"name": "created_at", "type": "long", "logicalType": "timestamp-millis"}
  ]
}
"""

avro_serializer = AvroSerializer(schema_registry_client, order_schema)

producer_conf = {
    'bootstrap.servers': 'production-cluster-kafka-bootstrap:9092',
    'value.serializer': avro_serializer,
}

producer = SerializingProducer(producer_conf)
producer.produce(
    topic='orders',
    value={
        'order_id': 'ORD-001',
        'customer_id': 'CUST-123',
        'total_amount': 99.99,
        'status': 'PENDING',
        'created_at': 1729900800000,
    }
)
producer.flush()


    Compatibility Modes

    Mode Rule
    BACKWARD New schema can read data written by the old schema. Can delete fields, add optional fields.
    FORWARD Old schema can read data written by the new schema. Can add fields, delete optional fields.
    FULL Both BACKWARD and FORWARD compatible. Only add/delete optional fields.
    NONE No compatibility checks. Not recommended for production.

    MirrorMaker 2 (Cross-Cluster Replication)

    Replicate data between Kafka clusters for disaster recovery or geo-distribution.

    # kafka-mirror.yaml
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaMirrorMaker2
metadata:
  name: dr-mirror
  namespace: kafka
spec:
  version: 3.8.0
  replicas: 2
  connectCluster: target-cluster
  clusters:
    - alias: source-cluster
      bootstrapServers: source-kafka-bootstrap.us-east-1.svc:9093
      tls:
        trustedCertificates:
          - secretName: source-cluster-ca-cert
            pattern: "*.crt"
    - alias: target-cluster
      bootstrapServers: target-kafka-bootstrap.eu-west-1.svc:9093
      tls:
        trustedCertificates:
          - secretName: target-cluster-ca-cert
            pattern: "*.crt"
      config:
        config.storage.replication.factor: 3
        offset.storage.replication.factor: 3
        status.storage.replication.factor: 3
  mirrors:
    - sourceCluster: source-cluster
      targetCluster: target-cluster
      sourceConnector:
        tasksMax: 4
        config:
          replication.factor: 3
          offset-syncs.topic.replication.factor: 3
          sync.topic.acls.enabled: "false"
          refresh.topics.interval.seconds: 30
      checkpointConnector:
        tasksMax: 1
        config:
          checkpoints.topic.replication.factor: 3
          sync.group.offsets.enabled: "true"
      topicsPattern: "orders.*|events.*|customers.*"
      groupsPattern: ".*"

    DR Best Practices
    • Use rack awareness — Spread replicas across AZs with rack.topologyKey
    • Set min.insync.replicas = 2 — Ensure at least 2 replicas acknowledge writes
    • MirrorMaker 2 for cross-region — Active-passive or active-active replication
    • GitOps for configurations — Store all Kafka CRDs in version control
    • PV reclaim policy = Retain — Prevent accidental data loss on PVC deletion

    Key Points

    Apache Kafka on Kubernetes Advanced Summary
    • Security
      - Enable TLS encryption for all listeners in production
      - Use SASL/SCRAM or mTLS for authentication with fine-grained ACLs
      - Strimzi automates certificate lifecycle management
    • Performance
      - Tune broker threads, JVM heap (max 6 GB), and use high-IOPS storage
      - Use pod anti-affinity to spread brokers across nodes/zones
      - Benchmark with kafka-producer-perf-test before production launch
    • Data Integration
      - Kafka Connect eliminates custom integration code
      - Debezium CDC captures database changes in real-time
      - Schema Registry enforces data contracts between services
    • Reliability
      - Multi-AZ deployment with rack awareness for HA
      - MirrorMaker 2 for cross-cluster disaster recovery
      - Cruise Control for automated partition rebalancing


    Conclusion

    Running Apache Kafka in production on Kubernetes is a well-proven pattern, but it requires careful attention to security, performance, and operational resilience. The Strimzi operator handles much of the complexity, but understanding the underlying mechanisms is essential for troubleshooting and optimization.

    The key takeaways for production Kafka on Kubernetes are: encrypt everything with TLS, authenticate every client, tune JVM and storage for your workload, use Kafka Connect instead of custom integrations, enforce schemas with Schema Registry, and plan for disaster recovery from day one.
