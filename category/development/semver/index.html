    Semantic Versioning (SemVer) Complete Guide: Version Numbers That Make Sense

    Understanding MAJOR.MINOR.PATCH versioning for reliable software releases


    Overview

    Semantic Versioning (SemVer) is a versioning scheme that helps manage software versions meaningfully.

    Rather than arbitrary number sequences, SemVer assigns meaning to version numbers, allowing both users and developers to easily understand the scope of changes.


    SemVer Format

    MAJOR.MINOR.PATCH

    Components:

    • MAJOR: Incremented for incompatible API changes
    • MINOR: Incremented for backward-compatible new features
    • PATCH: Incremented for backward-compatible bug fixes


    These rules maintain version consistency while providing a reliable contract between teams and library consumers.

    Additionally, pre-release versions (like alpha, beta, rc) and build metadata (like +build) clearly express various states during development.


    What is Semantic Versioning?

    Semantic Versioning (SemVer) is a versioning scheme used to assign meaningful version numbers to software releases. It helps developers and users understand changes in new releases and their potential impact on projects.


    Core Philosophy

    Version as Communication:

    Version Number = Promise to Users

1.0.0 → 1.0.1 : "Your code won't break"
1.0.0 → 1.1.0 : "New features, but still compatible"
1.0.0 → 2.0.0 : "Breaking changes - read migration guide!"


    SemVer Format Explained


    Basic Structure

    MAJOR.MINOR.PATCH

Example: 2.4.7
  │   │   │
  │   │   └─ PATCH version (bug fixes)
  │   └───── MINOR version (new features)
  └───────── MAJOR version (breaking changes)


    Component Details


    MAJOR Version

    When to increment:

    • Incompatible API changes
    • Removed functionality
    • Changed behavior of existing features

    Examples:

    v1.5.3 → v2.0.0

Changes:
- Removed deprecated `oldMethod()`
- Changed `getData()` return type from Array to Object
- Renamed configuration keys

    Impact: Users must update their code


    MINOR Version

    When to increment:

    • New backward-compatible functionality
    • Deprecation of existing functionality (but still works)
    • Substantial new features in private code

    Examples:

    v1.5.3 → v1.6.0

Changes:
+ Added `newMethod()` 
+ Added optional parameter to `existingMethod(param?)`
~ Deprecated `oldMethod()` (still works, will remove in v2.0.0)

    Impact: Users can upgrade safely


    PATCH Version

    When to increment:

    • Backward-compatible bug fixes
    • Security patches
    • Performance improvements (no API changes)

    Examples:

    v1.5.3 → v1.5.4

Changes:
- Fixed null pointer exception in `processData()`
- Corrected calculation in `computeTotal()`
- Security patch for XSS vulnerability

    Impact: Users should upgrade immediately


    Key Concepts


    1. Backward Compatibility

    Understanding Compatibility:

    Version Change Compatible? Can Break? Action Required
    PATCH (1.0.0 → 1.0.1) ✅ Yes ❌ No Update safely
    MINOR (1.0.0 → 1.1.0) ✅ Yes ❌ No Update safely
    MAJOR (1.0.0 → 2.0.0) ❌ No ✅ Yes Review changes, update code


    Example: API Evolution:

    // Version 1.0.0
class API {
  getData() {
    return [1, 2, 3];
  }
}

// Version 1.1.0 (MINOR - backward compatible)
class API {
  getData() {
    return [1, 2, 3];
  }
  
  getDataWithMetadata() {  // New method, old one still works
    return {
      data: [1, 2, 3],
      timestamp: Date.now()
    };
  }
}

// Version 2.0.0 (MAJOR - breaking change)
class API {
  getData() {
    return {              // Changed return type!
      data: [1, 2, 3],
      timestamp: Date.now()
    };
  }
}


    2. Pre-release Versions

    Format: MAJOR.MINOR.PATCH-prerelease

    Common Pre-release Identifiers:

    Identifier Meaning Example Stability
    alpha Early testing 1.0.0-alpha.1 Unstable, may have bugs
    beta Feature complete 1.0.0-beta.2 Mostly stable, testing
    rc Release Candidate 1.0.0-rc.1 Production-ready candidate


    Precedence Examples:

    1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta < 1.0.0-rc.1 < 1.0.0


    Real-world Usage:

    # Development cycle
1.0.0-alpha.1   # First alpha build
1.0.0-alpha.2   # Bug fixes in alpha
1.0.0-beta.1    # Feature complete, start testing
1.0.0-beta.2    # Beta bug fixes
1.0.0-rc.1      # Release candidate
1.0.0-rc.2      # Final fixes
1.0.0           # Production release!


    3. Build Metadata

    Format: MAJOR.MINOR.PATCH+metadata

    Purpose: Additional build information (ignored in version precedence)

    Examples:

    1.0.0+20241215
1.0.0+build.123
1.0.0+sha.a3f2b1c
1.0.0-beta.1+exp.sha.5114f85


    Usage in CI/CD:

    # GitHub Actions example
- name: Generate version
  run: |
    VERSION="1.0.0+build.$"
    echo "VERSION=$VERSION" >> $GITHUB_ENV


    SemVer Rules


    Rule 1: Initial Development

    Format: 0.y.z

    Guidelines:

    0.1.0   # Initial development
0.2.0   # Added features
0.3.0   # More features
0.9.0   # Nearly ready
1.0.0   # First stable release!

    Important:

    • MAJOR version 0 is for initial development
    • Anything may change at any time
    • Public API should not be considered stable


    Rule 2: Version 1.0.0

    When to release 1.0.0:

    ✅ Public API is defined
✅ API is stable
✅ Production-ready
✅ Backward compatibility will be maintained

    Example:

    Before 1.0.0:
- Experimental features
- Frequent breaking changes
- Not recommended for production

After 1.0.0:
- Stable API
- Breaking changes only in MAJOR versions
- Production-ready


    Rule 3: Version Precedence

    Precedence Order (lowest to highest):

    1.0.0-alpha
1.0.0-alpha.1
1.0.0-alpha.beta
1.0.0-beta
1.0.0-beta.2
1.0.0-beta.11
1.0.0-rc.1
1.0.0
1.0.1
1.1.0
2.0.0


    Rule 4: Once Released, Never Modify

    Wrong:

    git tag 1.0.0
# Oops, found a bug
git tag -d 1.0.0  # Delete tag
# Fix bug
git tag 1.0.0     # Re-tag same version ❌

    Right:

    git tag 1.0.0
# Found a bug
# Fix bug
git tag 1.0.1     # New version ✅


    Practical Examples


    Example 1: Library Evolution

    Scenario: Authentication library

    // Version 1.0.0 - Initial release
class Auth {
  login(username, password) {
    return token;
  }
}

// Version 1.1.0 - Added OAuth support (MINOR)
class Auth {
  login(username, password) {
    return token;
  }
  
  loginWithOAuth(provider, code) {  // New method ✅
    return token;
  }
}

// Version 1.1.1 - Fixed token expiry bug (PATCH)
class Auth {
  login(username, password) {
    return token;  // Now correctly sets expiry
  }
  
  loginWithOAuth(provider, code) {
    return token;
  }
}

// Version 1.2.0 - Added MFA support (MINOR)
class Auth {
  login(username, password, mfaCode?) {  // Optional param ✅
    return token;
  }
  
  loginWithOAuth(provider, code) {
    return token;
  }
  
  enableMFA(userId) {  // New method ✅
    return secret;
  }
}

// Version 2.0.0 - Changed to async/await (MAJOR)
class Auth {
  async login(username, password, mfaCode?) {  // Changed signature ⚠️
    return token;
  }
  
  async loginWithOAuth(provider, code) {  // Changed signature ⚠️
    return token;
  }
  
  async enableMFA(userId) {  // Changed signature ⚠️
    return secret;
  }
}


    Example 2: REST API Versioning

    Version 1.0.0:

    GET /api/users
Response: ["user1", "user2"]

    Version 1.1.0 (Added pagination - MINOR):

    GET /api/users
Response: ["user1", "user2"]  # Still works

GET /api/users?page=1&limit=10
Response: {
  "users": ["user1", "user2"],
  "total": 2
}

    Version 2.0.0 (Always return object - MAJOR):

    GET /api/users
Response: {           # Changed response structure ⚠️
  "users": ["user1", "user2"],
  "total": 2,
  "page": 1
}


    Example 3: Configuration File Changes

    Version 1.0.0:

    # config.yml
database:
  host: localhost
  port: 5432

    Version 1.1.0 (Added optional field - MINOR):

    # config.yml
database:
  host: localhost
  port: 5432
  ssl: true  # Optional, defaults to false

    Version 2.0.0 (Renamed fields - MAJOR):

    # config.yml
database:
  hostname: localhost    # Renamed from 'host' ⚠️
  port: 5432
  enableSSL: true        # Renamed from 'ssl' ⚠️


    Why Use SemVer?


    1. Clarity

    Without SemVer:

    v1.5   → v1.6   # What changed? 🤷
v1.6   → v2.0   # Breaking changes? 🤷

    With SemVer:

    v1.5.3 → v1.5.4 # Bug fix - safe to update ✅
v1.5.4 → v1.6.0 # New features - safe to update ✅
v1.6.0 → v2.0.0 # Breaking changes - review required ⚠️


    2. Dependency Management

    package.json example:

    {
  "dependencies": {
    "express": "^4.18.0",     // Accept MINOR and PATCH updates
    "lodash": "~4.17.21",     // Accept only PATCH updates
    "react": "18.2.0"         // Exact version
  }
}

    Version Range Operators:

    ^1.2.3  →  >=1.2.3 <2.0.0  (default, safe for MINOR/PATCH)
~1.2.3  →  >=1.2.3 <1.3.0  (conservative, PATCH only)
1.2.x   →  >=1.2.0 <1.3.0  (any PATCH version)
*       →  >=0.0.0          (any version - dangerous!)


    3. Automation

    Automated Version Bumping:

    # Using npm
npm version patch  # 1.0.0 → 1.0.1
npm version minor  # 1.0.1 → 1.1.0
npm version major  # 1.1.0 → 2.0.0

# Using semantic-release
# Automatically determines version from commit messages
feat: add new feature      → MINOR bump
fix: resolve bug           → PATCH bump
BREAKING CHANGE: API      → MAJOR bump


    4. Clear Communication

    Changelog Example:

    ## [2.0.0] - 2024-01-15

### Breaking Changes
- Changed `getData()` return type from Array to Object
- Removed deprecated `oldMethod()`

### Migration Guide
```javascript
// Before (v1.x)
const data = api.getData();  // Returns [1, 2, 3]

// After (v2.x)
const result = api.getData();
const data = result.data;    // Access via .data property

    [1.5.0] - 2024-01-10

    Added

    • New getDataWithMetadata() method

    Fixed

    • Fixed memory leak in cache manager


    Best Practices


    1. Document Your Public API

    Define what’s public:

    // ✅ Good: Clear public API
/**
 * @public
 * Authenticates user and returns token
 */
export function login(username, password) { }

// ❌ Bad: Internal function exposed
export function _internalHelper() { }  // Don't expose internals


    2. Use Conventional Commits

    Format: type(scope): subject

    # Commit messages that trigger version bumps
feat(auth): add OAuth2 support          → MINOR (1.0.0 → 1.1.0)
fix(api): resolve null pointer error    → PATCH (1.0.0 → 1.0.1)
feat!: change response format           → MAJOR (1.0.0 → 2.0.0)

# With body
feat(api): add pagination support

BREAKING CHANGE: Response format changed from array to object


    3. Deprecate Before Removing

    Version 1.5.0 - Deprecate:

    /**
 * @deprecated Use newMethod() instead. Will be removed in v2.0.0
 */
function oldMethod() {
  console.warn('oldMethod() is deprecated, use newMethod()');
  return newMethod();
}

function newMethod() {
  // New implementation
}

    Version 2.0.0 - Remove:

    // oldMethod() removed
function newMethod() {
  // New implementation
}


    4. Write Migration Guides

    Example for MAJOR version:

    # Migration Guide: v1.x to v2.0

## Breaking Changes

### 1. Changed Response Format
**Before:**

const users = await getUsers();  // Returns ['user1', 'user2']


**After:**

const response = await getUsers();
const users = response.data;  // Access via .data property


### 2. Removed Methods
- `oldMethod()` → Use `newMethod()` instead
- `legacyAPI()` → Use `modernAPI()` instead


    5. Automate Version Management

    GitHub Actions example:

    name: Release

on:
  push:
    branches: [ main ]

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Semantic Release
        uses: cycjimmy/semantic-release-action@v3
        with:
          branches: |
            ['main']
        env:
          GITHUB_TOKEN: $
          NPM_TOKEN: $


    Common Mistakes


    ❌ Mistake 1: Breaking Changes in MINOR

    // Version 1.5.0 → 1.6.0
// ❌ Wrong: Breaking change in MINOR version
function getData() {
  return { data: [] };  // Changed from returning Array
}

// ✅ Right: Should be 2.0.0


    ❌ Mistake 2: Not Starting at 1.0.0

    0.1.0 → 0.2.0 → ... → 0.9.0 → 0.10.0 → 0.11.0
                                ↑
                        Should be 1.0.0!


    ❌ Mistake 3: Modifying Released Versions

    # ❌ Wrong
git tag 1.0.0
git push --tags
# Found bug, delete and re-tag
git tag -d 1.0.0

# ✅ Right
git tag 1.0.0
git push --tags
# Found bug, create new version
git tag 1.0.1

    Conclusion

    Version numbers aren’t just numbers—they’re promises.

    Adopting Semantic Versioning improves:

    • Maintainability: Clear change tracking
    • Collaboration: Team understands impact
    • User Trust: Reliable upgrade path


    Key Takeaways

    ✅ MAJOR: Breaking changes (update with care)
    ✅ MINOR: New features (safe to update)
    ✅ PATCH: Bug fixes (update immediately)
    ✅ Pre-release: Testing versions (not for production)
    ✅ Build metadata: Additional info (ignored in precedence)


    Before Your Next Release

    Checklist:

    □ Is your API truly stable? (before 1.0.0)
□ Are breaking changes documented? (MAJOR version)
□ Did you deprecate before removing? (between MAJOR versions)
□ Is the changelog updated?
□ Are migration guides provided?
□ Did you test backward compatibility?


    Final Thought

    Versions are promises. SemVer is how you keep them.

    When you release 2.0.0, tell users what changed.
    When you release 1.1.0, assure them it’s safe.
    When you release 1.0.1, let them know the bug is fixed.

    Your version number is your contract with users—honor it with SemVer.
