    VictoriaMetrics Guide: Long-Term Prometheus Storage with vmagent

    Replace Prometheus memory bottlenecks and Thanos operational complexity with vmsingle, lossless disk-buffered vmagent ingestion, and native MetricsQL.


    Overview

    As Kubernetes cluster environments scale up, the volume of collected time-series metrics grows exponentially. Ingesting and retaining metrics from hundreds of nodes and tens of thousands of pods with a single Prometheus instance introduces chronic operational risks: high memory consumption leading to OOM-Kills, local disk I/O bottlenecks during long retention periods, and degrading query latencies. While Thanos is frequently adopted as an object storage-backed long-term storage solution, managing its distributed components—Sidecar, Store Gateway, Querier, Compactor, and Receiver—introduces operational complexity and infrastructure maintenance overhead.

    VictoriaMetrics is an ultra-lightweight, high-performance time-series database (TSDB) engineered to solve these operational pain points. Built with 100% Prometheus scrape configuration compatibility and PromQL support, it consumes 4 to 10 times less memory than Prometheus while delivering storage compression rates of 0.4 to 0.8 bytes per sample. Furthermore, paired with its lightweight collector vmagent, it enables a zero-loss metric ingestion pipeline backed by local disk queue buffering.

    This guide explores the core architecture of VictoriaMetrics (vmsingle vs Cluster), building a resilient metric pipeline with vmagent, production Helm deployments and seamless Grafana integration, MetricsQL query enhancements, non-disruptive S3 snapshot backups with vmbackup, and high-cardinality diagnosis with TSDB tuning.


    Prometheus Limitations and VictoriaMetrics Solutions

    Memory Bottlenecks and Disk I/O Pressure in Large Clusters

    Prometheus relies on in-memory chunks and local TSDB block structures to deliver high read and write performance. However, this architecture faces structural limits in dynamic, large-scale container environments. When thousands of ephemeral pods churn continuously, newly generated time series explode, driving memory utilization sharply upward. In particular, periodic TSDB block compaction cycles and heavy long-range queries cause memory spikes that routinely trigger pod OOM-Kills.

    In addition, Prometheus persists data directly to a single node’s local disk. Retaining metrics over several months for capacity planning or compliance escalates disk capacity requirements and I/O load beyond what a single local volume can reliably sustain.

    Operational Simplicity and Storage Efficiency over Thanos

    As discussed in earlier posts on What is Prometheus and Thanos? and Installing Prometheus and Thanos with Helm, Thanos offloads metrics to object storage via Prometheus sidecars to provide long-term retention and global query federation. However, managing Thanos in production requires operating multiple decoupled services. Engineering teams must resolve inter-service communication latencies, debug Compactor block overlap failures, and tune Store Gateway index cache memory.

    VictoriaMetrics delivers equal or superior performance while drastically reducing operational surface area. In single-node deployments, vmsingle runs as a standalone Go binary without external dependencies. In distributed environments, VictoriaMetrics Cluster divides responsibilities into three clear roles: vmstorage, vminsert, and vmselect. Its specialized block compression algorithm achieves 0.4 to 0.8 bytes per sample, cutting storage footprint and disk costs to less than half of Prometheus.

    VictoriaMetrics Core Architecture and Components

    Single-Binary All-in-One Mode: vmsingle

    VictoriaMetrics supports two deployment models depending on cluster size and operational requirements: vmsingle and Cluster mode. vmsingle is an all-in-one architecture where ingestion, storage, and query processing execute within a single Go process.

    • Ingestion Throughput: Easily processes over 1,000,000 samples per second on a single modest instance.
    • Operational Simplicity: Stores time-series data directly into a local directory with zero external coordination or database dependencies.
    • Target Use Cases: Optimized for individual Kubernetes clusters spanning dozens to hundreds of nodes, staging and testing environments, and edge infrastructure monitoring.

    Distributed Cluster Mode: vmstorage, vminsert, and vmselect

    For large enterprise environments, multi-cluster architectures, or multi-tenant setups requiring horizontal scalability, VictoriaMetrics Cluster mode separates storage from compute, allowing each tier to scale independently.

    • vmstorage: Stateful nodes responsible for storing raw time-series data, indexing label sets, and managing disk I/O.
    • vminsert: Stateless ingestion proxies that receive remote_write payloads from vmagent or Prometheus and distribute samples across vmstorage nodes using consistent hash routing.
    • vmselect: Stateless query routers that process PromQL and MetricsQL requests from Grafana or alerting systems, fetching and aggregating partial results from vmstorage nodes.

    Lightweight Ingestion and Lossless Pipelines with vmagent

    Full Prometheus Scrape Compatibility and Minimal Footprint

    vmagent is a purpose-built, ultra-lightweight agent that handles metric scraping and remote_write forwarding. Because it natively supports Prometheus scrape_configs syntax alongside ServiceMonitor and PodMonitor Custom Resource Definitions (CRDs), existing scrape configurations can be transferred directly without modifying a single line of YAML.

    Unlike a full Prometheus server that combines scraping, indexing, query execution, and TSDB compaction—consuming gigabytes of memory—vmagent strips away the query engine. Scraping hundreds of thousands of targets requires only tens of megabytes of RAM.

    Local Disk Buffering and Zero-Loss Mechanism

    The standout capability of vmagent is its integrated local disk queue buffer (-remoteWrite.tmpDataPath). When temporary network partitions occur or the remote storage endpoint becomes unreachable, standard Prometheus drops incoming samples once its in-memory queue reaches capacity. In contrast, vmagent spools undelivered samples to local disk.

    extraArgs:
  remoteWrite.tmpDataPath: "/vmagent-remotewrite-data"
  remoteWrite.maxDiskUsagePerURL: "10737418240" # Max 10 GiB buffer per destination URL
  remoteWrite.queues: "8"
  remoteWrite.flushInterval: "1s"

    Once connectivity to the remote storage backend is restored, vmagent replays the buffered data from disk in chronological sequence in the background, guaranteeing lossless metrics ingestion without operator intervention.

    Multi-Tenancy and Multi-Destination remote_write Routing

    vmagent natively supports replicating or conditionally routing metrics to multiple destination endpoints from a single collection pipeline:

    remoteWrite:
  - url: "http://vmsingle-victoria-metrics-single-server.monitoring.svc.cluster.local:8428/api/v1/write"
  - url: "http://backup-vminsert.monitoring.svc.cluster.local:8480/insert/0/prometheus/api/v1/write"
    urlRelabelConfig:
      - action: keep
        source_labels: [__name__]
        regex: "(node_.*|container_.*)"

    Using urlRelabelConfig, operators can forward all metrics to an operational vmsingle instance while replicating only essential host and container metrics to a secondary long-term storage cluster.


    Production Helm Deployment and Seamless Grafana Integration

    Deploying vmsingle and vmagent with Helm Charts

    Deploying VictoriaMetrics on Kubernetes is streamlined using the official Helm charts repository:

    helm repo add vm https://victoriametrics.github.io/helm-charts/
helm repo update

    Create a production-tuned values-vmsingle.yaml manifest configuring retention periods, persistent volume storage, and memory limits:

    server:
  image:
    tag: "v1.106.1"
  retentionPeriod: "12M" # 12-month retention period
  persistentVolume:
    enabled: true
    size: 150Gi
    storageClassName: "gp3"
  resources:
    limits:
      cpu: "4"
      memory: "8Gi"
    requests:
      cpu: "1"
      memory: "2Gi"
  extraArgs:
    memory.allowedPercent: "80"
    search.maxQueryDuration: "30s"
    search.maxConcurrentRequests: "16"

    Deploy the vmsingle server into the monitoring namespace:

    helm upgrade --install vmsingle vm/victoria-metrics-single \
  --namespace monitoring \
  --create-namespace \
  -f values-vmsingle.yaml

    Next, deploy vmagent configured to scrape cluster metrics and forward them to the vmsingle service endpoint:

    helm upgrade --install vmagent vm/victoria-metrics-agent \
  --namespace monitoring \
  --set remoteWrite[0].url="http://vmsingle-victoria-metrics-single-server.monitoring.svc.cluster.local:8428/api/v1/write" \
  --set extraArgs.remoteWrite\.tmpDataPath="/vmagent-remotewrite-data"

    Grafana Data Source Setup and Zero-Query-Modification Transition

    Connecting VictoriaMetrics to a Grafana environment—such as the one configured in the Grafana Installation Guide (Helm-based)—requires no dashboard refactoring. Because VictoriaMetrics provides an API fully compatible with Prometheus, Grafana’s data source type remains set to prometheus, requiring only an update to the HTTP endpoint URL.

    In Grafana’s datasources.yaml provisioning file:

    apiVersion: 1
datasources:
  - name: VictoriaMetrics
    type: prometheus
    access: proxy
    url: http://vmsingle-victoria-metrics-single-server.monitoring.svc.cluster.local:8428
    isDefault: true
    jsonData:
      httpMethod: POST
      timeInterval: 15s

    In Cluster mode, set the URL to http://vmselect-service:8481/select/0/prometheus/. Once provisioned, existing Kubernetes monitoring dashboards, Node Exporter templates, and custom PromQL alert rules execute identically without modifying a single query.


    MetricsQL Extensions and Practical Query Optimization

    Full PromQL Compatibility and MetricsQL Enhancements

    VictoriaMetrics evaluates standard PromQL out of the box. Beyond standard compatibility, it introduces MetricsQL, an extended query dialect that resolves structural limitations in PromQL and improves query ergonomics.

    MetricsQL optimizes subquery execution and supports implicit query conversions, eliminating the need for redundant range vector declarations in common aggregations.

    Subquery Optimization and Efficient rate Evaluation

    In standard PromQL, calculating the rate of change for a counter or gauge across a long window often requires expensive subqueries (such as [1h:1m]), which frequently trigger query timeouts in high-cardinality environments.

    MetricsQL redesigns the internal rollup calculation engine to be cache-aware. It processes subqueries up to an order of magnitude faster and allows omitting explicit step intervals when evaluating rates over extended time windows:

    # Calculate per-second HTTP request increase rate over 1 hour using a 5-minute subquery window
rate(http_requests_total[5m])[1h]

    Preserving Metric Names with keep_metric_names and Tracking changes

    A known frustration in PromQL is that transforming functions like rate() or increase() automatically strip the metric name label (__name__). This forces operators to manually reconstruct or remap metric labels when defining alert templates or composite dashboard variables.

    MetricsQL introduces the keep_metric_names modifier to preserve the original metric name across transformation functions:

    rate(http_requests_total[5m]) keep_metric_names

    In addition, the changes function counts how many times a metric’s value has altered over a given duration, providing an effective way to detect flapping status codes, pod restart cycles, or rapid deployment changes early.


    Non-Disruptive S3 Snapshot Backups and Disaster Recovery with vmbackup

    Instant Snapshots and Incremental Object Storage Backups

    Historical metric data serves as essential input for long-term capacity planning, SLA tracking, and incident postmortems. VictoriaMetrics provides vmbackup, a specialized utility that generates consistent point-in-time snapshots and backs them up incrementally to object storage services like AWS S3 without service interruption.

    The backup pipeline proceeds in three steps:

    1. Snapshot Creation: An HTTP call to /snapshot/create freezes data consistency via filesystem hard links in under one second, causing zero degradation to ongoing ingestion or query traffic.
    2. Incremental Sync: The vmbackup binary reads the snapshot directory, compares existing blocks with remote object storage, and uploads only newly added or modified data blocks.
    3. Snapshot Cleanup: Once the upload finishes, calling /snapshot/delete removes the local hard links.
    vmbackup \
  -storageDataPath=/storage \
  -snapshot.createURL=http://localhost:8428/snapshot/create \
  -dst=s3://<your-backup-bucket>/victoriametrics/backup

    Disaster Recovery Pipeline with vmrestore

    If a storage volume suffers corruption or a cluster must be recovered in a new environment, vmrestore pulls snapshot data from S3 directly into the designated local storage path:

    vmrestore \
  -src=s3://<your-backup-bucket>/victoriametrics/backup/latest \
  -storageDataPath=/storage

    Once the files are restored, starting the VictoriaMetrics process immediately serves historical metrics without requiring index rebuilds.


    High Cardinality Diagnosis and TSDB Tuning Strategies

    Tracking Cardinality Explosions via /api/v1/status/tsdb

    In microservice architectures, high cardinality represents the primary cause of TSDB performance degradation. When application developers attach unbounded labels—such as user IDs, UUIDs, or raw API paths—to metric dimensions, time series count explodes, exhausting memory and stalling queries.

    VictoriaMetrics provides a built-in diagnostic endpoint to inspect TSDB cardinality in real time:

    curl -s http://localhost:8428/api/v1/status/tsdb | jq .

    The returned JSON payload highlights the exact dimensions driving index growth:

    • seriesCountByMetricName: Top metric names generating the highest number of active time series.
    • labelValueCountByLabelName: Label keys with the highest count of unique label values.
    • seriesCountByLabelValuePair: Specific label=value pairs accounting for the largest share of stored series.

    Reviewing these fields enables operators to quickly identify offending workloads and isolate high-cardinality label keys.

    Metric Relabel Filtering and Memory Cache Optimization

    When high-cardinality labels like transaction IDs or user IDs are detected, they should be stripped during ingestion using metric_relabel_configs in vmagent:

    metric_relabel_configs:
  - regex: "(user_id|session_token|request_uuid)"
    action: labeldrop

    In addition, tune memory allocation flags on vmsingle or vmstorage to optimize disk caching and prevent memory exhaustion:

    • -memory.allowedPercent=80: Limits the process to 80% of total host RAM, leaving 20% for the operating system page cache and preventing kernel OOM-Kills.
    • -search.maxQueryDuration=30s: Enforces a hard 30-second timeout on complex queries to prevent rogue dashboard requests from monopolizing compute resources.


    Conclusion

    VictoriaMetrics preserves the key advantages of the Prometheus ecosystem—declarative scrape configuration, familiar PromQL syntax, and native Grafana dashboard support—while resolving its primary operational bottlenecks: high memory consumption and local disk I/O exhaustion.

    In single-cluster or mid-sized environments, combining vmsingle with vmagent provides a low-maintenance, resource-efficient monitoring architecture that handles over a million samples per second. In large enterprise or multi-cluster deployments, switching to VictoriaMetrics Cluster decouples stateless ingestion (vminsert) and query processing (vmselect) from stateful storage (vmstorage), delivering independent horizontal scalability and high availability.

    For teams struggling with Prometheus memory crashes or hesitant to manage the distributed operational complexity of Thanos, adopting VictoriaMetrics with vmagent provides an efficient, reliable, and production-tested metric pipeline.
