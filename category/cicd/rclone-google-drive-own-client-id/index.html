    rclone's Built-in Drive client_id Is Retiring: GitLab CI Migration

    A NOTICE line in a CI log, a free Google Cloud project, and a rollout that never took a backup job offline


    Overview

    In an earlier post, Automating File Uploads to Google Drive with GitLab CI and rclone, the client_id prompt was left blank and the “set your own client ID” advice was treated as an optional performance tweak. That advice is no longer optional.

    After a routine bump of our internal rclone image to v1.75.1, the very first backup job printed a line that the v1.74.1 jobs never had:

    NOTICE: gitlab-backup: This remote uses rclone's shared Google Drive client_id, which is being retired
and will stop working during 2026. Create your own client_id to avoid interruption:
https://rclone.org/drive/#making-your-own-client-id

    The job still succeeded. Nothing was broken yet. But the rclone documentation is explicit about where this is going:

    This shared client_id is being retired and will stop working during 2026. To avoid interruption you must create and use your own client_id, so creating one is now required rather than merely recommended.

    This post walks through the migration we did for two GitLab CI remotes: a source-code backup job that every repository inherits from a shared CI template, and a design-document sync job. It covers creating the OAuth client, updating rclone.conf without leaking the secret, one interactive prompt that quietly pointed a remote at the wrong Shared Drive, and rolling the new credentials into GitLab CI without taking a single job offline.


    Why It Matters

    When you leave client_id blank, rclone authenticates as rclone’s own Google Cloud project. Every rclone user on the internet who did the same shares that one client and its API quota. When the client is retired, every remote that depends on it stops authenticating at the same moment, on a date you do not control.

    In our setup that would have been loud:

    • The backup job comes from a shared CI template, so every repository runs it on every push.
    • On push, the job is not allow_failure. A dead client means every push pipeline in every repository turns red on the same day.
    • The design-document sync would fail too, so the team’s Drive copy would silently stop updating.

    The fix itself is identical whether you do it now or on the day it breaks. The only difference is whether you do it under pressure.

    There is also an upside. Because the shared client’s quota is split across every rclone user, rate-limit errors are more likely on it. Your own client has its own quota.


    Am I Affected?

    A Google Drive remote without a client_id line, or with an empty one, is on the shared client, unless it authenticates with a service account or env_auth. Those never go through the OAuth client at all. This prints the name of every affected remote and never prints a secret:

    awk '
/^\[/ { if (r && d && !c) print r; r = $0; d = 0; c = 0 }
/^type *= *drive/ { d = 1 }
/^client_id *= *[^ ]/ { c = 1 }
/^service_account_(file|credentials) *= *[^ ]/ { c = 1 }
/^env_auth *= *true/ { c = 1 }
END { if (r && d && !c) print r }
' ~/.config/rclone/rclone.conf

    Run the same check against what your CI actually uses, not just your laptop. In GitLab, that is the content of the File-type variable that holds rclone.conf. A local config that is already fixed tells you nothing about a CI variable that was pasted months ago.

    The NOTICE line above in a job log is the same signal, but only on rclone v1.74.4 or later, where it was introduced. Images on v1.74.3 or earlier never print it, so a quiet log there proves nothing.


    Creating Your Own OAuth Client

    The rclone docs describe the steps at Making your own client_id. Here is what the path looked like in practice, including the screens the docs do not mention.


    1. Which Google account?

    The rclone docs say it plainly: “It doesn’t matter what Google account you use. (It need not be the same account as the Google Drive you want to access)”. The client only identifies the app. Which Drive it can reach is decided later, by the account you log in with when you authorize rclone.

    Two practical reasons still pushed us toward a company account inside the Workspace organization:

    • Ownership. If the client lives in someone’s personal account and that account or project goes away, every CI job that uses it breaks.
    • The Internal audience. Our remotes point at Shared Drives, which means a Google Workspace organization. Creating the project under that organization lets you pick Internal, which avoids the testing-mode trap covered below.


    2. Create the project, and skip the billing screen

    Create a new project and make sure the Organization field is your Workspace domain, not “No organization”. It cannot be changed afterwards.

    On a first visit, the console may route you into a free trial / billing profile form asking for company tax details. You do not need it. Enabling the Google Drive API and creating an OAuth client works without a billing account. Close that form and open the project creation page directly. A first-time terms of service dialog is a different thing and is fine to accept.


    3. Enable the Google Drive API

    With the new project selected, open APIs & Services → Library → Google Drive API and click Enable.


    4. Configure the consent screen as Internal

    Open Google Auth Platform (the newer home of the OAuth consent screen), click Get started, and fill in:

    Field Value
    App name rclone
    User support email Your account
    Audience Internal
    Contact email Your account

    The rclone docs also add the docs, drive and drive.metadata.readonly scopes under Data Access. With an Internal audience we skipped that page and authorization still worked, because rclone requests its scope at authorization time. On External, add them as the docs describe.


    5. Create a Desktop client

    Under Clients → Create client:

    • Application type: Desktop app
    • Name: rclone
    • “This client will be used by an AI-powered agent”: leave it unchecked. rclone running in a CI job is not an AI agent.

    The console warns that settings can take from five minutes to a few hours to apply. If authorization fails with invalid_client right after creation, wait and retry before debugging anything else.

    You now have a client ID and a client secret. The console shows the client secret only once; Google stores it hashed afterwards and displays only its last four characters. Download the JSON now and keep it somewhere safe. Losing it means adding a new secret to the client.


    Internal vs External: The 7-Day Trap

    If you are not on Workspace, or cannot create the project under your organization, you will have to use External. That works, but one detail will break a CI job a week after you ship it.

    Google’s OAuth documentation:

    A Google Cloud Platform project with an OAuth consent screen configured for an external user type and a publishing status of “Testing” is issued a refresh token expiring in 7 days, unless the only OAuth scopes requested are a subset of name, email address, and user profile.

    rclone asks for the drive scope, so the exception does not apply. A CI job authorized in Testing mode works for exactly one week and then fails.

    Internal External, left in "Testing" External, published
    Who can authorize Users in your Workspace organization Listed test users Any Google account
    Refresh token lifetime Not subject to the 7-day rule Expires after 7 days Not subject to the 7-day rule
    Fits a CI job Yes No Yes

    If you go External, follow the rclone docs to the end: open Audience and click PUBLISH APP. If the button is greyed out, Google wants a home page URL and a privacy policy URL first, so fill them in under Branding. An unverified published app also shows an alarming confirmation screen when you authorize rclone in the browser. The rclone docs note that you can go ahead past it, and you only see it while configuring the remote.


    Updating rclone.conf Without Leaking the Secret

    Back up the config first:

    cp ~/.config/rclone/rclone.conf ~/.config/rclone/rclone.conf.bak-$(date +%Y%m%d)


    1. Write the client into every remote

    rclone config update takes the values as arguments. To keep the secret out of your shell history and off the screen, read it into a variable first. read -rs works in both bash and zsh:

    printf 'client_id: '; read -r CID
printf 'client_secret: '; read -rs CS; echo
for r in "gitlab-backup" "design-docs"; do
  rclone config update "$r" client_id "$CID" client_secret "$CS" config_refresh_token false
done
unset CS

    config_refresh_token false stops update from trying to refresh the token on its own. A token issued to the old client cannot be refreshed by the new one anyway. The next step does a full re-authorization on purpose.

    One client can serve every remote. You do not need one per remote.


    2. Re-authorize each remote

    rclone config reconnect "gitlab-backup":

    The prompts, and what to answer:

    Token already configured - replace it?
y/n> y

Use web browser to automatically authenticate rclone with remote?
y/n> y

NOTICE: Make sure your Redirect URL is set to "http://127.0.0.1:53682/" in your custom config.
NOTICE: Log in and authorize rclone for access
NOTICE: Waiting for code...
NOTICE: Got code

Change current Shared Drive (Team Drive) ID "0AXXXXXXXXXXXXXXXXX"?
y/n> n
    • In the browser, log in with the account that has access to the Shared Drive this remote points at.
    • The Make sure your Redirect URL ... in your custom config notice refers to the custom client, a good sign that the update in step 1 landed.
    • Answer n to the Shared Drive question. The next section explains why.


    Gotcha: reconnect Can Silently Switch Your Shared Drive

    We re-authorized two remotes, one per Shared Drive. Both reconnects succeeded. Then we listed them:

    $ rclone lsd "gitlab-backup": | head -2
           0 2025-10-20 15:02:14        -1 project-a
           0 2025-11-03 12:25:16        -1 project-b

$ rclone lsd "design-docs": | head -2
           0 2025-10-20 15:02:14        -1 project-a
           0 2025-11-03 12:25:16        -1 project-b

    Two remotes, the same folders. The backup remote should have listed one folder per repository.

    The reason is the Change current Shared Drive (Team Drive) ID? prompt. Answer y, and rclone lists every Shared Drive the account can see. Pick the wrong entry, and the remote’s team_drive is rewritten with no further warning. Authentication is fine, so nothing errors. If that config had reached CI, every repository’s backup would have started writing into the design-documents drive, and its retention cleanup would have run in the wrong folder.

    The fix is one line, using the ID from your backup copy:

    rclone config update "gitlab-backup" team_drive 0AXXXXXXXXXXXXXXXXX config_refresh_token false

    Before anything goes near CI, check two things for every remote:

    grep -E '^\[|^team_drive' ~/.config/rclone/rclone.conf       # IDs match the backup copy
rclone lsd "gitlab-backup": | head -5                         # contents are what you expect

    A successful reconnect proves authentication. Only listing the contents proves the remote points where it should.


    Rolling It Out to GitLab CI

    Our CI keeps one remote per File-type variable. Both are instance-level variables on a self-managed GitLab (Admin → Settings → CI/CD → Variables), so every project sees them:

    Variable Holds Used by
    GITLAB_BACKUP_RCLONE_CONFIG [gitlab-backup] The shared source-backup template, in every repository
    RCLONE_CONFIG [design-docs] The design-document sync job

    Changing them changes every pipeline at once, so we treated it like a deploy, with a rollback path.


    1. Keep the current values

    Save each variable’s current value to a mode-600 file before touching it. That is the rollback:

    for k in GITLAB_BACKUP_RCLONE_CONFIG RCLONE_CONFIG; do
  ( umask 077
    glab api "admin/ci/variables/$k" \
      | python3 -c 'import json,sys; sys.stdout.write(json.load(sys.stdin)["value"])' > "$k.rollback" )
done


    2. Extract one section per variable, and test it standalone

    Since each variable holds exactly one remote, extract that section from the updated local config:

    extract() { awk -v s="[$1]" '/^\[/ { on = ($0 == s) } on' ~/.config/rclone/rclone.conf; }
( umask 077
  extract "gitlab-backup" > gitlab-backup.conf
  extract "design-docs"   > design-docs.conf )

    Then run each file on its own, with --config, exactly as CI will:

    rclone lsd "gitlab-backup": --config gitlab-backup.conf | head -3
rclone lsd "design-docs":   --config design-docs.conf   | head -3


    3. Exercise the write path

    The backup job uploads, lists, and deletes old archives. Listing only proves read access, so run the same three operations in a scratch folder:

    echo "client-id swap test $(date)" > probe.txt
dst="gitlab-backup:_rclone-client-id-test"
rclone copy  probe.txt "$dst/" --config gitlab-backup.conf
rclone lsf   "$dst/"           --config gitlab-backup.conf
rclone purge "$dst"            --config gitlab-backup.conf


    4. Replace the variables and compare hashes

    Paste each file into the variable in the UI, keeping the type as File, or use the API. With glab, -F value=@file sends the file’s contents:

    glab api -X PUT "admin/ci/variables/GITLAB_BACKUP_RCLONE_CONFIG" -F "value=@gitlab-backup.conf"
glab api -X PUT "admin/ci/variables/RCLONE_CONFIG" -F "value=@design-docs.conf"

    Then confirm what GitLab stored, without printing it, by comparing a hash of the live value with the file:

    glab api "admin/ci/variables/RCLONE_CONFIG" \
  | python3 -c 'import json,sys,hashlib; v=json.load(sys.stdin); print(v["variable_type"], hashlib.sha256(v["value"].encode()).hexdigest()[:12])'
shasum -a 256 design-docs.conf | cut -c1-12

    The type should still be file, and the two hashes should match. A mismatch catches more than you might expect, for example a client that sent the literal string @design-docs.conf instead of the file’s contents.


    Verifying in CI

    Only a real job proves the swap. Here, the next push to any repository ran the backup job with the new variable:

    Using Kubernetes executor with image <internal-registry>/<rclone-image>:<rclone-1.75.1-tag> ...
Transferred:            1 / 1, 100%
[INFO] Deleting old backup: <project>_<sha>_20260916_055649.tar.gz
Job succeeded

    What is missing matters as much: the shared Google Drive client_id NOTICE is gone. The same rclone version printed it earlier that day, so its absence confirms the new client is the one in use.

    The design-document sync then listed about 6,000 objects and checked roughly 2,900 files against the drive with zero errors.

    Only after both variables had a passing real job did we delete the saved *.rollback values, the extracted *.conf files and probe.txt. The local rclone.conf backup from the first step goes the same way, since it holds tokens too. The downloaded client JSON holds the secret, so move it into your secret store rather than leaving it in ~/Downloads.


    Side Notes


    Google Cloud console 2-step verification

    While creating the project, the console showed a banner announcing that 2-step verification becomes mandatory. Per Google’s MFA requirement page, Enterprise Cloud Identity accounts that do not use SSO, in organizations created before August 3, 2026, are covered on or after October 20, 2026. The requirement applies to the Google Cloud console and the Firebase console.

    It does not affect rclone. The requirement is about signing in to those consoles, and rclone never signs in to a console. It uses the OAuth token it was issued when you authorized it. You will still need 2SV the next time you come back to rotate the client secret, so turn it on and keep backup codes. On a shared company account, codes tied to one person’s phone become a single point of failure.


    Cost

    Nothing. The project needs no billing account, the Drive API has no per-call charge, and storage still comes out of the same Shared Drive.


    Conclusion

    The shared client_id was a convenience that rclone has decided to stop providing. The migration is small, but it touches credentials that every pipeline depends on, so the useful parts are the guardrails, not the clicks.


    Checklist

    1. ✅ Find every Drive remote without a client_id, in local configs and in CI variables
    2. ✅ Create the project under your Workspace organization so Internal is available
    3. ✅ Skip the billing / free-trial form. Enable only the Google Drive API
    4. ✅ Create a Desktop app client, and leave the AI-agent checkbox unchecked
    5. ✅ If you must use External, publish the app, or the refresh token dies in 7 days
    6. ✅ Read the secret with read -rs. Never paste it on the command line
    7. ✅ Answer n to Change current Shared Drive?, then verify team_drive and lsd for every remote
    8. ✅ Back up the CI variables, test each extracted config standalone, and exercise the write path
    9. ✅ Compare hashes after the update. Keep the variable type as File
    10. ✅ Watch a real job: the NOTICE should be gone. Then delete every copy of the old tokens


    Nothing was broken when we started. The NOTICE was the only warning we were going to get before every backup job failed on the same day. Doing it now cost one afternoon and zero failed pipelines.
