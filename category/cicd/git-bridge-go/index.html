    Git-Bridge: Multi-Platform Git Mirroring System Built with Go

    Building a unified repository mirroring solution with EventBridge, SQS, Webhooks, and Terraform


    Overview

    In multi-platform Git environments, repository synchronization is a common challenge. When using CodeCommit as the source while needing to mirror to an internal GitLab or GitHub, each platform has different event delivery mechanisms — requiring a unified mirroring solution.

    This post introduces git-bridge, a Git repository mirroring tool written in Go. It covers the full architecture including CodeCommit event ingestion via AWS EventBridge + SQS, GitLab/GitHub webhook receivers, and Terraform-based infrastructure provisioning.

    Key Features
    • Multi-provider — CodeCommit, GitLab, GitHub (extensible via Provider interface)
    • Bidirectional mirroring — source-to-target, target-to-source, or both
    • DLQ-based retry — Failed messages automatically move to Dead Letter Queue after 5 retries
    • Slack notifications — Real-time alerts on sync success/failure
    • Kubernetes-native — Runs as a Deployment with health/readiness probes


    git-bridge GitHub Repository


    Architecture

    git-bridge handles two types of event sources:

    • CodeCommit: EventBridge captures events and delivers them to SQS, where git-bridge consumes via long-polling
    • GitLab / GitHub: HTTP POST webhooks deliver events directly to git-bridge

    Event Flow Summary

    Source Provider Event Delivery Trigger
    CodeCommit EventBridge → SQS → long-polling referenceUpdated, referenceCreated, referenceDeleted
    GitLab Push Webhook → POST /webhook/gitlab Push event
    GitHub Push Webhook → POST /webhook/github Push event


    Why SQS?

    CodeCommit does not provide native webhook support. Therefore, EventBridge + SQS is the only way to receive CodeCommit events. This approach actually provides better reliability than webhooks.

    SQS Advantages over Webhooks
    • Message guarantee — SQS provides at-least-once delivery, eliminating event loss
    • Automatic retry — Failed messages become visible again after VisibilityTimeout
    • DLQ — Messages failing 5 consecutive times move to DLQ for manual inspection
    • Decoupling — Event source and consumer scale independently
    • Outbound HTTPS only — No inbound port forwarding required, just SQS polling


    SQS vs Webhook Comparison

    Aspect SQS (CodeCommit) Webhook (GitLab/GitHub)
    Trigger EventBridge → SQS HTTP POST
    Delivery Polling (Pull) Listening (Push)
    Retry SQS auto-retry + DLQ None (fire-and-forget)
    Direction source → target target → source
    Reliability High (message guaranteed) Low (possible loss)


    Terraform Infrastructure

    The AWS infrastructure for git-bridge is provisioned with Terraform — managing EventBridge rules, SQS queues, DLQ, and IAM policies as code.


    EventBridge Rule

    Captures referenceCreated, referenceUpdated, and referenceDeleted events from CodeCommit and forwards them to SQS. Mirror target repositories are managed as a variable, so adding a new repo only requires updating the Terraform variable.


    The key point is using a for expression in the resources field of event_pattern to dynamically manage mirror target repos. Simply adding a repo name to var.codecommit_mirror_repos automatically reflects it in the EventBridge rule.

    # terraform.tfvars
codecommit_mirror_repos = ["my-app", "my-api"]


    SQS Queue + DLQ

    The main queue and DLQ are separated to isolate repeatedly failing messages for independent management.


    Why Separate Main Queue and DLQ?

    If a message keeps failing, it stays in the main queue and triggers infinite retries — impacting normal message processing and wasting resources. Moving failed messages to the DLQ keeps the main queue clean and allows separate root cause analysis.


    Flow:
    1. Message arrives → Main Queue → Retry 1 (fail)
    2. Retry 2 (fail) → Retry 3 (fail) → Retry 4 (fail) → Retry 5 (fail)
    3. Move to DLQ (retained for 14 days)
    4. Operator inspects DLQ → Root cause analysis → Manual reprocessing or deletion


    SQS Key Parameters

    Parameter Value Description
    receive_wait_time_seconds 20s Long-polling wait time
    visibility_timeout_seconds 120s Message hidden during processing
    maxReceiveCount 5 Max retries before moving to DLQ
    message_retention_seconds (Queue) 4 days Main queue retention period
    message_retention_seconds (DLQ) 14 days DLQ retention period


    visibility_timeout_seconds = 120 is set because git clone --mirror + git push --mirror can take tens of seconds depending on repository size. 120 seconds provides sufficient time for most mirror operations while avoiding excessive retry delays on failure.


    SQS Queue Policy

    Configures a queue policy to allow EventBridge to send messages to SQS.

    The ArnEquals condition restricts the queue to only accept messages from the specific EventBridge rule, preventing unauthorized sources from sending messages to the SQS queue.

    Event Processing Flow

    1. Developer pushes to CodeCommit
2. EventBridge captures "Repository State Change" event
3. EventBridge rule forwards message to SQS queue
4. git-bridge SQS Consumer receives via long-polling (20s)
5. Process by event type:
   - referenceUpdated/Created → Sync()  (clone --mirror + push --mirror)
   - referenceDeleted         → SyncDelete() (delete ref on target)
6. Success → delete message from SQS
   Failure → message stays in queue for retry (up to 5 times → DLQ)
7. Slack notification on success/failure


    Features


    Multi-Provider & Any-to-Any Mirroring

    git-bridge abstracts various Git platforms through the Provider interface.

    type Provider interface {
    CloneURL(repoPath string) string
    Type() string
}

    This interface enables mirroring across all provider combinations — CodeCommit → GitLab, GitLab → GitHub, GitHub → CodeCommit, and more. Adding a new Git platform only requires implementing this interface.


    Mirror Direction

    Direction Description Trigger
    source-to-target Source → Target only SQS (CodeCommit) or source webhook
    target-to-source Target → Source only Target provider webhook required
    bidirectional Both directions SQS + target webhook both required


    Loop Detection

    Bidirectional mirroring can cause infinite loops. git-bridge detects when a push result is already up-to-date and skips the Slack notification, preventing redundant alerts in bidirectional sync scenarios.


    Multi-SQS Consumer

    When using CodeCommit across multiple AWS regions or accounts, each SQS queue can be consumed independently. Consumers are distinguished using the SQS_<NAME>_* environment variable naming convention.

    # Example: Consuming SQS from EU and US regions simultaneously
sqs:
  - name: eu
    queue_url: ${SQS_EU_QUEUE_URL}
    region: ${SQS_EU_REGION}
  - name: us
    queue_url: ${SQS_US_QUEUE_URL}
    region: ${SQS_US_REGION}


    Configuration

    git-bridge configuration is divided into two parts:

    • Credentials → K8s Secret (injected via environment variables with ${VAR} syntax)
    • Repository definitions → K8s ConfigMap (written directly in YAML)


    Environment Variables (K8s Secret)

    Variable Description
    CODECOMMIT_<NAME>_REGION AWS region per CodeCommit provider
    CODECOMMIT_<NAME>_GIT_USERNAME CodeCommit HTTPS Git username
    CODECOMMIT_<NAME>_GIT_PASSWORD CodeCommit HTTPS Git password
    GITLAB_<NAME>_BASE_URL GitLab instance URL
    GITLAB_<NAME>_TOKEN GitLab personal access token
    GITHUB_<NAME>_TOKEN GitHub personal access token
    SQS_<NAME>_QUEUE_URL SQS queue URL per consumer
    SQS_<NAME>_REGION SQS region per consumer
    SQS_<NAME>_ACCESS_KEY AWS access key per consumer
    SQS_<NAME>_SECRET_KEY AWS secret key per consumer
    SLACK_WEBHOOK_URL Slack incoming webhook URL


    All environment variables follow the <TYPE>_<NAME>_<FIELD> pattern. <NAME> can be freely chosen (e.g., EU/US, MAIN/SECONDARY).


    Repository Config (ConfigMap)

    Repositories are defined directly in the ConfigMap. New repos can be added without changing Secrets.

    repos:
  - name: my-app
    source: codecommit-eu
    target: gitlab-main
    source_path: my-app
    target_path: team/my-app
    direction: source-to-target


    Kubernetes Deployment

    git-bridge runs as a Kubernetes Deployment.


    Endpoints

    Path Method Description
    /health GET Liveness probe
    /ready GET Readiness probe
    /webhook/gitlab POST GitLab push event receiver
    /webhook/github POST GitHub push event receiver


    Deploy Steps

    # 1. Create namespace
kubectl apply -f k8s/namespace.yaml

# 2. Create secrets (edit values first!)
kubectl apply -f k8s/secret.yaml

# 3. Create configmap and deployment
kubectl apply -f k8s/configmap.yaml
kubectl apply -f k8s/deployment.yaml

# Verify
kubectl get pods -n git-bridge
kubectl logs -n git-bridge -l app=git-bridge -f


    Adding a New Repository

    Adding a new repo to the mirror pipeline is a 3-step process.


    Step 1. Add repo to ConfigMap

    # k8s/configmap.yaml
repos:
  - name: new-repo
    source: codecommit-eu
    target: gitlab-main
    source_path: new-repo
    target_path: team/new-repo
    direction: source-to-target

    Step 2. Add repo to Terraform variable

    # terraform.tfvars
codecommit_mirror_repos = ["my-app", "my-api", "new-repo"]

    Step 3. Apply changes

    terraform apply -var-file=example.tfvars
kubectl apply -f k8s/configmap.yaml
kubectl rollout restart -n git-bridge deployment/git-bridge
    No changes to Secret or Deployment are needed.

    Webhook setup on the target provider (GitLab/GitHub) is only required when direction is target-to-source or bidirectional.


    Webhook Setup

    Webhook configuration is only required when direction is target-to-source or bidirectional. For source-to-target with CodeCommit as source, SQS triggers automatically — no webhook needed.


    GitLab Webhook

    1. GitLab project → Settings → Webhooks
    2. URL: http://git-bridge.example.com/webhook/gitlab
    3. Secret token: Match WEBHOOK_GITLAB_SECRET
    4. Trigger: Push events
    5. SSL verification: Disable (if HTTP)


    GitHub Webhook

    1. GitHub repo → Settings → Webhooks → Add webhook
    2. Payload URL: http://git-bridge.example.com/webhook/github
    3. Content type: application/json
    4. Secret: Match WEBHOOK_GITHUB_SECRET
    5. Events: Just the push event

    Summary

    git-bridge overcomes CodeCommit’s lack of webhook support using EventBridge + SQS, while simultaneously integrating GitLab/GitHub webhooks into a unified mirroring pipeline.

    Key Design Points
    • SQS long-polling for reliable CodeCommit event ingestion (outbound HTTPS only)
    • DLQ for isolating and managing repeatedly failed messages
    • Webhook server integrating GitLab/GitHub events into the same mirror pipeline
    • Provider interface for easy addition of new Git platforms
    • Bidirectional mirroring with loop detection for complex sync scenarios
    • Terraform for reproducible infrastructure as code
    • Slack notifications for real-time mirroring status monitoring
