    Linux eBPF Tracing Guide: System Analysis with bpftrace and BCC

    Trace system calls, analyze disk I/O bottlenecks, and troubleshoot network latency with bpftrace one-liners and BCC tools


    Overview

    In production Linux environments handling heavy traffic, intermittent tail latency spikes, disk I/O bottlenecks, network packet loss, and transient CPU spikes represent the most elusive failure modes. Traditional monitoring tools such as top, vmstat, iostat, and netstat provide averaged statistics over one-second or multi-second intervals. Consequently, they fail to capture microbursts and transient anomalies that emerge and vanish within a few milliseconds. Furthermore, user-space application logs and APM solutions cannot inspect deep operating system bottlenecks, such as kernel scheduling latencies, Virtual File System (VFS) lock contention, or TCP socket backlog queues.

    Extended Berkeley Packet Filter (eBPF) provides an observability breakthrough by allowing engineers to execute sandboxed tracing programs directly inside the Linux kernel without modifying kernel source code or loading dangerous Loadable Kernel Modules (LKMs). While earlier posts covered specialized eBPF platforms—such as Cilium Deep Dive - Advanced eBPF-based Kubernetes Networking and Security, Troubleshooting Kubernetes Networks in Cilium CNI Environments, and Kubernetes Tetragon Guide: eBPF In-Kernel Runtime Security—this guide focuses on the low-level, foundational eBPF toolkits that systems engineers and SREs use directly: bpftrace and bcc (BPF Compiler Collection).

    This guide examines the core eBPF runtime architecture (Verifier, JIT compiler, and BPF maps) alongside kernel and user-space instrumentation mechanisms (kprobe, tracepoint, uprobe, and USDT). It then introduces practical bpftrace one-liners for real-time system call and VFS latency profiling, followed by deep troubleshooting workflows using core bcc utilities (biolatency, biosnoop, tcpretrans, tcpconnlat, and execsnoop). Finally, it details essential operational strategies for mitigating hot-path probe overhead and navigating kernel version requirements.


    eBPF Runtime Architecture and Kernel Instrumentation Mechanisms

    Verifier, JIT Compiler, and BPF Maps

    eBPF programs execute directly within the kernel address space, providing bare-metal execution speed and full access to internal kernel context. However, executing arbitrary code in kernel space carries catastrophic risk: an invalid memory dereference, an out-of-bounds array access, or an accidental infinite loop could trigger an immediate kernel panic, taking down the entire operating system. To eliminate this risk, the Linux kernel enforces a strict verification and compilation pipeline before any program is loaded.

    • BPF Verifier: When eBPF bytecode is loaded via the bpf() system call, the verifier executes comprehensive static analysis. It explores all reachable execution paths in the Control Flow Graph (CFG) to prove that the program halts (no unrolled or unbounded loops), does not dereference invalid memory addresses, initializes all registers before reading, and stays strictly within kernel stack boundaries. Any program that cannot be proven completely safe is rejected immediately.
    • Just-In-Time (JIT) Compiler: Once validated, the bytecode passes through the in-kernel JIT compiler, which translates generic BPF instructions into native machine instructions (x86_64, ARM64, etc.). This ensures instructions run at bare-metal execution speeds without interpreter overhead.
    • BPF Maps: Running eBPF code requires an efficient, safe mechanism to store state and share data with user-space tools (bpftrace, Python BCC scripts, or Go daemons). BPF maps are kernel-managed key-value data structures. They support various specialized layouts—including hash tables, arrays, ring buffers, and per-CPU histograms—enabling atomic in-kernel aggregations and high-throughput asynchronous event streaming.

    Thanks to this pipeline, engineers can attach non-disruptive instrumentation to live production nodes without restarting services, patching binaries, or risking operating system crashes.

    kprobe and uprobe vs tracepoint and USDT

    To bind eBPF programs to system events, the Linux kernel and user space provide four primary instrumentation probe types. Selecting the appropriate probe type is critical for balancing debugging flexibility against production stability and overhead.

    Probe Type Target Layer Mechanism Key Advantages Limitations and Gotchas Representative Use Cases
    kprobe / kretprobe Kernel Space Dynamic Can dynamically hook the entry and return of virtually any non-inlined kernel function Internal kernel symbols and function signatures change across minor kernel updates, breaking scripts VFS latency profiling (vfs_read), kernel mutex lock contention
    tracepoint Kernel Space Static Stable ABI guaranteed by kernel source macros (TRACE_EVENT); minimal execution overhead Limited strictly to locations explicitly instrumented in the upstream kernel source System calls (syscalls), block I/O requests, scheduler context switches
    uprobe / uretprobe User Space Dynamic Hooks arbitrary function entries and returns in user binaries and shared libraries (libc, OpenSSL) Requires user-to-kernel context switching; higher per-event overhead than kernel probes Tracking memory allocations (malloc), tracing unencrypted SSL/TLS plaintext payloads
    USDT User Space Static Pre-defined static tracepoints embedded at binary compile time; stable symbols across versions Target applications must be built with USDT probe flags enabled Tracing internal database transactions (PostgreSQL, MySQL), JVM and Node.js runtimes

    Dynamic probes (kprobe) operate by patching the target function’s first instruction with a software breakpoint or an ftrace jump. When the breakpoint fires, execution traps into the eBPF runtime. While kprobes provide total freedom during ad-hoc root-cause investigations, they are tightly coupled to private kernel implementation details. In contrast, static tracepoints are baked into the kernel source as formal instrumentation APIs. When building ongoing monitoring daemons, prioritizing tracepoints guarantees portability and forward compatibility across kernel upgrades.


    Real-Time System Tracing with bpftrace One-Liners

    Probe, Filter, and Action Syntax and Built-In Variables

    bpftrace is a high-level tracing toolkit featuring a concise Domain-Specific Language (DSL) inspired by AWK and C. It allows engineers to write and execute ad-hoc kernel instrumentation directly from the CLI without managing C toolchains, compilation steps, or Python wrappers.

    The fundamental syntax of a bpftrace probe follows this pattern:

    probe[,probe,...] /filter/ { action }
    • probe: Specifies the target event to trace. Examples include tracepoint:syscalls:sys_enter_openat or kprobe:vfs_read. Multiple probes can be grouped with comma separators.
    • filter: A boolean expression enclosed in slashes (/ /) that gates execution of the action block. For example, /comm == "nginx"/ or /pid == 1234/ isolates events to a specific process.
    • action: A block of semicolon-separated statements executed whenever an event matches the filter. Actions store data in maps, format log messages, or compute statistical distributions.

    Inside action blocks, bpftrace provides powerful built-in variables:

    • pid, tid: Process ID and Thread ID of the executing thread.
    • comm: Name of the current executable file (string).
    • nsecs: Monotonic timestamp in nanoseconds elapsed since boot.
    • retval: Return value of the instrumented function (available in kretprobe and uretprobe).
    • args: Pointer to the static argument structure defined by a tracepoint (e.g., args->filename, args->dfd).
    • @: Prefix for kernel-managed BPF associative arrays (maps).

    Syscall Frequency Aggregation and File Open Tracing

    The power of bpftrace shines when aggregating system-wide behavior into concise histograms or frequency tables in real time.

    The following one-liner aggregates all system calls executed across the system, categorized by process name:

    bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'

    This command hooks the raw_syscalls:sys_enter tracepoint, which intercepts every system call entry point. It increments an in-kernel counter in a BPF map keyed by the executable name (comm). When terminated with Ctrl+C, bpftrace automatically prints the map sorted in ascending order. If an unexpected background utility or malfunctioning daemon is overwhelming the CPU with excessive system calls, this one-liner identifies it in seconds.

    To inspect which specific files are being opened by processes on the system, trace the openat system call:

    bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%-6d %-16s %s\n", pid, comm, str(args->filename)); }'

    Here, args->filename accesses the path pointer passed to openat. The built-in str() function safely copies the string from user space into the BPF buffer. This immediately exposes rogue scripts opening unexpected configuration files or unindexed directories.

    Measuring VFS Read Latency Histograms

    When evaluating filesystem performance, average latency numbers can be deceiving. If 99% of read operations finish within 0.1 milliseconds while 1% take 500 milliseconds due to lock contention or disk saturation, the average latency remains low while client-facing tail latency degrades drastically.

    The following bpftrace command hooks into the Virtual File System layer (vfs_read) to compute a power-of-two latency distribution histogram for each process:

    bpftrace -e 'kprobe:vfs_read { @start[tid] = nsecs; } kretprobe:vfs_read /@start[tid]/ { @[comm] = hist((nsecs - @start[tid]) / 1000); delete(@start, tid); }'

    The execution flow operates as follows:

    1. When vfs_read enters, kprobe:vfs_read records the entry time (nsecs) into the @start map keyed by the thread ID (tid).
    2. When the read completes, kretprobe:vfs_read triggers. The filter /@start[tid]/ verifies that a corresponding start timestamp exists for this thread.
    3. The elapsed time is calculated, converted to microseconds ((nsecs - @start[tid]) / 1000), and added to a log-scale histogram bucket using hist().
    4. The entry is immediately evicted with delete(@start, tid) to prevent unbounded memory growth in the BPF map.

    The resulting output displays a clear ASCII histogram:

    @[mysqld]: 
[4, 8)               124 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@                    |
[8, 16)              185 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@    |
[16, 32)              52 |@@@@@@@@@@@@@                                       |
[32, 64)               8 |@@                                                  |
[64, 128)              2 |                                                    |
[128, 256)             0 |                                                    |
[256, 512)             1 |                                                    |

    The histogram distribution clearly highlights a tail latency anomaly: while most reads complete within 16 microseconds, an outlier required between 256 and 512 microseconds, pointing to filesystem allocation delays or underlying device queues.


    Troubleshooting with BCC Tools

    While bpftrace excels at rapid, ad-hoc CLI investigations, the BPF Compiler Collection (BCC) provides a rich suite of pre-packaged, production-tested diagnostic tools. Written in Python and C, BCC utilities offer extensive command-line flags and deep kernel event instrumentation.

    Diagnosing Storage I/O Bottlenecks with biolatency and biosnoop

    Standard storage utilities like iostat -xz 1 aggregate average request sizes and average service times (await). However, they cannot reveal whether individual block I/O requests are stalling at the hardware device driver layer. biolatency fills this void:

    sudo biolatency -m 1 5

    This command tracks block device I/O from the moment a request is issued to the device driver until hardware completion, outputting a millisecond-scale (-m) latency distribution every second for 5 intervals:

    Tracing block device I/O... Hit Ctrl-C to end.

     msecs               : count     distribution
         0 -> 1          : 4210     |****************************************|
         2 -> 3          : 312      |**                                      |
         4 -> 7          : 45       |                                        |
         8 -> 15         : 12       |                                        |
        16 -> 31         : 3        |                                        |
        32 -> 63         : 0        |                                        |
        64 -> 127        : 1        |                                        |

    While over 4,000 requests complete in under 1 millisecond, a single request stalled for between 64 and 127 milliseconds. To identify the exact process and disk sector responsible for that stall, run biosnoop alongside it:

    sudo biosnoop

    biosnoop logs individual block I/O operations in real time:

    TIME(s)     COMM           PID    DISK    T  SECTOR     BYTES  LAT(ms)
0.000000    kworker/u16:2  342    nvme0n1 W  12582912   4096      0.21
0.002145    mysqld         1842   nvme0n1 W  84920448   16384     0.85
0.015241    backup.sh      29104  nvme0n1 R  49152000   1048576  68.42

    The output reveals the culprit: a background backup script (backup.sh, PID 29104) issued a large 1MB sequential read on sector 49152000, creating a 68.42ms queue stall for concurrent database writes.

    Retransmits and Connect Latency with tcpretrans and tcpconnlat

    Packet loss and TCP retransmissions trigger severe latency degradation and connection timeouts in distributed microservices. Standard counters in netstat -s indicate that retransmissions are accumulating, but they provide no context regarding which remote IP, port, or connection state triggered the loss.

    tcpretrans hooks into the kernel’s tcp_retransmit_skb function, emitting connection details the instant a retransmission occurs:

    sudo tcpretrans -l

    The -l (--lossprobe) flag monitors both standard TCP retransmissions and Tail Loss Probe (TLP) events (local port and socket state are included in standard output even without options):

    TIME     PID IP LADDR:LPORT         T> RADDR:RPORT          STATE
14:20:15 0   4  192.0.2.10:48210    R> 198.51.100.25:443    SYN_SENT
14:20:16 0   4  192.0.2.10:48210    L> 198.51.100.25:443    SYN_SENT
14:20:18 5124 4 192.0.2.10:39422    R> 203.0.113.80:8080    ESTABLISHED
    • Retransmissions in SYN_SENT: The host sent an initial SYN packet to 198.51.100.25:443 but received no SYN-ACK. This points to routing failure, remote host outage, or a firewall/security group dropping packets silently.
    • Retransmissions in ESTABLISHED: The connection was established, but transmitted data was lost in flight due to network switch buffer overflow or intermediate link congestion.

    To measure outbound connection establishment latency directly, use tcpconnlat:

    sudo tcpconnlat

    tcpconnlat calculates the exact time elapsed between sending an outbound TCP SYN and receiving the corresponding SYN-ACK (the 3-way handshake round-trip latency):

    PID    COMM         IP SADDR            DADDR            DPORT LAT(ms)
2104   curl         4  192.0.2.10       198.51.100.50    443   145.21
8921   node         4  192.0.2.10       203.0.113.12     3306  1.12

    Here, connections to the internal MySQL database (203.0.113.12:3306) establish in 1.12ms, while connections to an external third-party API (198.51.100.50:443) take 145.21ms, pinpointing the network latency source immediately.

    Finding Short-Lived Processes with execsnoop

    Servers occasionally suffer from recurring CPU usage spikes where top and ps show no offending processes. This symptom typically stems from high rates of short-lived processes (fork-and-exec churn) that run and terminate within a few milliseconds.

    execsnoop monitors the sys_enter_execve system call to trace every newly spawned process across the entire operating system:

    sudo execsnoop -t

    The -t flag prepends a timestamp in seconds elapsed since tracing began (Note: -T outputs the HH:MM:SS time format):

    TIME(s)  PCOMM            PID    PPID   RET ARGS
0.001    crond            1205   1        0 /bin/sh /opt/scripts/healthcheck.sh
0.004    healthcheck.sh   1206   1205     0 /usr/bin/curl -s http://127.0.0.1:8080/health
0.012    healthcheck.sh   1207   1205     0 /usr/bin/grep healthy
0.015    healthcheck.sh   1208   1205     0 /usr/bin/awk {print $2}

    The output reveals the root cause: crond executes an unoptimized shell script every second, repeatedly spawning child shells and CLI binaries (curl, grep, awk) and wasting significant CPU cycles on fork overhead.


    Production Deployment and Overhead Management

    BCC vs bpftrace vs CO-RE (libbpf)

    When introducing eBPF tooling into production, teams must evaluate the underlying compilation models and runtime dependencies of each architecture.

    Dimension BCC (BPF Compiler Collection) bpftrace libbpf + BPF CO-RE
    Compilation Timing On target host at runtime (Clang / LLVM) On target host at execution time (lightweight AST) Ahead of time on build host (pre-compiled binary)
    Host Dependencies Kernel headers (linux-headers), Python, LLVM/Clang runtime bpftrace binary, BTF support or kernel headers BTF-enabled kernel (/sys/kernel/btf/vmlinux) only
    Resource Footprint High: tens to hundreds of megabytes memory spike and multi-second compilation delay per tool invocation Moderate: Lightweight interpreter consuming a few megabytes of memory Minimal: Standalone binary, instant load time in microseconds
    Primary Operational Scope Legacy systems, in-depth offline analysis, custom Python scripting Ad-hoc terminal troubleshooting, interactive one-liner profiling Continuous production monitoring agents and enterprise security daemons

    Early BCC utilities required installing the full LLVM/Clang compiler toolchain and kernel development headers on every production node. Each time a tool launched, it parsed hundreds of megabytes of C headers, causing noticeable CPU and memory surges.

    To eliminate this operational friction, modern Linux kernels adopt BPF CO-RE (Compile Once – Run Everywhere) powered by libbpf and BPF Type Format (BTF). BTF embeds compact type and layout metadata directly into the kernel image (/sys/kernel/btf/vmlinux). With CO-RE, eBPF programs are compiled ahead-of-time on a build machine. When loaded on a target host, libbpf automatically relocates struct field offsets using the target’s BTF data. For production monitoring, bpftrace serves as the preferred ad-hoc triage tool, while libbpf + CO-RE represents the production standard for background observability daemons.

    Hot Paths, Map Leaks, and Kernel Versions

    Although eBPF operates safely within an in-kernel sandbox, poorly designed instrumentation can still degrade system performance. Adhering to the following rules ensures safe production tracing:

    • Avoid dynamic kprobes on extreme hot paths: Hooking functions executed millions of times per second—such as packet ingress routines (napi_gro_receive, tcp_v4_rcv) or core scheduler context switches—with dynamic kprobes causes measurable overhead. Instruction replacement and breakpoint trap handling can introduce a 5% to 15% CPU penalty. For hot-path instrumentation, utilize hardware PMU counters or filtered, static tracepoints.
    • Prevent BPF map memory leaks: When calculating latency by pairing a kprobe (start timestamp) with a kretprobe (completion time), unexpected error returns or interrupted execution can leave stale keys in the map. Always call delete() explicitly in kretprobes and monitor map capacity to avoid memory leaks.
    • Verify kernel requirements and BTF support: Modern eBPF features require Linux LTS 4.19 or higher. For full BPF CO-RE and BTF support, Linux 5.4+ with CONFIG_DEBUG_INFO_BTF=y is recommended.


    Conclusion

    eBPF transforms Linux systems observability by providing non-disruptive, real-time insight into kernel and hardware operations that traditional metrics tools cannot reach:

    • bpftrace offers a concise, AWK-inspired CLI DSL for rapidly capturing system call rates, tracing file access patterns, and visualizing VFS read latencies in logarithmic histograms.
    • bcc tools (biolatency, biosnoop, tcpretrans, tcpconnlat, and execsnoop) uncover the root causes behind storage I/O long tails, network packet loss, connection setup latency, and transient process churn.
    • For production deployment, engineering teams must avoid dynamic probes on high-frequency hot paths, prevent BPF map memory leaks, and migrate toward BPF CO-RE (libbpf) architecture to achieve zero-overhead, portable in-kernel observability.
