    Multus CNI: Multi-Homed Pods with Macvlan, SR-IOV, and PBR

    Connecting secondary network interfaces to Pods using NetworkAttachmentDefinition, Whereabouts IPAM, and policy-based routing


    Overview

    In standard Kubernetes networking, every Pod is provisioned with a single virtual network interface (eth0) connected to a cluster overlay network. This single-IP-per-Pod design simplifies communication across microservices by ensuring that all Pods can communicate without NAT. However, in enterprise environments running high-bandwidth storage synchronization (Ceph, NFS), real-time streaming, telecommunications workloads (VNF/CNF), or regulatory financial networks, a single interface introduces severe throughput bottlenecks and security isolation challenges.

    Multus CNI is a meta-plugin that enables Kubernetes Pods to attach multiple distinct network interfaces (eth0, net1, net2, etc.) simultaneously. Rather than replacing the primary CNI (such as Calico or Cilium), Multus delegates interface creation: it preserves the default overlay network for Kubernetes control traffic while attaching secondary interfaces directly to physical host NICs via Macvlan or binding SR-IOV Virtual Functions (VFs) for near-bare-metal data plane performance.

    This guide explores the Multus CNI meta-plugin architecture and the runtime mechanics of Multus 4.0’s Thick plugin daemon. We will walk through configuring NetworkAttachmentDefinition custom resources with Macvlan, SR-IOV, and Whereabouts distributed IPAM, injecting network annotations into Pod manifests, and resolving production routing pitfalls—specifically default gateway collisions and asymmetric routing with policy-based routing (PBR).


    1. Kubernetes 1-Pod 1-NIC Limitations and the Multus Meta-Plugin Architecture

    Production Bottlenecks and Traffic Isolation in Single-Interface Pods

    Kubernetes adopts the fundamental networking principle that every Pod receives its own IP address and can communicate with any other Pod without Network Address Translation (NAT). Under this model, container runtimes and CNI plugins provision only the loopback (lo) interface and a single virtual ethernet interface (eth0) inside the Pod network namespace. While this abstraction simplifies web applications and microservice architectures, it creates serious constraints for infrastructure and data-heavy workloads.

    A prime issue is contention between storage and application traffic. When distributed storage systems like Ceph RBD, GlusterFS, or high-performance NFS are mounted directly inside a Pod, large backup or replication bursts can saturate the eth0 interface. This bandwidth exhaustion leads to packet loss and latency spikes on customer-facing service APIs sharing that same interface.

    Furthermore, overlay networks using VXLAN or Geneve encapsulation incur CPU processing overhead and reduce MTU sizes, increasing the risk of packet fragmentation. In financial compliance, 5G telecom core networks, and distributed AI/ML training clusters, architectural standards demand that control, storage, and data plane traffic remain physically and logically isolated across dedicated VLANs and physical switches. A single eth0 interface cannot satisfy these physical segmentation requirements.

    Network Plumbing Working Group Standards and Multus Delegation

    To address these limitations, the CNCF Network Plumbing Working Group (NPWG) established the “Kubernetes Network Custom Resource Definition De-facto Standard.” Multus CNI is the reference implementation of this specification.

    Multus does not implement packet forwarding or routing logic itself. Instead, it operates as a meta-plugin that orchestrates and chains other CNI plugins. When kubelet issues a CNI request to set up a Pod sandbox, Multus first delegates to the cluster’s primary CNI to establish eth0. It then parses the Pod’s annotations, resolves the referenced NetworkAttachmentDefinition custom resources, and calls delegate plugins in sequence to attach secondary interfaces (net1, net2, etc.) into the Pod’s network namespace.


    Network Classification Primary Interface (eth0) Secondary Interfaces (net1, net2, ...)
    CNI Role Primary CNI (Calico, Cilium, Flannel) Delegate CNI (Macvlan, SR-IOV, Bridge, IPvlan)
    Traffic Purpose Kubernetes control plane, Service VIPs, Pod-to-Pod overlay High-throughput data plane, dedicated storage, L2 isolated traffic
    IP Management (IPAM) Cluster default IPAM (host subnet pool) Host-local, Whereabouts, Static IPAM
    Requirement Mandatory (core component communication) Optional (injected selectively via Pod annotations)


    When kubelet dispatches a CNI ADD request during Pod creation, Multus inspects configuration files in /etc/cni/net.d/ to provision eth0. It then evaluates the k8s.v1.cni.cncf.io/networks annotation in the Pod manifest, invoking the delegate plugins defined in each NetworkAttachmentDefinition CRD to bind virtual or physical network interfaces into the Pod.


    2. Thick Plugin vs Thin Plugin Runtime Architecture

    Fork-Exec Overhead and API Server Throttling in Thin Plugins

    Earlier versions of Multus CNI (3.x) operated under a traditional CNI execution model known as the Thin Plugin architecture. In this design, kubelet executed /opt/cni/bin/multus as a standalone binary via fork-exec whenever a Pod was created or destroyed.

    On every invocation, the thin binary parsed local kubeconfig files, generated disk I/O, and issued REST queries directly to kube-apiserver to retrieve Pod metadata and NetworkAttachmentDefinition objects.

    In large-scale clusters, this pattern created operational bottlenecks. During node reboots or rapid scale-out events where dozens or hundreds of Pods were scheduled concurrently, the burst of fork-exec processes caused host CPU spikes. Concurrently, hundreds of Multus binaries hammered kube-apiserver with duplicate API queries, triggering client-side throttling and API server rate limits. Consequently, CNI operations frequently exceeded runtime deadlines (Context Deadline Exceeded), leaving Pods stuck in ContainerCreating states.

    Multus 4.0 multus-daemon and multus-shim Unix Domain Socket Architecture

    To resolve these scalability limits, Multus 4.0 introduced the Thick Plugin architecture based on a client-server model.

    The Thick architecture separates responsibilities between multus-daemon, which runs as a cluster DaemonSet on each node, and multus-shim, an ultra-lightweight client binary invoked by kubelet.


    sequenceDiagram autonumber participant K as Kubelet participant S as "multus-shim
    (Client Binary)" participant D as "multus-daemon
    (DaemonSet)" participant C as "Delegate CNI
    (Macvlan / SR-IOV)" K->>S: CNI ADD / DEL request S->>D: Forward payload via Unix Socket (/run/multus/multus.sock) Note over D: Evaluates spec using cached Informer data D->>C: Invoke delegate CNI binary (chrootDir: /hostroot) C-->>D: Interface provisioned & IP assigned D-->>S: Return JSON CNI result S-->>K: Hand off result to Kubelet


    1. Kubelet invokes the lightweight multus-shim binary on the host filesystem.
    2. Rather than executing API queries or heavy logic, multus-shim passes CNI parameters (environment variables and standard input JSON) over a host-mounted Unix domain socket (/run/multus/multus.sock) to multus-daemon.
    3. multus-daemon maintains an in-memory cache of Kubernetes API resources using client-go Informers, eliminating repetitive queries to kube-apiserver.
    4. Using the cached configuration, multus-daemon executes delegate CNI plugins and returns the result through multus-shim to kubelet.

    When delegate plugins require access to host resources (such as Flannel’s /run/flannel/subnet.env or local daemon sockets), the chrootDir: "/hostroot" configuration ensures that binaries execute cleanly in the host root filesystem context.

    Prometheus Metrics and Production DaemonSet Configuration

    The Thick plugin model also introduces observability. An integrated HTTP metrics server within multus-daemon exports Prometheus metrics tracking CNI operation latency, success rates, and failure counts.

    The core daemon configuration file, /etc/cni/net.d/multus.d/daemon-config.json, is structured as follows:

    {
  "chrootDir": "/hostroot",
  "cniConfigDir": "/host/etc/cni/net.d",
  "logToStderr": true,
  "logLevel": "verbose",
  "logFile": "/tmp/multus.log",
  "binDir": "/opt/cni/bin",
  "cniDir": "/var/lib/cni/multus",
  "socketDir": "/host/run/multus/",
  "metricsPort": 9091,
  "cniVersion": "0.3.1",
  "multusConfigFile": "auto",
  "multusAutoconfigDir": "/host/etc/cni/net.d"
}

    In production clusters, deploy the official thick DaemonSet manifest after verifying security contexts and host path mounts:

    kubectl apply -f https://raw.githubusercontent.com/k8snetworkplumbingwg/multus-cni/master/deployments/multus-daemonset-thick.yml

    Once the DaemonSet is running, /run/multus/multus.sock is initialized on each node, and Multus creates /etc/cni/net.d/00-multus.conf to intercept all subsequent network sandbox creation calls.


    3. NetworkAttachmentDefinition CRD and High-Performance Plugins

    Macvlan Mode: Eliminating Overlay Encapsulation Overhead

    Macvlan is a Linux kernel virtualization driver that creates multiple virtual network sub-interfaces, each with a unique MAC address, directly on top of a single physical parent network interface (master). To the physical network switch, each virtual interface appears as a distinct physical endpoint.

    Because Macvlan bypasses overlay encapsulation (such as VXLAN or Geneve tunnels), it eliminates CPU tunneling overhead and packet processing delays, delivering throughput close to physical line rate.

    Secondary network configurations are declared using the NetworkAttachmentDefinition CRD (abbreviated as net-attach-def or nad). Below is a manifest bridging a secondary network across the host’s eth1 physical interface:

    apiVersion: "k8s.cni.cncf.io/v1"
kind: NetworkAttachmentDefinition
metadata:
  name: macvlan-storage-net
  namespace: default
spec:
  config: '{
    "cniVersion": "0.3.1",
    "plugins": [
      {
        "type": "macvlan",
        "capabilities": { "ips": true, "mac": true },
        "master": "eth1",
        "mode": "bridge",
        "ipam": {
          "type": "host-local",
          "subnet": "192.168.100.0/24",
          "rangeStart": "192.168.100.100",
          "rangeEnd": "192.168.100.150",
          "routes": [
            { "dst": "192.168.100.0/24" }
          ]
        }
      },
      {
        "type": "tuning",
        "capabilities": { "mac": true }
      }
    ]
  }'


    Macvlan Host-to-Pod Communication Constraint
    • A fundamental constraint of Macvlan is that the parent (master) interface cannot communicate directly with its child virtual interfaces over Layer 2.
    • Direct packets between the host OS itself and local Pod Macvlan interfaces are blocked by Linux kernel design.
    • Pods on the same node communicate with each other using mode: bridge, and traffic between Pods and external systems or other nodes functions normally.


    SR-IOV Virtual Function Binding for Near-Bare-Metal Performance

    For workloads requiring extreme low latency—such as financial market data, high-frequency trading (HFT), telecom network functions (NFV), and high-throughput storage clusters—even kernel software bridge latency can be prohibitive. In these scenarios, Single Root I/O Virtualization (SR-IOV) provides hardware-level virtualization.

    SR-IOV partitions a physical PCIe network adapter (Physical Function, or PF) into multiple independent Virtual Functions (VFs). Each VF features its own PCIe configuration space and register set, allowing the host kernel to be bypassed entirely and passing hardware-direct networking straight to the Pod.

    In Kubernetes, the sriov-network-device-plugin discovers available VFs and exposes them as node allocatable resources (intel.com/sriov_net). Multus then references a NetworkAttachmentDefinition configured with sriov-cni:

    apiVersion: "k8s.cni.cncf.io/v1"
kind: NetworkAttachmentDefinition
metadata:
  name: sriov-telecom-net
  namespace: default
  annotations:
    k8s.v1.cni.cncf.io/resourceName: intel.com/sriov_net
spec:
  config: '{
    "cniVersion": "0.3.1",
    "type": "sriov",
    "vlan": 200,
    "ipam": {
      "type": "host-local",
      "subnet": "192.168.200.0/24",
      "rangeStart": "192.168.200.10",
      "rangeEnd": "192.168.200.50",
      "routes": [
        { "dst": "192.168.200.0/24" }
      ]
    }
  }'

    When a Pod requesting this resource is scheduled, the kubelet Device Manager allocates an unused VF, and sriov-cni configures VLAN tagging (VLAN 200) and IP addresses before moving the VF directly into the Pod network namespace.

    Host-local vs Whereabouts Distributed IPAM for Cluster-Wide IP Allocation

    Selecting an appropriate IP Address Management (IPAM) plugin is critical for secondary network reliability.

    The standard host-local IPAM records allocated IP addresses only in local node storage (/var/lib/cni/networks/). If multiple worker nodes share a common Layer 2 broadcast domain (the same VLAN and subnet) and use identical host-local IP ranges, nodes cannot track allocations made by peers. This leads to duplicate IP collisions where Pods on different nodes receive the same IP address (e.g., 192.168.100.101).

    While segmenting subnets per node or setting up external DHCP servers can mitigate collisions, both approaches increase operational complexity.

    The Network Plumbing Working Group solves this with Whereabouts, a distributed IPAM CNI plugin. Whereabouts uses Kubernetes custom resources (ippools.whereabouts.cni.cncf.io) as its backing store. By combining distributed locking with IP pool CRDs, it coordinates cluster-wide IP allocations safely without external dependencies.

    apiVersion: "k8s.cni.cncf.io/v1"
kind: NetworkAttachmentDefinition
metadata:
  name: macvlan-whereabouts-net
  namespace: default
spec:
  config: '{
    "cniVersion": "0.3.1",
    "type": "macvlan",
    "master": "eth1",
    "mode": "bridge",
    "ipam": {
      "type": "whereabouts",
      "range": "192.168.100.0/24",
      "range_start": "192.168.100.10",
      "range_end": "192.168.100.200",
      "exclude": [
        "192.168.100.1/32",
        "192.168.100.50/31"
      ],
      "routes": [
        { "dst": "192.168.100.0/24" }
      ]
    }
  }'

    With Whereabouts, Pods scheduled across any number of worker nodes atomically claim unique addresses from the shared 192.168.100.0/24 CIDR pool and return them automatically upon termination.


    4. Pod Network Injection and Runtime Verification

    Text and JSON Declarations with k8s.v1.cni.cncf.io/networks

    To attach secondary networks to a Pod, declare the k8s.v1.cni.cncf.io/networks annotation under metadata.annotations. Multus supports both comma-separated text strings and structured JSON arrays.

    The text format is suitable for simple deployments that draw dynamic IPs from the default pool. Cross-namespace references use the <namespace>/<name> format:

    apiVersion: v1
kind: Pod
metadata:
  name: storage-client-pod
  annotations:
    k8s.v1.cni.cncf.io/networks: macvlan-storage-net, sriov-telecom-net
spec:
  containers:
  - name: app
    image: alpine:3.20
    command: ["sleep", "infinity"]
    resources:
      requests:
        intel.com/sriov_net: '1'
      limits:
        intel.com/sriov_net: '1'

    Custom Interface Naming, Static IPs, and Fixed MAC Addresses

    In production environments, monitoring daemons or application scripts often require deterministic interface names, while firewall rules and licensing servers may require fixed IP and MAC addresses.

    The structured JSON array syntax provides full control over interface parameters (the text format also supports interface naming via the @ syntax):

    apiVersion: v1
kind: Pod
metadata:
  name: database-cluster-pod
  annotations:
    k8s.v1.cni.cncf.io/networks: '[
      {
        "name": "macvlan-storage-net",
        "interface": "storage0",
        "ips": ["192.168.100.88/24"],
        "mac": "02:42:c0:a8:64:58"
      }
    ]'
spec:
  containers:
  - name: db
    image: alpine:3.20
    command: ["sleep", "infinity"]

    With this configuration, Multus overrides the default net1 naming convention, creating an interface named storage0 with the specified static IP (192.168.100.88) and MAC address (02:42:c0:a8:64:58).

    Verifying Network Separation Inside the Container

    Verify interface and address allocation within the running container using ip link and ip addr:

    kubectl exec -it database-cluster-pod -- ip link show

    1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN mode DEFAULT group default qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
2: eth0@if12: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1450 qdisc noqueue state UP mode DEFAULT group default 
    link/ether 52:54:00:12:34:56 brd ff:ff:ff:ff:ff:ff link-netnsid 0
3: storage0@if3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP mode DEFAULT group default 
    link/ether 02:42:c0:a8:64:58 brd ff:ff:ff:ff:ff:ff link-netnsid 0

    Inspect the assigned IP addresses:

    kubectl exec -it database-cluster-pod -- ip addr show

    2: eth0@if12: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1450 qdisc noqueue state UP group default 
    inet 192.0.2.145/24 brd 192.0.2.255 scope global eth0
       valid_lft forever preferred_lft forever
3: storage0@if3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP group default 
    inet 192.168.100.88/24 brd 192.168.100.255 scope global storage0
       valid_lft forever preferred_lft forever

    Here, eth0 retains the cluster overlay address (192.0.2.145/24) for regular Kubernetes service communication, while storage0 is bound to the isolated physical subnet (192.168.100.88/24), establishing a dedicated data path.


    5. Multi-Gateway Collision Prevention and Routing Troubleshooting

    Control Plane Outages Caused by Default Route Overwrites

    The most common and disruptive failure mode in Multus deployments is a default gateway (0.0.0.0/0) collision.

    By default, a Pod’s default route points to eth0. Kubernetes relies on this route for DNS queries to CoreDNS (10.96.0.10), API server communication (10.96.0.1), and kubelet liveness/readiness health probes.

    However, if a secondary NetworkAttachmentDefinition specifies a gateway and injects routes: [{"dst": "0.0.0.0/0"}], or if a Pod manifest includes the default-route parameter, Multus installs a default route pointing out through the secondary interface (net1 or storage0).

    kubectl exec -it database-cluster-pod -- ip route show

    In a misconfigured Pod, the routing table shifts to the secondary interface:

    default via 192.168.100.1 dev storage0 
192.0.2.0/24 dev eth0 proto kernel scope link src 192.0.2.145 
192.168.100.0/24 dev storage0 proto kernel scope link src 192.168.100.88


    Default Route Overwrite Hazard
    • When the default route shifts to the external gateway (192.168.100.1), requests for CoreDNS (10.96.0.10) or the Kubernetes API server VIP (10.96.0.1) exit via storage0 rather than eth0.
    • External physical routers discard these packets because they have no route for internal cluster VIPs.
    • In-cluster DNS resolution fails, API server connectivity drops, kubelet health checks time out, and Pods enter CrashLoopBackOff.


    Explicit Subnet Routing and Controlling Default Routes

    To prevent route collisions, follow this core principle:

    Never configure a 0.0.0.0/0 default route in secondary CNI configurations. Restrict secondary IPAM routing rules to explicit destination CIDRs.

    Declare explicit subnets in the NetworkAttachmentDefinition IPAM configuration:

    "ipam": {
  "type": "whereabouts",
  "range": "192.168.100.0/24",
  "routes": [
    { "dst": "192.168.100.0/24" },
    { "dst": "198.51.100.0/24", "gw": "192.168.100.1" }
  ]
}

    This preserves the Pod routing table:

    default via 192.0.2.1 dev eth0 
192.0.2.0/24 dev eth0 proto kernel scope link src 192.0.2.145 
192.168.100.0/24 dev storage0 proto kernel scope link src 192.168.100.88 
198.51.100.0/24 via 192.168.100.1 dev storage0

    All general internet and cluster control plane traffic exits through eth0, while only packets targeting the external storage subnet (198.51.100.0/24) are routed through the storage0 gateway.

    If a specialized network appliance Pod genuinely requires the secondary interface to serve as its default internet gateway, declare default-route explicitly in the JSON annotation and manually add static routes back to the cluster Service CIDR and Pod CIDR through the eth0 gateway.

    Policy-Based Routing and Preventing Asymmetric Routing Drops

    Another common multi-NIC trap is asymmetric routing.

    Consider an external client initiating a TCP handshake to the Pod’s secondary interface IP (192.168.100.88). The Pod receives the TCP SYN on storage0. However, when generating the response (SYN-ACK), if the client IP lies outside the local subnet, the Linux kernel evaluates the default routing table and forwards the packet out through eth0.


    The Asymmetric Routing Trap: Incoming requests hit storage0 (192.168.100.88), but return SYN-ACK packets follow the default routing table out through eth0 (192.0.2.145). Stateful firewalls or Linux kernel reverse path filtering (rp_filter) drop the mismatched connection immediately.


    Because the response originates from 192.0.2.145 instead of 192.168.100.88—or traverses a path with stateful firewalls enforcing Reverse Path Filtering (rp_filter)—the packet is dropped and the TCP connection fails.

    To ensure symmetrical packet flow, implement Policy-Based Routing (PBR) by routing outbound packets according to their source IP address.

    Configure policy rules inside the container via an entrypoint script or an init container:

    # 1. Define a routing table dedicated to the secondary interface (table 100)
ip route add 192.168.100.0/24 dev storage0 proto kernel scope link src 192.168.100.88 table 100
ip route add default via 192.168.100.1 dev storage0 table 100

# 2. Direct all packets originating from the storage0 IP to evaluate table 100
ip rule add from 192.168.100.88/32 table 100

    With this rule active, any response packet originating from 192.168.100.88 evaluates table 100 and exits symmetrically through storage0 and its associated gateway.

    Additionally, ensure that the host OS kernel parameter rp_filter is not set to strict mode. If /proc/sys/net/ipv4/conf/all/rp_filter is set to 1 (strict), the kernel drops packets arriving on an interface if the reverse path would not route back through that same interface. On multi-homed nodes, adjust this parameter to 2 (loose mode) to avoid unexpected packet drops.


    Conclusion

    As Kubernetes expands into data-intensive computing, distributed storage, and telecommunications network functions, overcoming the constraints of single-interface networking becomes essential.

    Key takeaways from this architecture:

    1. Meta-Plugin Delegation: Multus CNI preserves the primary CNI (eth0) for cluster control and service VIP traffic while delegating secondary interfaces (net1, storage0) to specialized plugins.
    2. Thick Plugin Efficiency: Multus 4.0’s multus-daemon and multus-shim architecture eliminates kube-apiserver query storms and fork-exec overhead through in-memory caching and Unix domain sockets, while exposing native Prometheus metrics.
    3. Data Plane Acceleration: Macvlan removes overlay encapsulation overhead, and SR-IOV bypasses the kernel entirely to deliver near-bare-metal line-rate performance, complemented by Whereabouts for coordinated cluster-wide IPAM.
    4. Production Routing Resilience: Avoid configuring secondary default routes (0.0.0.0/0) to safeguard cluster DNS and API server connectivity, and employ Policy-Based Routing (PBR) with loose rp_filter to prevent asymmetric routing drops.
