개별 저장소(Repo)의 CI 잡마다 Alpine 베이스에 필수 도구(helm·helmfile·kubectl·crane·aws-cli)를 매번 설치해 빌드 환경 프로비저닝에 평균 5분이 소요되었습니다. 또한 도구 버전이 저장소별로 파편화되어 신규 버전 반영 시 전수 수정이 필요했고, :latest 태그 의존으로 인해 빌드 재현성과 보안 취약점 추적이 어려웠습니다.
접근 전략
  • Layer 1 (Mirror): 외부 레지스트리(Docker Hub, GHCR)의 도구 이미지를 Multi-arch 매니페스트를 유지한 채 crane copy로 사내 Harbor에 미러링해 외부 의존성 제거
  • Layer 2 (Custom): Layer 1을 기반으로 사전 빌드된 공용 이미지(helmfile-tools, base-tools, node-build, rclone-backup, aws-cli-tools)를 구성해 개별 저장소가 이미지 태그 지정만으로 도구를 즉시 활용하도록 표준화
  • 버전 관리 체계 (SSOT): 공용 빌드 템플릿(.toolchain_build_custom)과 중앙 버전 변수(TOOLCHAIN_*_TAG)를 정의해 하위 저장소가 개별 도구 태그를 직접 추적하지 않도록 일원화
  • 공용 CI 템플릿 모듈화: 개별 복사해 쓰던 CI 잡을 공용 템플릿 저장소로 통합하고 include 방식으로 참조. 공용 앵커(git·ssh·rules·job-config)와 주요 잡(정적 키 없는 AWS 인증, Kaniko 빌드, ArgoCD 배포, 백업)을 중앙에서 관리해 설정 드리프트(Configuration Drift) 원천 제거
  • 자동 버전 사이클 구축: Upstream 신규 버전 감지부터 하위 전파까지 자동화하되, 파이프라인 실행과 Tier 2 MR 승인 단계에 사람의 검증 게이트(Human-in-the-loop)를 배치해 안정성 확보:
       · (1) Upstream 신규 버전 감지 (주간 스케줄러)
       · (2) Layer 1 미러링 자동 MR 생성
       · (3) Layer 2 리빌드 및 중앙 버전 변수 동기화 자동 MR 생성
       · (4) 하위 저장소(Consumer Repos) 대상 일괄 자동 전파 (template provider repo 제외)
트러블슈팅
  • 도구 간 버전 충돌로 인한 툴체인 빌드 실패: 자동 버전 상향 중 helmfile 1.5.1의 최소 요구 사양(helm 3.18.6 이상)과 기존 고정 버전(helm 3.16.4) 간의 불일치로 build_custom 빌드 파이프라인 장애 발생
  • 원인 및 해결: 도구 간 상호 의존성은 upstream 릴리스 노트 외에 사전 자동 감지가 불가능하다고 판단. helm·helmfile·kubectl에 minor-guard를 도입해 동일 minor 내 patch 버전만 자동 상향되도록 통제하고, minor·major 변경은 호환성 검증 후 수동 승격하도록 분리(*_TARGET_MINOR 환경 변수를 통한 1회성 계획적 오버라이드 지원)

문제

접근 전략

  • 선언적 클러스터 관리 전환 (ECK Operator): 공식 Helm 차트의 업데이트 정체(2년 이상) 문제를 해결하고자 ECK Operator를 도입하고, CRD 기반의 선언적 라이프사이클 관리 체계 구축
  • 클라우드(EKS) 확장 및 키리스(Keyless) 자동화: 온프레미스 스택을 AWS EKS 환경에 맞춰 템플릿화해 배포하고, 인덱스 수명주기(ILM) 및 S3 스냅샷 백업 경로에 IRSA를 적용해 정적 자격증명 없이 자동화
트러블슈팅
  • ECK Admission Webhook 다운그레이드 거부로 인한 복구 장애: 온프레미스 Elastic Stack 신규 버전 자동 갱신 중 릴리스 피드에는 등록되었으나 레지스트리에 미배포된 이미지를 참조해 ImagePullBackOff 발생. 즉각 롤백을 시도했으나 ECK Admission Webhook의 다운그레이드 거부 정책으로 복구가 차단되며 Operator 장애로 확산
  • 원인 분석 및 개선: 단순 배포 실패보다 '롤백 불능 상태'를 핵심 운영 리스크로 정의. 업그레이드 파이프라인에 이미지 레지스트리 실존 사전 검증, 클러스터 헬스 체크, 메이저 버전 상향 시 스냅샷 백업 경고, Webhook 제약을 고려한 안전 롤백 절차를 체계화해 재발 방지
성과

기여도 100% (단독 설계 및 표준 절차를 자동화 스크립트로 코드화해 팀 내 재사용) 2025.12 ~ 현재
안정적인 클러스터 운영을 위해 모니터링과 Kubernetes 업그레이드·Helm 관리를 자동화하고, 네트워크 컨트롤러를 Gateway API로 전환했으며, 스토리지 병목 해소와 배포/업그레이드 파이프라인 정비까지 이어갔습니다.
이어서 클러스터 밖 사내 시스템 전반의 백업·복구 체계와, 오래 정체되어 있던 사내 GitLab 메이저 업그레이드까지 함께 맡았습니다.
5-1. 모니터링 & 알림 고도화 (2025.12 ~ 현재)
kube-prometheus-stack 기반 커스텀 알림과 Grafana 대시보드를 설계하고 DB·Node Exporter·Cilium 메트릭을 통합했습니다. 알림 규칙을 컴포넌트 그룹 및 심각도(severity)별로 세분화하고, 상위 알림 발생 시 하위 알림을 억제(inhibit)해 동일 장애의 중복 통보를 차단했습니다.
이후 클러스터 외부에서 CRD가 삭제되어 Prometheus 자체가 중단되었음에도 인지하지 못했던 장애를 계기로, 감시자가 감시 대상과 같은 장애 도메인 안에 있으면 함께 실패한다는 구조적 한계를 도출하고, 클러스터 외부 Bastion의 cron watchdog이 5분 주기로 모니터링 스택의 생존을 능동 점검하도록 구성했습니다(클러스터 내부 CronJob 방식은 감시 대상과 운명을 공유하므로 기각).
5-2. Kubernetes 업그레이드 자동화 & Helm 차트 관리 프레임워크 (2025.12 ~ 현재)
Kubespray 업그레이드 절차와 업그레이드 후 9개 필수 검증 항목(노드·etcd·API Server·인증서 만료 등)을 스크립트화하고, Helm 프레임워크 및 표준 템플릿 동기화로 버전 관리를 표준화해 검증 시간을 90% 단축하고 인증서 갱신 자동화로 만료 장애를 원천 제거했습니다.
5-3. Ingress-nginx → NGINX Gateway Fabric(NGF) 마이그레이션 (2026.04)
온프레미스의 다중 ingress-nginx 인스턴스를 NGF 2.x 단일 컨트롤플레인과 클래스별 Gateway CR로 통합 전환했습니다. MetalLB IP를 유지해 기존 DNS와 방화벽을 그대로 둔 채 사고 없이 cutover를 마쳤고(클래스당 30~60초), Wildcard 인증서 통합 적용으로 수동 갱신 공수를 50% 절감했습니다.
5-4. 스토리지 성능 최적화: etcd / DB SSD 마이그레이션 및 빌드 I/O 격리 (2주, 2026.04 ~ 2026.05)
GitLab Runner(buildx)의 디스크 I/O 급증으로 HDD 기반 etcd 및 게임 DB에 초 단위 지연이 발생하는 병목을 진단하고, Control Plane과 DB 워커를 SSD로 이전함과 동시에 빌드 워크로드를 별도 물리 서버의 전용 VM으로 완전 격리해 게임 DB COMMIT 지연을 9~14초에서 ms 단위로 정상화하고, 빌드 중 인게임 접속 불가 및 서비스 지연 장애 0건을 달성했습니다.
5-5. Kubernetes 인프라 배포 자동화 및 멀티클러스터 GitOps(ArgoCD) 전환 (2026.03 ~ 현재)
문제 정의
Shell/awk 기반의 인프라 모노레포는 복잡한 YAML 조작과 환경별 분기 처리의 한계로 테스트 자동화가 불가능했고, CI 러너 중심의 Push 배포(helmfile apply)는 클러스터 상태 드리프트(Drift) 감지 불가 및 멀티클러스터 확장의 한계가 존재했습니다.
접근 전략
  • Python 표준 라이브러리 기반 툴링 리팩토링: 서드파티 패키지 의존성을 배제한 Python3 모듈화 및 모듈별 1:1 단위 테스트(unittest) 체계를 도입해 로컬·CI 러너 간 실행 일관성 확보
  • 단계별(Wave) 배포 및 업그레이드 자동화: 컴포넌트 의존성에 따른 6단계 Wave 배포 체계를 수립하고, 차트 신버전 감지 시 Values diff 및 호환성 검증을 포함한 MR 자동 생성 파이프라인 구축
  • ArgoCD Pull-GitOps 컨트롤플레인 전환: ApplicationSet(Matrix/Git Generator)으로 온프레미스·AWS 배포를 자동화하고, 기존 Helm 릴리스를 리소스 재생성 없이 ArgoCD 관리 상태로 무중단 이관(Adoption)
  • GitOps 거버넌스 및 안전장치 수립: 최상위 계층 연쇄 삭제 방지(Cascading Prune 차단) 및 AppProject 허용 목록(Whitelist)을 적용해 장애 영향 범위(Blast Radius) 격리
주요 성과
  • 온프레미스·AWS 멀티클러스터 플랫폼 릴리스를 단일 GitOps 컨트롤플레인에서 선언적으로 중앙 통제
  • 레거시 Shell 스크립트를 단위 테스트가 보장된 Python 툴링으로 전면 마이그레이션해 배포 안정성 확보
  • 차트 업그레이드 MR 자동화 및 Wave 배포를 통해 인프라 운영 오버헤드 대폭 감축
  • 선언형 형상 자동 복구(Self-healing) 및 계층별 Prune 통제로 대규모 삭제 사고 위험 원천 차단
5-6. 백업·복구(DR) 체계 구축과 복구 검증 (2026.08 ~ 2026.09)
사내 시스템 8곳과 NAS 경로 2곳의 백업·복구 체계를 구축하고, 단순 '백업 수행'이 아닌 '실제 복구 가능 여부'를 기준으로 검증 프로세스를 정립했습니다. DB 덤프가 중간에 잘린 채로도 백업 작업이 정상 종료(Exit code 0)로 기록되어 실제 복원 시 실패하던 잠재 결함을 사전에 발견해 수정했고, 검증 기준을 '스크립트 실행 완료'에서 '복구된 데이터의 정합성 확인'으로 옮겨 재해 복구의 실질적 신뢰성을 확보했습니다.
5-7. 사내 GitLab 이원화 및 레거시 메이저 업그레이드: 21 hop 경로 (2024.10 신규 구축 / 2026.08 ~ 2026.09 업그레이드 6일)
입사 직후 신규 베어메탈 GitLab을 구축해 신규 프로젝트의 소스 저장소로 삼고, 필요한 기존 저장소는 GitLab mirroring으로 이관했습니다. 구 GitLab(컨테이너)은 백업·외부 노출 역할로 남기고, 두 인스턴스는 자체 개발한 git-bridge로 상시 동기화합니다.
이후 정체되어 있던 구 GitLab을 공식 업그레이드 경로를 따라 6일간 21회 hop으로 끌어올렸습니다. 버전을 건너뛰지 않고 경로를 그대로 밟은 것은, 중간 버전이 수행하는 마이그레이션을 건너뛰면 복구 경로가 사라지기 때문입니다. 첫 hop 다운타임 약 6분 30초(1회성 볼륨 이동 포함), 업그레이드 이후 야간 DR 복제본 123G → 39G(−68%).
프로젝트 6: 인프라 보안 및 거버넌스 체계 구축
기여도 100% (설계, 배포, SSO 연동) 2026.04 ~ 현재
파편화되어 있던 계정 인증·시크릿 관리·원격 접근 경로를 표준화하여 사내 보안 거버넌스를 일원화했습니다.
6-1. 중앙 인증(SSO/OIDC) 체계 일원화 (Keycloak Operator, 2026.04 ~ 현재)
사내 도구(Harbor·ArgoCD·Vaultwarden)마다 개별 연동되어 파편화되었던 GitLab OIDC 인증 경로를 Keycloak Operator 기반 중앙 IdP로 통합. GitLab Group → Keycloak Group Mapper → ArgoCD Role로 이어지는 권한 흐름을 일원화해 인증 정책 중앙 통제 및 단일 로그인(SSO) 환경 구축
6-2. 시크릿 거버넌스 수립: Vaultwarden · GitOps Secrets (2026.04 ~ 현재)
메일·메신저 등에 흩어져 있던 사내 공용 패스워드를 Kubernetes 기반 Vaultwarden으로 이관하고 SSO를 연동해 중앙 관리 체계 확립. 또한 Git에 평문 커밋되던 DB 접속 정보를 External Secrets Operator(AWS Secrets Manager 연동)로 전환하고, Harbor 클러스터 시크릿을 Sealed Secrets로 표준화하여 GitOps 환경의 자격증명 노출 취약점 원천 차단
6-3. 사내망 보안 원격 접속 환경 구축 (OpenVPN PKI, 2026.07)
동시 접속 50명 규모의 온프레미스 사내망 VPN 게이트웨이를 PKI 기반으로 구축하고, 사용자별 인증서 발급·폐기 전 과정을 멱등 셸 스크립트로 자동화
프로젝트 7: AWS EKS 프로덕션 게임 런칭 플랫폼 구축 (신규 외부 퍼블리싱 게임)
기여도 100% (단독 설계·구축·운영) 2026.06 ~ 현재 (구축·운영 중)
신규 외부 퍼블리싱 게임의 상용 런칭을 위해 그린필드 EKS 프로덕션 환경을 단독 구축하고(7-1), 분산 추적(7-2)과 Canary 무중단 배포(7-3)를 보강해 소프트 런칭(7-4)까지 운영했으며, 실트래픽 위에서 SLI/SLO·에러 버짓(7-5)과 게임 CDN 엣지 보안(7-6)을 더했습니다.
7-1. 그린필드 EKS 프로덕션 인프라 구축 및 실트래픽 최적화 (2026.06 ~ 현재)
문제 정의
온프레미스 단일 클러스터 환경은 글로벌 트래픽 대응과 유연한 오토스케일링에 한계가 있어, 해외 상용 런칭을 위한 독립적인 고가용성 EKS 프로덕션 아키텍처 수립이 필요했습니다.
접근 전략
  • 하이브리드 멀티클러스터 및 선언적 관리: 그린필드 EKS 클러스터를 신설하고, 플랫폼 컴포넌트 전반을 GitOps(ArgoCD)로 선언적 일원화 관리
  • Karpenter 기반 컴퓨트 분리 최적화: 게임 서비스는 On-Demand 노드로 안정성을 담보하고, CI 러너는 ARM 다중 패밀리 Spot 풀로 다변화해 비용 절감 및 인스턴스 회수율 최소화
  • 네트워킹·인증 자동화: AWS Load Balancer Controller, ExternalDNS, Wildcard ACM을 연계해 Ingress 및 TLS 인증서 발급 전 과정을 자동화하고, 전체 ServiceAccount에 Pod Identity/IRSA를 적용해 정적 IAM 키 제거
  • 로깅·시크릿 기반 구축: eck-operator 기반 HA EFK 스택(3노드 3-AZ, EBS gp3, S3 스냅샷 SLM)과 External Secrets Operator를 도입해 신규 클러스터의 로그 수집·시크릿 참조 경로 확보
  • 배포 경로 자격증명 격리: 클라이언트 아티팩트는 Jenkins → S3 → CloudFront 파이프라인으로 전송하고, 서버 매니페스트는 S3 중계 및 SSM SendCommand를 통해 Bastion EFS에 원격 전달(SSH 키 상시 보관 배제)
트러블슈팅
  • Karpenter 노드 축소와 게임 세션 보호 양립: 노드 회수 완전 차단(karpenter.sh/do-not-disrupt)은 유휴 비용을 유발하므로 배제하고, 세션이 Redis로 외부화된 Stateless 구조를 활용해 preStop drain + PDB(minAvailable: 1) + Disruption Budget(nodes: 1) 조합으로 1노드씩 안전한 순차 축소 달성
  • 롤링 배포 후 유휴 노드 미회수 개선: 메모리 Request 과다 설정(실측 101MiB 대비 2GiB)으로 발생한 노드 간 점유 불균형(92% vs 35%) 및 자동 축소 실패를 진단. Request를 512MiB로 현실화하고 Consolidation 조건을 조정해 빈패킹(Bin-packing) 밀도와 자동 노드 회수 정상화
  • 신규 Pod 기동 중 트래픽 유입 차단: Pod 기동 중 ALB가 트래픽을 선제 전달해 발생하던 간헐적 5xx 에러를 ALB Pod Readiness Gate 도입으로 해결. Target Group 헬스체크 통과 후에만 Pod를 Ready로 판정하도록 제어
주요 성과
  • 해외 런칭을 위한 독립 AWS 하이브리드 멀티클러스터 구축 및 플랫폼 매니페스트 100% GitOps 선언적 관리 확립
  • Bastion SSH 키를 비롯한 인프라 전반의 정적 자격증명 완전 제거
  • 프로덕션과 심사용 워크로드를 단일 NodePool로 통합해 풀 분리 시 풀마다 기본 점유하던 최소 1노드의 비용 낭비 제거 및 bin-packing 밀도 극대화
  • GitOps 매니페스트 및 CI/CD 전환 절차를 표준 런북으로 문서화하여 팀 내 인수인계 및 동일 환경 재구축이 가능하도록 함
7-2. OpenTelemetry 엔드투엔드 분산 추적 파이프라인 (OTel + Tempo, 2026.06 ~ 현재)
문제 정의
기존 관측 체계(EFK 로깅, Prometheus 메트릭)만으로는 마이크로서비스 간 호출 흐름과 지연 시간(Latency) 병목 구간, 분산 환경의 에러 전파 경로를 파악하는 데 한계가 있었습니다.
접근 전략
  • 추적 스택 및 무침습 계측 환경 구축: AWS EKS에 OpenTelemetry Collector와 Grafana Tempo(S3 백엔드, EKS Pod Identity로 정적 키 없이 연동)를 구축하고, OTel Operator Auto-instrumentation으로 애플리케이션 코드 수정 없이 언어별 SDK 주입
  • 샘플링 지점 분리를 통한 관측 정확도·스토리지 비용 최적화: RED 메트릭은 샘플링 전 100% Span에서 추출해 집계 정확도를 보장하고, 저장은 Tail Sampling(에러 전체 + 500ms 초과 요청 + 정상 요청 10%)으로 스토리지 비용 절감

접근 전략
