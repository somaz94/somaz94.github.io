7-1. 그린필드 EKS 프로덕션 인프라 구축 및 실트래픽 최적화 (2026.06 ~ 2026.11)
문제
제품마다 AWS 계정을 따로 두는 원칙에 따라 신규 외부 퍼블리싱 게임은 새 계정에서 해외 상용 런칭을 해야 했습니다. 그래서 기존 클러스터에 올리지 않고, 그 계정에 고가용성 EKS 프로덕션 환경을 처음부터 구축했습니다.
접근 전략
  • GitOps 관리와 워크로드별 노드 분리: 부트스트랩 계층(Karpenter·LBC·ArgoCD)은 helmfile, 나머지 플랫폼 컴포넌트는 ArgoCD로 관리하고, Karpenter 노드 풀은 모두 ARM으로 두되 게임 서비스는 세션 중 노드가 회수되지 않게 On-Demand에, CI 러너는 여러 인스턴스 패밀리의 Spot에 분산
  • 네트워킹·인증 자동화: AWS Load Balancer Controller·ExternalDNS·wildcard ACM 인증서로 Ingress만 선언하면 ALB 규칙·DNS·HTTPS가 자동으로 이어지게 하고, 모든 ServiceAccount에 Pod Identity/IRSA를, 시크릿에 External Secrets Operator를 적용해 워크로드의 정적 IAM 키 제거
트러블슈팅
  • 빈 노드가 회수되지 않던 문제: 실사용 101MiB인 서비스의 메모리 request 2GiB를 512MiB로 낮춰 92%와 35%로 벌어졌던 노드 점유를 고르게 맞추고 Consolidation이 동작하게 함
  • 노드 교체 시 Pod 쏠림과 Consolidation 루프: AMI 교체 때 한 서비스의 Pod 2개가 새 노드 한 대에 몰려 17초간 Degraded된 문제를 배포 버전 단위의 노드 간 분산 제약으로 해결. 같은 제약을 다른 서비스에 걸자 사용률 기반 Consolidation이 약 7분 30초마다 노드를 16번 다시 띄워, 운영 중인 Pod를 계속 축출하느니 빈 노드만 정리하는 정책으로 되돌림
성과
  • 신규 게임 전용 AWS 계정에 EKS 프로덕션 환경을 처음부터 구축하고, 플랫폼 매니페스트 100%를 Git으로 선언 관리(IAM 제외)
  • Bastion SSH 키(배포를 Jenkins → S3 → CloudFront·SSM 경유로 전환)와 클러스터 워크로드의 정적 IAM 키를 제거하고, CI 에이전트에 남은 AWS 키는 역할 전환 권한만 갖도록 제한
7-2. OpenTelemetry 엔드투엔드 분산 추적 파이프라인 (OTel + Tempo, 2026.07 ~ 현재)
문제
EFK 로깅과 Prometheus 메트릭만으로는 마이크로서비스 사이의 호출 흐름, 지연이 생기는 구간, 에러가 번지는 범위를 알기 어려웠습니다.
접근 전략
  • 추적 스택과 자동 계측: OpenTelemetry Collector와 Grafana Tempo(S3)를 구축하고 OTel Operator 자동 계측으로 코드 수정 없이 SDK 주입
  • 메트릭 추출 지점과 저장 지점을 분리: RED 메트릭은 샘플링 전 100% Span에서 뽑아 집계를 정확히 유지하고, 저장은 Tail Sampling(에러 전체 + 500ms 초과 요청 + 정상 요청 10%)만 남겨 비용을 줄임
성과
  • Metrics·Traces·Logs를 Grafana 한 화면에서 오가게 연결해 서비스 간 병목을 가시화하고, 트레이스에서 그 요청의 로그만 trace_id로 바로 열리게 함
  • Collector replica마다 커넥션이 고정돼 메트릭 시리즈 1,650 : 541로 한 replica에 쏠려 있던 부하를, Trace ID 기반 2계층 라우팅으로 두 샘플링 인스턴스가 초당 Span 4.09 : 5.18로 고르게 나눠 받게 함
7-3. Argo Rollouts 기반 Canary 무중단 배포 전환 (Blue-Green → Canary, 2026.07 ~ 현재)
Blue-Green 배포는 promote 때 Target Group을 통째로 바꿔, 새 Pod가 등록되기 전에 기존 Pod가 빠지면 요청이 503으로 실패했습니다. 같은 Target Group 안에서 새 Pod가 준비된 뒤 구버전을 내리는 Canary로 바꾸고 ALB 등록 해제 지연(30초) < preStop(35초) < 종료 유예(60초)로 종료 시점을 맞춰, 공개 트래픽을 받는 메인 서비스의 하위 호환 패치를 무중단으로 배포합니다. 두 버전이 함께 떠 있으면 안 되는 변경은 정기 점검 때 반영합니다.
7-4. 소프트 런칭 운영 (2026.07 ~ 현재)

  • 소프트 런칭 2주간의 실트래픽을 근거로 Pod requests·limits를 다시 잡아, requests가 과도해 HPA가 스케일아웃하지 못하던 구조를 바로잡고 requests를 CPU 48%·메모리 71% 줄임
7-5. SLI/SLO·에러 버짓 정의 (2026.08)
샘플링 전 전체 Span에서 뽑은 요청 지연시간으로 SLI 기록 규칙과 에러 버짓 소진을 비교하는 SLI/SLO 대시보드를 만들고, 늘 통과해 의미가 없는 목표('p95 2초 미만' 등)는 실측 분포로 걸러냈습니다. 게임 서버가 예외에도 HTTP 200을 돌려줘 약 790만 건의 요청 Span 중 에러가 0건이어서, 장애 중에도 100%로 보일 가용성 SLI는 애플리케이션이 에러를 에러로 돌려주기 전까지 보류했습니다.
7-6. 게임 CDN 엣지 보안: AWS WAFv2 적용 (2026.07 ~ 2026.09)
런칭을 앞두고 WAF 없이 노출돼 있던 게임 CloudFront 앞단에 WAFv2를 도입했습니다. AWS 관리형 룰 그룹 4종을 Count 모드로 실트래픽에서 먼저 관측해 정상 유저를 막지 않았고, 이후 내부 API 경로는 운영자 허용 IP 밖의 요청을 차단했습니다. CGNAT 뒤의 유저까지 막을 수 있는 Rate-based 룰은 데이터가 쌓일 때까지 보류했습니다.
프로젝트 8: EKS Auto Mode 클러스터로 프로덕션 이관과 Site-to-Site VPN(WireGuard) 게이트웨이 구축
