문제

접근 전략

  • GitOps 기반 지속 배포(CD) 파이프라인 구축 - GitLab CI와 ArgoCD를 연계해 Git Push를 트리거로 빌드 → 테스트 → 배포 전 과정을 자동화하고, Git에 선언된 형상과 클러스터 상태 간 불일치를 감지해 자동 복구(Self-healing)하도록 구성. dev·qa·review·prod 4개 환경의 배포 로직을 단일 파이프라인으로 통합해 관리 일관성 확보
  • 최소 권한 기반의 안전한 이미지 빌드 환경 수립 - Docker-in-Docker(DinD)는 호스트 관리자 권한(Privileged 모드)이 필요해, 도커 데몬 없이 사용자 영역(User-space)에서 컨테이너 이미지를 빌드하는 Kaniko로 전환. 빌드 컨테이너에서 Privileged 권한을 제거해, 빌드 잡이 침해되더라도 호스트까지 장악될 위험을 낮춤

트러블슈팅

  • ArgoCD 연쇄 삭제(cascading prune) 방지 - Git 커밋 오류로 하위 Application이 연쇄 삭제되지 않도록, 워크로드 Application은 prune: true + selfHeal: true로 자동 일치시키고 최상위 app-of-apps 루트·AppProject 계층은 prune: false로 두어 삭제는 수동 검증을 거치게 함. 모든 sync 이벤트는 Slack 알림으로 실시간 추적
  • 정적 데이터 배포 경로에서 SSH 키 제거 - CI 배포 계정이 SSH 키를 보유한 채 대상 인스턴스에 직접 접속(scp/rsync)하던 구조를, 산출물을 S3 중계 버킷에 올리고 SSM SendCommand로 인스턴스가 스스로 내려받는 방식으로 교체해 배포 환경의 정적 SSH 키를 완전히 제거하고 키 유출 경로를 없앰

성과

문제

개별 저장소(Repo)의 CI 잡마다 Alpine 베이스에 필수 도구(helm·helmfile·kubectl·crane·aws-cli)를 매번 설치해 빌드 환경 프로비저닝에 평균 5분이 소요되었습니다. 또한 도구 버전이 저장소별로 파편화되어 신규 버전 반영 시 전수 수정이 필요했고, :latest 태그라 이미지 안에 어떤 버전이 들어 있는지 알기 어려웠습니다.

접근 전략

  • Layer 1 (Mirror): 외부 레지스트리(Docker Hub, GHCR)의 도구 이미지를 멀티 아키텍처 매니페스트를 유지한 채 crane copy로 사내 Harbor에 미러링해 외부 의존성 제거
  • Layer 2 (Custom): Layer 1을 기반으로 사전 빌드된 공용 이미지 5종을 구성해 개별 저장소가 이미지 태그 지정만으로 도구를 즉시 활용하도록 표준화
  • 버전 관리 체계 일원화: 공용 빌드 템플릿과 중앙 버전 변수를 정의해 각 저장소가 개별 도구 태그를 직접 추적하지 않도록 함
  • 공용 CI 템플릿 모듈화: 저장소마다 복사해 쓰던 CI 잡을 공용 템플릿 저장소로 통합하고 include 방식으로 참조. 공용 앵커와 주요 잡(정적 키 없는 AWS 인증, Kaniko 빌드, ArgoCD 배포, 백업)을 중앙에서 관리하고, 모든 저장소가 같은 템플릿을 참조하게 해 공통 잡이 저장소마다 달라지지 않게 함
  • 자동 버전 사이클 구축: Upstream 신규 버전 감지부터 각 저장소 전파까지 자동화하되, 파이프라인 실행과 Tier 2 MR 승인은 사람이 직접 확인하도록 남겨 안정성 확보:
       · (1) Upstream 신규 버전 감지 (주간 스케줄러)
       · (2) Layer 1 미러링 자동 MR 생성
       · (3) Layer 2 리빌드 및 중앙 버전 변수 동기화 자동 MR 생성
       · (4) Consumer 저장소 대상 일괄 자동 전파 (템플릿 제공 저장소 제외)

트러블슈팅

  • 도구 간 버전 충돌로 인한 공용 이미지 빌드 실패: 자동 버전 상향 중 helmfile 1.5.1이 요구하는 helm 최소 버전(3.18.6)이 기존 고정 버전(helm 3.16.4)보다 높아 빌드 파이프라인이 멈춤
  • 원인 및 해결: 도구 간 의존성은 upstream 릴리스 노트에만 나와 있어 미리 자동으로 감지할 수 없다고 판단. helm·helmfile·kubectl에 minor-guard를 도입해 동일 minor 내 patch 버전만 자동 상향되도록 통제하고, minor·major 변경은 호환성 검증 후 수동 승격하도록 분리(필요할 때 환경 변수로 한 번만 예외 적용)

  • Consolidation이 노드를 끝없이 교체하던 문제: Pod 분산 제약을 하나 더 걸자 Karpenter의 배치 판단과 실제 스케줄 결과가 어긋나, 약 7분 30초마다 노드를 지우고 곧바로 새로 띄우는 일이 16번 반복됨. 원인을 사용률 기반 정리의 시뮬레이션 불일치로 보고 빈 노드만 정리하는 정책으로 되돌림. 운영 중인 Pod를 반복해서 축출하느니 사용률이 낮은 노드를 남겨 두는 편을 택했고, 스케일아웃이 아직 없는 소프트 런칭 규모라 그 추가 비용이 크지 않다고 판단
  • 기동 중인 Pod로 트래픽이 들어가던 문제: ALB가 아직 준비되지 않은 Pod에 트래픽을 보내 간헐적으로 5xx가 나던 것을 ALB Pod Readiness Gate로 해결. Target Group 헬스체크를 통과해야 Pod가 Ready로 판정되게 함

문제

기존 Blue-Green 배포는 승격할 때 ALB Target Group을 통째로 바꾸는데, 새 Pod가 등록되기 전에 기존 Pod가 먼저 빠지면 트래픽을 받을 Pod가 없어 그 사이 들어온 요청이 503으로 실패했습니다.

  • Stateless 구조 전제: 게임 서비스는 상태를 JWT와 Redis·DB(TypeORM)에 두는 stateless HTTP라, 전환 중 구버전과 신버전에 요청이 섞여도 결과가 같음을 확인. 다만 두 버전이 함께 떠 있으면 안 되는 변경(API 스펙 변경 등)은 이 방식으로 배포하지 않고 정기점검 시간에 처리
  • 배포 진입·종료 시점 맞추기: ALB Pod Readiness Gate로 ALB에 정상 등록된 Pod만 Ready로 치고, 종료 시에는 ALB 등록 해제 대기(30초)보다 preStop(35초)을, preStop보다 전체 종료 유예(terminationGracePeriodSeconds, 60초)를 길게 잡아 ALB에서 빠진 뒤에 Pod가 내려가게 함(SIGTERM에서 스스로 처리 중인 요청을 정리하는 .NET 서비스만 75초)
  • 배포 전략 템플릿화·컨트롤러 HA: 공용 Helm 차트에서 설정값으로 Deployment와 Rollout을 바꿀 수 있게 템플릿화해, 공개 트래픽을 받는 프로덕션 게임 메인 서비스에만 Canary를 적용하고(같은 게임의 내부 서비스는 일반 Deployment 유지), 컨트롤러는 replica 2개의 Leader Election과 PDB로 노드가 교체될 때 둘이 함께 내려가지 않게 함

문제

신규 퍼블리싱 게임은 퍼블리셔 내부 인증 계정과 공용 인터넷을 거치지 않는 사설 경로로 통신해야 해 VPC 피어링이 필요했습니다. 그런데 기존 프로덕션 VPC 대역이 피어링 요건과 맞지 않아 VPC부터 클러스터·데이터 계층까지 새로 만들어야 했고, 퍼블리셔는 새 클러스터를 EKS Auto Mode로 구성해 달라고 요청했습니다. 기존 클러스터는 관리형 노드그룹 위에 Karpenter를 직접 운영해 컴퓨트 쪽 Terraform 관리 대상이 많았고, 노드 수명주기·Spot 중단·핵심 애드온도 직접 관리해야 했습니다. 또 VPC 피어링은 다른 망을 거쳐 가는 경로를 지원하지 않아 온프레미스에서 내부 ALB로 가는 사설 경로를 따로 만들어야 했습니다.

접근 전략

  • EKS Auto Mode로 컴퓨트 계층을 관리형으로 전환: 노드 프로비저닝과 수명주기, Karpenter 운영에 필요한 AWS 리소스(IAM·SQS·EventBridge), 내장 애드온(LB Controller·EBS CSI)을 AWS 관리에 맡기고, 코드에는 NodePool 선언만 남김
  • NodePool을 ArgoCD보다 먼저 배포하는 부트스트랩 순서 설계: 모든 NodePool을 Graviton(arm64)으로, 빌드 풀은 Spot으로 쓰려고 amd64·On-Demand로 고정된 내장 general-purpose 풀을 끄자, 남은 system 풀의 CriticalAddonsOnly 테인트 때문에 자체 NodePool이 생기기 전에는 일반 Pod가 올라갈 노드가 없음. NodePool까지 ArgoCD로 배포하면 클러스터 재구축 시 ArgoCD부터 Pending에 멈추므로, NodePool·IngressClass는 ArgoCD보다 먼저 helmfile로 배포하는 Tier 0 단계에 남김
  • IPAM 제약에 맞춘 재설계: 할당받은 /18을 /20 4개가 정확히 채워 서브넷을 늘릴 수 없어, 데이터 계층을 전용 서브넷으로 떼어 두던 구조 대신 AZ별 private 서브넷 안에서 보안 그룹으로 격리하도록 바꾸고, Aurora·Valkey·EFS를 이 구조로 옮기는 코드를 전환에 앞서 작성
  • Site-to-Site WireGuard VPN 게이트웨이 구축: 퍼블릭 ALB를 하나 더 두면 같은 서비스가 호스트명·인증서·DNS 레코드를 따로 갖게 되고 환경이 하나 늘 때마다 그 세 가지가 함께 늘어나므로, 대신 터널링을 택해 단일 도메인·인증서 체계를 유지한 채 모든 내부 트래픽이 사설 경로로 통신하도록 설계. 온프레미스에서 AWS(EIP) 방향 아웃바운드로 터널을 수립하고, Peer Endpoint를 비워 첫 핸드셰이크 과정에서 상대 주소를 동적으로 학습하도록 구성
  • VPC 정적 라우트를 사무실 라우터 한 곳에서 관리: 노드마다 라우트를 넣으면 설정이 빠진 노드의 Pod만 VPC에 닿지 못해 Pod 위치에 따라 성공과 실패가 갈리는 부분 장애가 생기므로, 라우트를 라우터에만 두어 경로 문제가 모든 호스트에서 한꺼번에 드러나게 함
  • Terraform 밖 의존 요소 관리: terraform plan으로 감지되지 않는 터널의 외부 의존 요소 세 가지(라우터 정적 경로·게이트웨이 설정 파일·개인키)를 런북에 문서화. 개인키는 state에 평문으로 남지 않도록 Terraform 밖에서 AWS SSM Parameter Store SecureString으로 생성하고 게이트웨이가 부팅 시 조회
  • 플랫폼 컴포넌트 호환 마이그레이션: 관측성·보안·CI 도구 등 16개 핵심 플랫폼 컴포넌트를 Auto Mode 사양에 맞게 재구성하고, 10개 컴포넌트를 ArgoCD pull-GitOps 관리 체계로 전환

트러블슈팅

  • Auto Mode가 ALB 그룹 어노테이션을 무시하는 문제 해결: Auto Mode 내장 컨트롤러는 여러 Ingress를 ALB 하나로 묶는 group.name 어노테이션을 읽지 않고 IngressClassParams로만 그룹을 인식함. ALB stack 태그에 그룹명 대신 Ingress 이름이 붙은 것으로 식별했고, 그대로 두었다면 service 그룹 Ingress 5개 중 4개와 공개 호스트가 ALB를 받지 못할 상황이었음. ALB 그룹마다 IngressClass·IngressClassParams를 선언하고, 클래스를 옮기면 ALB가 재생성되므로 Ingress를 먼저 지워 이름 충돌 없이 옮김
  • NodeClass API 그룹 변경 및 미지원 애드온 분리: Auto Mode에서 NodeClass API 그룹이 karpenter.k8s.aws/v1 EC2NodeClass에서 eks.amazonaws.com/v1 NodeClass로 바뀌어 기존 매니페스트와 호환되지 않음. 스펙을 신규 CRD에 맞춰 다시 쓰고, Auto Mode에 없는 EFS CSI Driver는 별도 배포로 분리

성과

  • 새 클러스터에서 컴퓨트 계층의 Terraform 관리 대상이 102개에서 17개로 83% 줄고, Karpenter 컨트롤러와 그 운영에 필요한 IAM·중단 이벤트 처리는 AWS가 운영하며 노드 풀 정책만 NodePool로 직접 관리
  • 온프레미스·AWS 간 Site-to-Site VPN 게이트웨이를 구축해 내부 ALB의 공용 인터넷 노출 없이, 환경이 늘어나도 단일 내부 호스트명과 단일 TLS 인증서 체계를 그대로 유지

문제

게임·블록체인 데이터를 수동으로 수집하다 보니 분석가가 매일 2~3시간을 소비했고, 휴먼 에러로 인한 데이터 누락도 빈번했습니다.

접근 전략

  • 멀티 소스 BigQuery 적재 - MongoDB는 Dataflow Flex Template ETL, CloudSQL은 BigQuery 직접 connection, Google Analytics · Dune은 각자 API(Dune은 별도 API Key)로 적재, 공통 스키마로 정규화

  • 전체 인프라 Terraform IaC - BigQuery Dataset · Cloud Function · Scheduler · Cloud Storage · Artifact Registry · IAM · Service Account를 코드로 관리

트러블슈팅

  • CloudSQL → BigQuery 직접 connection(federated query)이 리전 불일치와 connection Service Account 권한 부족으로 실패. connection을 동일 리전에 생성하고 connection SA에 Cloud SQL Client 권한을 부여하여 해결
  • Dune API의 execute → poll → fetch 비동기 실행 구조와 요청 한도로 결과 누락·타임아웃 발생. 실행 상태 폴링과 백오프로 결과 수신을 보장하고 API Key를 Secret Manager로 분리
  • Daily 재실행 시 동일 레코드가 BigQuery에 중복 적재되는 문제 발생. 중복 제거 Cloud Function에 MERGE 및 ROW_NUMBER() 기반 정합성 로직을 적용해 적재를 멱등화
  • BigQuery 결과를 Google Sheets API로 적재할 때 호출이 몰리면 분당 요청 한도(429)에 걸리고, 결과가 크면 한 번에 쓰지 못해 갱신이 실패. 결과를 1,000행씩 나눠 날짜별 시트에 쓰고, 호출 사이에 간격을 두며 한도를 넘으면 지수 백오프로 재시도하게 해 한도 안에서 동작하게 함

  • 전체 인프라를 Terraform으로 관리해 같은 파이프라인을 다른 GCP 프로젝트 3곳에 빠르게 재구축하고, 변경 이력은 Git으로 모두 추적

Windows에서 손으로 하던 세팅을 Linux와 세팅 스크립트로 대체하고, 그 스크립트를 사내·GCP·외부 IDC GPU 서버 전체의 표준 구축 절차로 사용

기술 글 2

자세히 보기

문제

사내 GPU 서버가 Windows로 운영돼 이미지 생성 모델(Stable Diffusion 계열)을 돌릴 때마다 엔지니어가 실행 환경을 직접 세팅해야 했습니다. 드라이버·CUDA·프레임워크 조합을 손으로 맞추다 보니 같은 환경을 재현하기 어려웠고, 장비는 있는데 쓰기까지 시간이 걸렸습니다.

접근 전략

  • Windows → Linux 표준화 - 사내 GPU 서버를 Ubuntu 22.04로 전환하고, 세팅 스크립트 하나로 드라이버 스택(nvidia-driver-550 · CUDA 11.8 · cuDNN 8.6) 설치·동작 확인, 공유 모델 저장소(NFS) 마운트, GPU별 Stable Diffusion WebUI 기동까지 처리해 어느 서버에서나 같은 환경을 재현. LoRA 학습용 kohya_ss와 ComfyUI도 같은 구성에 배치
  • GCP 클라우드 확장 - A100 40GB와 L4 GPU VM을 Terraform으로 관리하며 수요에 맞춰 구성을 바꿔 운영하고, 최대 A100 4장과 L4 8장까지 확장. 리전·존별 GPU 가용성 확인과 쿼터 상향을 거쳐 앞선 마이그레이션의 Shared VPC 서브넷에 연결해 네트워크 표준 유지
  • 외부 IDC 20대 증설·워크로드별 카드 분리 - 같은 세팅 스크립트로 GPU 서버 20대 구축. 학습은 VRAM이 큰 카드가 필요하고 추론은 요청마다 독립적이라 GPU 수만큼 처리량이 늘어, 학습·대용량 작업은 GCP A100, 대량 추론은 IDC의 소비자용 RTX 40 시리즈로 나눠 배치

성과
